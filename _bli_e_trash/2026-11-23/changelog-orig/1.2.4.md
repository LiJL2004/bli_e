## v002 修：夜间模式下节点表脚部三行文案看不清

**现象**：设置面板 →「功能增强」→ 节点表，夜间模式下弹窗底色已经是 `#202226`，
但脚部「重测次数 / 重测全部节点 / 节点管理」三个标签仍是 `#1c1c1e` —— 深灰字落在
深灰底上，几乎看不见（用户截图里只剩滑块和数字还能认出来）。

**原因**：`.label` 的深色写在 panel.css 的通用规则里，夜间版本只有
`.panel.is-night .label` 这一条。节点表弹窗 `.cdn-mask` 是 `.panel` 的**兄弟节点**
（`.panel` 自己有 `transform`，弹窗放里面的话 `position: fixed` 会以面板为参照），
所以那条规则根本选不中它 —— 和 1.2.3 v011 加弹窗时要单独切一份 `is-night` 是同一个坑，
那次只补了行、标题、说明、按钮，漏了脚部的 `.label`。

**改法**：在节点表那组夜间规则里补一条
`.cdn-mask.is-night .cdn-dialog-foot .label { color: #e6e8ec; }`，与面板夜间标签同色。
弹窗里只有这三行用 `.label`，不用再判 `.panel`。

滑块轨道保持浅色渐变没动：它是 `::after` 的强调色填充，在深色卡片上对比度足够，
压暗反而会和行底色糊在一起。

## v001 夜间模式浮钮 + 整页圆形过渡 + 消息中心夜间背景

三件事，都属于「夜间模式终于能随手开关、且真的全站变黑」。

### 1. 操作浮钮新增「夜间模式」键（`fabNightMode`，默认显示）

`features.ts` 里新增 `fabNightMode`（`界面优化`，`default: true`），按现有约定顺着
`fabHalfHide` 往后排，自动并进「操作浮钮」那张卡。**注意默认值只管这颗按钮的
可见性**：`nightMode` 本身仍然默认 `false` —— 改整站配色不该替用户决定，但「入口」
放在手边没有副作用。

`floatingButtons.ts` 里常驻渲染这颗键（放在栈末尾、最靠近 ⚙），关掉开关时用现成的
`.fab.is-hidden` 收掉，不重排 DOM。图标是月亮 / 太阳两枚 SVG 叠在 `.fab-ic` 里做
透明度 + 反向旋转的交叉切换（`floatingButtons.css`），夜间整列 `.stack.is-night`
换成深底浅字 —— 只换一颗键会在一列白圆里格外扎眼。

### 2. `setNightMode()`：以点击处为圆心的整页过渡

新增 `labFeatures.ts → setNightMode(on, origin?)`，浮钮与设置面板都走它，不要自己
`persist({ nightMode })`。参考 `bili_cat` 的 `useDark`：

- `document.startViewTransition()` 里执行 `persist()` —— 新旧快照是回调前后的两帧，
  回调外的类名变化进不了「新」那一帧；
- 回调里 **等主题表换好**（`waitForTheme()`，上限 300ms）。`light.css → dark.css`
  是异步的，实测 20~50ms；不等就会先拍到一个亮色页面，圆铺开以后里面还是白的，
  300ms 后才突然变黑；
- `transition.ready` 后给 `::view-transition-(old|new)(root)` 指定 z-index，并用
  `Element.animate(..., { pseudoElement })` 做 `circle()` clip-path；
- 过渡期间挂 `*{transition:none!important}`，避免快照底下颜色补间导致扩散边缘对不上
  （浮钮在 Shadow DOM 里，不受影响）；
- 不支持 View Transitions 或 `prefers-reduced-motion: reduce` 时直接 `persist()`。

`designTokens.css` 里常驻两条 `::view-transition-old/new(root){animation:none;
mix-blend-mode:normal}` —— 默认的 root 交叉淡入会把两帧叠成一层灰；而且夜间模式
第一次打开时 `night.css` 还没注入，这两条不能放在那里。

设置面板的 `input[data-key]` 处理器为 `nightMode` 单开一条分支，圆心取开关自身的
`getBoundingClientRect()` 中心，这样从面板里切换也是从开关处铺开。

### 3. 消息中心（`message.bilibili.com`）夜间背景

它是个独立应用，主题**只看 cookie `theme_style`**（`created()` 里读一次），不看
`bili_dark`；调色板会跟着 `bili_dark` 变，但铺满整屏的背景图是 Vue 里
`bgSrc = .../${this.theme}_bg.png`，初始 `theme` 固定 `'light'`。所以外挂
`bili_dark` 后文字 / 面板都深了、背景图还是浅色 pastel。

不去动 B 站 cookie（跨子域共享，关掉扩展还会残留），在 `night.css` §6 直接把
`.message-bg`（`#skeleton-bg` 也带这个类）的 `background-image` 用 `!important`
换成同目录的 `dark_bg.png`；`.message-bgc` 再兜一条 `#1D2736` 背景色。

## v003 节点表重测改成「按次数循环 N 轮」+ 实时进度

**改法**：`guard.js` 的 `retestAll()` 从「一个节点连着测 N 次再换下一个」改成
**外层轮、内层节点**的二维循环 —— 第 1 轮把表里所有节点挨个测一遍，第 2 轮再来一遍，
共 `重测次数`（2~6）轮。每轮重新取一段 Range（第 1 轮测文件开头，之后每轮 `sampleOffset()`
随机），节点在表里的位置不再决定它在什么时间段被测量；N 轮读数求平均后覆盖长期表
（不加权，同 v012）。预热还是只在每个节点第一次碰到时做一次 1 字节请求。

**进度**：每开始测一个节点就把 `STATE` 写一次 `{ round, rounds, idx, n, host }`。
节点表弹窗新增一行进度条（`#cdn-progress`，文字 + 细条）显示
「重测中：第 2/3 轮 · 第 5/14 个节点（mirrorhwb）」；卡片下面那行状态字同样显示。
**弹窗的遮罩盖住了卡片，所以进度必须画在弹窗里** —— 重测按钮就在弹窗脚部，用户点完
看到的就是弹窗。面板轮询从「固定 90s 截止」改成**跟着 state 续期**（guard 每测一个节点
刷新 `ts`，25s 内还在动就继续轮询），节点多 / 轮数多时不会半路停在「测速中…」。

**顺带**：

- `CdnState` 增加 `round` / `rounds` / `idx` / `host`；`done` / `total` 的含义收窄成
  「当前这一轮已测完几个 / 一轮共几个」，旧的「重测进度 3/14」文案改成「第几轮第几个」；
- 重测按钮在跑重测时写「重测中…」，跑普通测速时仍是「测速中…」；
- 弹窗说明的「重测取多次平均」改成「重测按轮次取平均」。

`DEV_VERSION` → `1.2.4 v003`。

## v004 「触发面板材质」补上自绘顶栏的悬停浮层

**现象**：「高级材质 → 触发面板」打开后，原生顶栏的频道面板、右侧头像 / 消息浮层、
卡片「⋮」菜单都变成毛玻璃，但**自绘顶栏（顶栏优化）**下右侧那五个悬停浮层
（头像 / 消息 / 动态 / 收藏 / 历史）仍然是纯白卡片 —— 同一块材质，一半跟、一半不跟。

**原因**：那五个浮层是我们自己画的（`selfTopbar.ts`，结构
`.tb-item > .tb-pop > .tb-pop-card`），和 topbar.css §7 里那套 B 站原生
`.v-popover` 完全不是一批节点，§7.1 / §7.2 / §7.5 一个选择器都命中不了。
1.1.6 做这块材质时也确实是按「浮层不跟毛玻璃」写的（当时原生面板就是纯白卡片）。

**改法**：`selfTopbar.css` 新增 §5.1，挂 `html.bili-elite-homepanel-glass`：

- `.tb-pop-card` 换成和 §7.2 完全同一组值（`--bili-homepanel-tint` 61% 白底 +
  顶部 12% 白高光 + `blur(--bili-homepanel-blur)` `saturate(190%)` `brightness(1.06)` +
  1px 半透明白描边 + 两层投影），不新开滑块；
- 条目悬停底 `.tb-media:hover` / `.tb-fav-cat:hover` 从 `#f6f7f8` 换成
  `rgba(120,120,128,.12)`，否则毛玻璃上是一块不透明白板（同 §7.1 频道面板条目）；
- **淡入挪一层**（§7.3 同一个坑）：`.tb-pop` 的 `opacity` 是 0→1 过渡的，祖先
  `opacity < 1` 会成为背景根 → 整段 180ms 里卡片采不到后面的页面内容，最后一帧才
  「啪」地糊上。材质开着时把 `.tb-pop` 的 `opacity` 钉成 1（开合仍靠
  `visibility` / `pointer-events`），淡入改挂到 `.tb-pop-card` 自己身上
  （打开 120ms / 关闭 90ms，与 `.tb-pop` 原时长逐条对齐）。

夜间（`night.css` §1.3.1）：补一条深色玻璃，值抄 §4 频道面板 / §4.3 ⋮ 菜单那一套
（`rgba(26,27,31,max(.78,tint))`、`saturate(180%) brightness(.55)`、白 8% 描边），
悬停底换 `rgba(255,255,255,.08)`。

## v006 修：动态悬浮打开点了还是跳转 + 悬浮窗改按 bili_cat 的样子重画

### 1. 点击不生效：`$log` 是页面世界的 expando，隔离世界读不到

**现象**：打开「动态悬浮打开beta」后点动态正文，还是照旧整页跳 / 开新标签页，悬浮窗一次都没出来。

**原因**：v005 的地址解析直接读 `.bili-dyn-time` 上的 `$log.click.url`（B 站 v-log 指令
挂的）和兜底的 `__vue__.id`。这两个都是**页面世界的 JS expando**，而内容脚本跑在隔离世界：
同一份 DOM 在两边是两套 JS 包装对象，expando 不跨世界。单独写了个探针扩展实测，页面里
`document.body.__test__ = 'x'` 之后，内容脚本读同一个节点拿到的是 `undefined`。

于是 `resolveDetailUrl()` 永远返回 `null` → `onClick` 在 `preventDefault` 之前就早退 →
B 站原版行为照常发生。**用合成点击验证过**：`e.defaultPrevented` 一直是 `false`。

**改法**：让页面世界的 `guard.js` 代读（新增 §8），通道沿用仓库里既有的「属性当数据、
事件当敲门砖」：

- 内容脚本给那条动态挂 `data-blie-dyn-ask`，再 `dispatchEvent` 一个**不带 detail** 的
  普通 `Event`（`CustomEvent.detail` 跨世界会被抹成 `null`，§7 那条注释早就记过 ——
  这次又实测了一遍：主世界监听里 `e.detail` 就是 `null`）；
- `guard.js` 同步解析 `$log.click.url` / `__vue__.id`，写回 `data-blie-dyn-url`；
- 内容脚本读出来、擦掉两个属性。全程同步，所以能在同一个 click 里决定拦不拦。

监听只在 `t.bilibili.com` 挂，别处一个字节都不多；`guard.js` 没装上就读到空，退回原版跳转。

**验证**（探针 chromium + `--load-extension`，动态页真点正文）：页面地址不变、
`#bili-elite-dynamic-host` 出现、标签页数仍是 1、iframe 的 `src` 是
`https://t.bilibili.com/720941201754161156`。

### 2. 悬浮窗样式对标 bili_cat（BewlyCat）的动态详情弹窗

原来是我们自己那套「标题栏 + 蓝色圆点 + Esc 副标题」，和 bili_cat 不像。现在逐条对齐
它的 `Dialog` / `moment-detail-*`：

- **去掉标题栏**，窗口本身就是一整页详情（bili_cat 是 `show-header=false` + `content-flush`）；
- 圆角 18 → **24**（`--bew-modal-radius`），描边 `rgb(131 131 145 / 18%)`，
  投影换成 `--bew-shadow-4` + 内侧高光 `--bew-edge-glow-2`；
- 「新标签页」和关闭键从标题栏挪到**窗口右下角外面**一行（往下让 12px、右对齐、间距 8），
  两个都是白底胶囊 / 圆形 + `--bew-shadow-2`，34 / 32 高；
- 遮罩从「半透明 + 10px 模糊」改成**纯黑 40%**（`bg="black opacity-40"`）；
- 进出动画只留 140ms 淡入淡出（bili_cat 的 `moments-dialog` 就不做位移 / 缩放）；
- 窗口尺寸 `min(1088px, 100vw-64px)` × `min(100dvh-64px, 88dvh)`，四边留 32px；
- 夜间换 bili_cat 的 dark token（底 `#1F2125`、控件 `#33363B`、描边 16%）；
- iframe 里那层「去顶栏 + 内容居中」的样式同步换底色（亮 `#FFF` / 暗 `#1F2125`，
  卡片圆角 16、内容宽 820），并补一条**根滚动条**样式 —— `color-scheme: dark` 下
  Chrome 给的还是浅灰轨道（实测 rgb(138,138,138)），压在深色窗口右边缘上是一条亮线。
  只挑 `html` / `body` 自己的滚动条，别用后代选择器（评论列表、图片画廊的滚动条是
  B 站自己画的）。

**顺手删掉**：`.dyn-window` 的 `backdrop-filter`。窗口里是不透明的 iframe（loading 层也是
实底），毛玻璃一帧都露不出来，却要按 1088×663 整片做背景采样 —— 纯白花的 GPU。

小窗口（宽 ≤720 或高 ≤560）时窗口贴边留 16px，按钮那行改放窗口**里面**右下角，
否则 12 + 34 的按钮行会掉出视口。

## v007 悬浮窗内部改两栏：纯文字「文字左 / 评论右」，有图「图片左 / 文字+评论右」

**为什么做**：v006 之后窗口里就是一整页详情照搬，1088 宽的窗口里正文只有 820 居中，右边
一大片空白，评论还得往下滚很远 —— 16:9 的大窗口里这个比例是浪费的。bili_cat 的动态详情
弹窗是分栏的，跟着做。

**布局**（只有窗口够宽够高才开：iframe 宽 ≥ 900 且高 ≥ 480，否则保持原来的单栏居中）：

- 纯文字：左栏 = 正文（作者 / 文字 / 视频卡 / 专栏卡），右栏 = 评论区，各自滚动；
- 有图：左栏 = 图片舞台（单图 contain 居中，多图按张数铺 2 / 3 列），右栏 = 正文（上）+
  评论区（下），右栏整体滚动。

**为什么搬 DOM 而不是纯 CSS**：详情页的树是 `.card > [.bili-dyn-item, .bili-tabs]`，
「图片」却藏在正文内部（`.dyn-card-opus__pics`）。要让图片和评论同列就得跨子树移动，
CSS Grid 挪不了跨层级节点；`display: contents` 又要连着压平 7 层 B 站包装盒（每层都有
自己的 padding / 背景，压平后全得重写），B 站改一个类名整块就塌。搬 3 个节点只有 3 个前提
（`.card` / `.bili-dyn-item` / `.bili-tabs`），任何一个找不到就原地放弃、退回单栏，不会
出现「半个分栏」。新模块 `dynamicOpusLayout.ts`（`applyOpusSplit` / `resetOpusSplit`）。

**踩到的坑**：

- **`.bili-dyn-item` 自带 `min-width: 556px`**（动态流那边的定宽），搬进 391 的窄栏直接
  横向溢出、文字被裁掉半行。必须 `min-width: 0`。
- 正文的头像列是 `padding-left: 88px` + 绝对定位头像。窄栏里这 88px 决定一行能放几个字 →
  收到 68（头像 56）、右内边距收到 0、`.bili-dyn-item__desc` 的 `padding-right` 120 → 72。
- **窄栏自己的滚动条**：`color-scheme: dark` 下 Chrome 还是给浅灰轨道，深色窗口右边缘一条
  亮线 → 两栏的 `::-webkit-scrollbar` 也一起换成细条（同 iframe 根滚动条那套）。

## v010 修：页面开着很久之后，顶栏搜索点了没反应

**现象**（用户报）：某个页面闲置很久，再用顶栏搜索框搜东西 —— 回车、点热搜、点历史，
**一点反应都没有**（不开新标签页、本页也不跳）。页面本身、面板、热搜都还是正常的。

**原因**：内容脚本和扩展的连接会断，断掉之后这一页里的 `chrome.*` 不但用不了，**调用还会
同步抛** `Error: Extension context invalidated.`。触发点最常见的就是「页面开着的时候扩展
被重新加载 / 自动更新」（商店版每几小时查一次更新，装上就重载一次，所有已打开的页面当场
变孤儿）。

而 `go()` 里 `pushHistory()` 排在 `window.open()` **前面**：

```js
pushHistory(kw)            // ← chrome.storage.local.set 在这里抛
closePanel()
const win = window.open(url, '_blank')
```

三个调用点（表单 submit / 回车选中行 / 点面板行）**都是先 `preventDefault()` 再进 `go()`**，
异常一抛，浏览器原生的表单提交也已经被掐掉了 —— 于是「什么都不发生」。
顶栏是断连之前画好的，面板、热搜、联想全是页面世界的 `fetch`，所以除了搜索，别的看起来
全都正常。

**改法**（`selfTopbar.ts`）：

1. `localStore()` 统一取 `chrome.storage.local`，取值本身包 try；`readHistory` 的 `get`
   也包一层（拿不到就当没有历史）。`writeHistory` 的 `set` 失败只吞掉那一笔记录，
   并用 `logger.error` 提示一次（`error` 常开）：
   「搜索历史写入失败（扩展上下文可能已失效，刷新页面可恢复）」。
2. `go()` 里 `pushHistory` 包 try，`window.open` 也包 try —— **这个函数不许抛错**。
   弹窗被拦时的兜底从「直接赋 `location.href`」改成：同址就 `location.reload()`，
   否则本页跳转（同址赋 href 是空操作，等于没反应）。
3. 表单 submit 再兜一层：`go()` 真出了意料之外的错就 `form.submit()`，交回浏览器原生
   GET（`action` 本来就是搜索页）—— 代价是本页跳转，但一定搜得出来。
4. 回车选中行时**先确认这一行真的有关键词**再 `preventDefault`。原来只判 `if (row)`：
   选中行过期（列表重画过）时会「拦了回车却不跳」，同样表现为没反应。

**验证**（探针 chromium + `--load-extension`，新脚本 `Temp/bili-probe/search-idle.cjs`）：
用 SW 里的 `chrome.runtime.reload()` 精确模拟「页面开着、扩展被重载」——

- 旧产物：重载后搜索 `NO-REACTION`，页面报 `Error: Extension context invalidated.`（复现）；
- 新产物：重载后照常 `NEW-TAB .../all?keyword=重载之后`，控制台只有那一条历史写入失败的提示。

`DEV_VERSION` → `1.2.4 v010`。

## v011 修：扩展重载后页面里还有一批 `Uncaught: Extension context invalidated`

**现象**（用户截图）：`chrome://extensions` 的错误页里一条
`Uncaught Error: Extension context invalidated.`，上下文 `www.bilibili.com`。

**原因**：v010 只兜住了**搜索**这一条路径（`chrome.storage.local`）。同一个失效上下文里
还有一批 `chrome.*` 调用是裸的，任何一次用户操作都会再抛一条：

| 位置 | 调用 | 触发时机 |
| --- | --- | --- |
| `config.ts` persist | `storage.sync.set` | 点任意开关 |
| `paramStore.ts` persist | `storage.sync.set` | 拖任意滑块 |
| `panelHotkeyConfig` / `quickKeysConfig` / `quickWheelConfig` 的 `write()` | `storage.sync.set` | 改按键 / 拖槽位 |

| `settingsPanel` / `topbarOptimize` | `runtime.getURL` | 开设置面板 / 奶睿 logo |
| `quickWheel` `openInNewTab` | `runtime.sendMessage` | 点轮盘项（这条本来就有 try） |

**改法**：把「碰 chrome」这件事收进 `storage.ts`（本来就是存储唯一入口），新增四个出口，

- `chromeApi()`：判据是 `chrome.runtime.id`（断连后变 `undefined`，**读属性不抛**，

- `syncSet(patch)` / `syncGetAll(cb)` / `chromeGetURL(path)`：各自 try，失败返回 false / 空串。

- `startStorageSync` 失败时**不能**退化成 localStorage 快照 —— 那份是空的，会把所有开关按
  默认值重新应用一遍，用户看到的是「设置被重置」。只有「压根没有 chrome」（本地注入调试）
  才走回落，上下文失效就直接保持现状。
- 写入失败退回 localStorage 保持原样（`persist()` 本来就这么写），只是不再抛。

页面不刷新）：重载后开设置面板 / 点开关 / 搜索三步 —— 旧产物抛 1 条 `Uncaught`，

## v012 「播放节点优选」的加速链路收口（全在 `guard.js` §7）

用户报「这一版视频打开速度不佳」。实测（真实 Chrome，登录态，`BV19pW26jEhZ`）：
冷启动 TTFB 580ms / DCL 830ms，106 个分片里视频全在 `cn-hljheb-ct-01-02`、
音频在 `-01`（按设计不改写），`applied.managed = false`、`scores = null` ——
**这一页既没测速也没换节点**，也就是说「打开慢」不是这一页在抢带宽，而是**优选本身已经
停摆**了。顺着查到五处，一次改完。

### 1. 手动指定的节点无效时，逐分片改写会永久停摆

用户的 `bili-elite-cdn-force` 是 `x5zy00k.edge.mountaintoys.cn:4483` —— 一个 **P2P 主机**
（名字里的哈希是按文件生成的，换视频就变）。`preferredHostFor()` 里原来写的是：

```js
if (force) {
  if (force !== cur && t.urls[force] && isCdnHost(force)) return force
  return ''          // ← 无效 force 直接收工
}
```

而 `applyPick()`（页面加载时那一次）在 force 找不到时会**继续走 auto 分支**。两处语义不一致的
后果：加载时可能换一次，之后**每个分片都返回空**，于是「节点优选开着、面板显示生效中，
实际一个字节都没换」。这也是「手动选过节点之后感觉没效果」的根因。

改成 force 只当**优先项**：命中就用，无效就落到自动逻辑（`isAvcStrategy()` 之后那一套）。
单测覆盖四种情形：无效 P2P → 自动挑；有效 → 用它；等于当前 → 不动；无 force → 按 40% 门槛。

### 2. 每个视频分片都同步写一次 localStorage

`noteMedia()` 挂在每个 `/upgcxcode/` 请求上，里面 `saveRetestRef(u)` 无条件 `setItem`
一条 793 字节的 JSON。实测 20 秒 10 个分片 = 10 次写，5 分钟的视频 200+ 次 ——
纯写放大，还顺带把 `storage` 事件广播给所有同源标签页。

同一视频的**全部分片 URL 完全一样**（B 站靠 Range 头切段），所以按「地址没变 + 60 秒内」
跳过；换视频 / 换清晰度时地址一变立刻写，重测拿到的仍是最新签名。实测 100 次同址调用只写 1 次。

### 3. 长期表没有保质期，表齐了就永不重测

`hasUnknownHost()` 只要表里有这个主机就返回 false，于是 24 个节点的读数可以冻结几周：
节点变慢了没人纠正，用户感受就是「用久了不如刚装时快」。而 `bumpRank()` 是覆盖式写入，
一次网络抖动就能把好节点永久写成慢的。

新增 `bili-elite-cdn-rank-ts`（`{ host: 时间戳 }`），**`RANK` 的格式一个字没改**
（面板 / `cdnBoost.ts` 照旧按 `{ host: 毫秒 }` 读）。超过 7 天的读数视为「没测过」，
下次打开播放页顺手补一轮（只测当前这条流的 2~3 个节点）。老版本没写过这个键 ——
读出来是空的，整张表算过期，正好完成一次平滑迁移，不需要迁移脚本。
`retestAll()` 只给「这一轮真测通」的节点打时间戳，没测到的保留原时刻。
「节点管理」删除节点时 `cdnBoost.ts` 的 `removeCdnRankHosts()` 同步清时间戳。

### 4. 缓冲不达标时不再「10 秒后强行测」

`scheduleProbe()` 原来是 `waited < 10000`：缓冲一直起不来（**最缺带宽**的时刻）就 10 秒一到
无条件 `probe()`，正好和「不跟播放器抢」的初衷相反。改成一直等到 `PROBE_WAIT_MAX = 30s`，
还不达标就**这一轮不测**（下次打开播放页、或表过期时再来）。

### 5. 高码率流测两段取较小值

128KB 的耗时分不清「低延迟窄带」和「高带宽」：地方节点下 128KB 只要两百毫秒，读数看着最快，
真播 16Mbps 却喂不住。`bw ≥ 4Mbps`（1080P60 / 2K / 4K）时对同一节点**再测一段、取较小值**
—— 偶发抖动只会让读数变大，取 min 才接近真实能力。代价是每个节点多 128KB，
只在自动测速（2~3 节点）里做；重测仍走单段多轮平均，不放大流量。
`sampleOffset()` 增加 `need` 参数，保证两段都落在文件范围内（否则第二段被服务端截短，
耗时偏小、读出一个假的「很快」）。

### 6. 顺带修：成功读数不再和失败撞在 0 上

`fetchRange()` 原来成功也直接返回 `Date.now() - started`，同一毫秒下完就是 `0`，
而所有调用方都用 `if (ms)` 判成功 —— 本地 / 极近节点会被判成「测不通」，
第 5 条那个「再测一段」的分支也会被 `!a` 直接跳掉。改成成功读数 `Math.max(1, 耗时)`，
`0` 专门留给失败。单测里就是这么撞出来的（高码率本该 6 次请求，实际只发了 4 次）。

### 验收

**25/25 通过**，覆盖：force 四种情形、100 次同址只写 1 次、TTL 三种状态、500 次取样不越界、
`rank-ts` 同时写入、缓冲不足 30s 后不调 `probe`、暂停时立刻测、高码率 6 次请求 / 普通码率 4 次。

## v013 搜索历史：不再顶掉旧词，超过 4 行给「展开」按钮

用户报：搜索栏弹窗里的历史词一多，最早的那些就被挤没了。

**原因**：`selfTopbar.ts` 的 `HISTORY_MAX = 10`，`writeHistory()` 每次 `slice(0, 10)`。
搜过十一次之后，第一条就永久没了 —— 而面板本身（`selfTopbar.css` §3.2）其实早就能滚，
只是被这个 10 条卡死在「永远不超过 4 行」。

**改法**（三处）：

1. **`HISTORY_MAX` 10 → 100**。100 条按每条 30 字算也就 3KB 左右，
   `chrome.storage.local` 的 5MB 配额远远够；真到 101 条才会顶掉最早的。
2. **超过 4 行时出现「展开」按钮**（`.tb-sp-fold`，在历史区底部、贴一条极淡的分隔线）。
   点击把历史区撑到面板能给的最大高度，按钮文案与箭头一起翻成「收起」。
   收起态不跨次保留 —— `closePanel()` 里统一 `setHistoryExpanded(false)`，
   下次点开搜索框还是 4 行的默认样子。
3. **展开高度 = `max(172px, 66vh - 80px)`**。80 = 上下 padding(13+16) + 标题行 24 + 按钮 30
   + 给滚动条本身留的 8px（不留这 8px，30 条这种「差 3px」的内容会白冒一条滚动条）。
   外层的 `max(172px, …)` 是兜底：视口很矮时 66vh 算出来比 172 还小，展开不能反而变矮。
   撑满之后仍装不下就在历史区里自己滚（`overscroll-behavior: contain` 照旧，
   滚到底不会把滚动链甩给面板）。

**判据为什么不用 `histories.clientHeight`**：它在展开状态下已经变大，拿它比永远「不超出」，
按钮会在展开那一刻自己消失、再也收不回来。改用**列表自身的 `offsetHeight` + 12**（列表的
`margin-top`）—— 只受内容影响，收起 / 展开两种状态下是同一个值。历史区 `hidden` 时
（没有词 / 正在显示联想）`offsetHeight` 是 0，按钮一律不显示。

`HISTORY_COLLAPSED_H = 172` / `HISTORY_TOP_GAP = 12` 两个常量与 CSS 里的
`max-height: 172px` / `margin: 12px` 是同一组数字，**改一边要同步另一边**（注释里已标）。

夜间：`night.css` §3 补了按钮的文字色与分隔线（亮色的 `#f1f2f3` 在深底上会变成一道白光）。

## v014 修：动态悬浮窗打开时先闪一下空白，再把「正在加载」占位补上

**现象**（用户报）：点动态正文，悬浮窗出来了，但**先闪一下空白**（白窗 / 底下的动态流透出来），
过一会儿「正在打开动态…」的占位才出现，然后才是正式界面；关闭也没有衔接，啪地一下没了。

**根因一：`visibility` 是继承属性，占位被 `.dyn-stage` 的 `hidden` 带住了。**
`.dyn-stage` 关闭态是 `visibility: hidden`（靠它收尾，避免退场动画被当场掐断），
`.dyn-loading` 自己没写 `visibility` → 继承到 `hidden`；而它身上挂着
`transition: … visibility 0s linear 180ms`，打开时 `.dyn-stage` 变 `visible`，占位还要**再等
180ms** 才跟着显形。实测采样（每帧读 computed style）：

```
t=21   stageOp=0    loadVis=hidden      ← 窗口开始淡入，占位还看不见
t=274  stageOp=0.003 loadVis=hidden     ← 一路都是白窗
t=360  stageOp=1    loadVis=visible     ← 占位这时才浮出来
```

改法：`.dyn-loading` 显式写 `opacity: 1; visibility: visible`，**延迟只放在 `.is-loaded`
那一侧**（收起时等淡出跑完再 hidden，重新打开时立刻可见）。同理 `.dyn-frame` 的淡入时长
160 → 260ms，让内容像「浮上来」而不是硬切。

**根因二：`is-open` 和 `frame.src` 在同一帧。**
iframe 插进文档会先加载一次 `about:blank`，它的 `load` 在 `open()` 之后才异步到达 —— 那次
load 被当成「详情页加载完了」，把占位提前收掉。同时 iframe 的首次绘制（白底 / B 站骨架）
和窗口淡入抢同一帧。

改法：

- `open()` 里**先让窗口 + 占位画出来，等入场动画跑完（200ms）再开始导航**。B 站详情页和
  动态流同站同进程，iframe 一导航就占住主线程 —— 实测同一帧设 src 时入场动画会被冻在
  半路，`opacity` 从 0 直接跳到 1（等于没有动画）；
- 新增 `frameReady()`：`about:blank` 不算、`lastDocHref` 相同的（重开时上一条文档晚到的
  load）不算、origin 不一致不算；`lastDocHref` 在释放 iframe 时清空，重开同一条动态不会被
  自己的判断挡掉；
- 新增 `waitFrameContent()`：`load` 只代表文档到了，B 站是 Vue 后渲染，那一刻 `.card`
  里常常还是空壳（高 0）。等 `.bili-dyn-item` 有高度再揭开，80ms × 15 ≈ 1.2s 上限，
  超时也揭开（登录 / 风控页永远等不到，不能让转圈一直转）。

**动画本身**：窗口从 96.5% 放大 + 淡入（220ms `cubic-bezier(.22,.61,.36,1)`），退场缩回
97%；遮罩 180ms；占位淡出 220ms / iframe 淡入 260ms 交叉。`prefers-reduced-motion` 下
全部取消过渡（原来只把转圈放慢）。

**顺带修掉宽度回摆**：窗口宽度原来会 1088 → 1244 → 1088 摆两趟 ——

- 图片分栏的兜底宽度从 1800 改成 1088（打开那一刻还没量到图，先按基础宽度出现），
  并给 `.dyn-stage` 的 `width` 加 240ms 过渡；
- `syncMediaWidth` **算一次就锁住**（`mediaWidthLocked`），用户换图 / 改浏览器窗口大小时
  才解锁。宽度一变 iframe 就 resize，再算一次又会得到另一个值；
- 只在**原图真的解码完**之后才量：`img.src` 没有 `@264w_264h` 后缀、且 `currentSrc`
  已经跟上 `src`。只判 src 的话，新图加载中 `naturalWidth` 还是缩略图那个方形 264x264，
  算出来的宽度是错的；
- 右栏宽是窗口的 36%（clamp 340~430），拿实测值算会「先到位再回摆」—— 改成按目标宽度
  迭代两步，一次落到位。

### 验收（探针 chromium 123 + `--load-extension`，`Temp/probe/probe2.mjs`）

每帧采样 `stage` 的 opacity / visibility / transform / 宽度、`.dyn-loading` 与 `.dyn-frame`
的 opacity / visibility，跑「打开 → 关闭 → 再打开另一条」：

| 时刻 | 观测 |
| --- | --- |
| t=31 | stageOp 0.003、**loadVis visible**（占位第一帧就在）|
| t=31→364 | opacity 0.003 → 0.987 → 1、scale 0.968 → 1（逐帧推进，不再跳变）|
| t≈550 | 入场跑完才开始导航（`about:blank` 的 load 被 `frameReady` 挡掉）|
| reveal | 正文有高度才 `is-loaded`，占位 1 → 0.5 → 0.1 → 0 与 iframe 0 → 0.35 → 0.8 → 1 交叉 |
| 关闭 | opacity 1 → 0.997 → 0.8 → 0.5 → 0.03 → 0，scale 1 → 0.965，220ms 后 visibility hidden |

## v015 修：揭开时窗口下半部透出重影 + 评论区加宽到 1.5 倍

### 1. 占位淡出、内容揭开的那 260ms 里，窗口下半部会「半透明显现」重影

**现象**（用户截图）：加载动画往正式界面过渡时，窗口上半部内容清晰，下半部却透出一层
模糊、半透明、像是重复了一遍的内容。

**原因**：`.dyn-frame` 原来有 `opacity: 0 → 1` 的 260ms 过渡。给 iframe 做 opacity 动画时，
Chrome 会把它提升成合成层、先按**低分辨率纹理**糊一帧再逐帧重绘 —— 大 iframe 的下半部分
（还没光栅化到的区域）就是那层模糊重影。

**改法**：

- **iframe 恒 `opacity: 1`，不做任何过渡**。视觉上改成「白幕揭开」：只让上面的
  `.dyn-loading`（实底白 + 转圈）淡出 260ms，iframe 一直在底下、从头到尾不透明。
  加载期间它被占位完全盖住，一个字节都露不出来。
- `.dyn-body` 补一条实底 `background: var(--dyn-canvas)` 兜底：万一 iframe 还没绘制
  （导航中），露出来的也是白，而不是 `.dyn-window` 那层 68% 半透明的 surface。
- `prefers-reduced-motion` 里 `.dyn-frame` 那条选择器一并去掉（已经没有过渡了）。

实测（把淡出临时放慢到 4s 后连拍）：整个窗口的白幕是**均匀**变薄的，左右两栏、上下
各部分透出程度一致，没有重影。另测 `.dyn-body` / `.dyn-frame` 的 rect 与窗口完全一致
（1262x782），不存在「iframe 没撑满、下半部露出半透明窗口底色」的情况。

### 2. 右侧评论区加宽到 1.5 倍

右栏原来 `clamp(340px, 36%, 430px)`，430 里读评论每条只剩三四个字就换行。

- `EMBED_CSS` 的 `grid-template-columns: minmax(0,1fr) clamp(510px, 54%, 645px)`；
- 纯文字分栏的窗口宽度 1240 → **1440**（正文 720 + 评论 645 + 留白），否则左栏正文会被挤窄；
- `syncMediaWidth` 的 `rightAt()` 同步成 `clamp(510, 54%, 645)`（和 CSS 是同一组数，
  **改一边要改另一边**），图片分栏的窗口宽度会自动跟着变宽（实测 1264，左栏图片 594）；
- `SPLIT_MIN_WIDTH` 900 → **1080**：右栏最窄 510，窗口 1080 时左栏还剩 570，
  再窄就该退回单栏了。

实测（探针 chromium，视口 1600×1000）：`rightW = 645`、窗口 1264、左栏图片 594，
评论一行能放下的字数约为原来的 1.5 倍；纯文字分栏窗口 1440、右栏 645。

## v016 动态页的视频也用悬浮窗打开（播放页去掉右栏推荐）

用户要的：动态里点视频卡，不再开新标签页，而是在同一个悬浮窗里打开**我们版本的播放页** ——
只有播放器 + 下面的 UP 主 / 简介 / 评论，不要右栏那串「接下来播放」。

### 1. 硬约束：视频页是**跨源**的

动态详情能做得那么细（注入样式、两栏、搬图片）是因为 `t.bilibili.com` 详情页和动态流同源，
父页面能读 `contentDocument`。播放页在 `www.bilibili.com`，跨源 —— 父页面**一个字节都改不了**。

所以排版只能由 iframe 里的自己来做：

- manifest 的内容脚本加 `all_frames: true`（`src/manifest.ts` + 产物 `extension/manifest.json`）；
- `index.ts` 顶部加两个守卫：`IS_TOP` / `IS_EMBED`。**B 站自己的 iframe**（广告 / 登录框 /
  播放器）里一个模块都不装，直接什么都不做；
- 嵌入标记走 URL 的 `blie_embed=1`（B 站忽略未知参数，比 `window.name` 可靠），
  `isEmbeddedVideoFrame()` 三条同时满足才算：非顶层 + `www.bilibili.com` + `/video/`；
- 嵌入帧里只跑 `injectDesignTokens` + `bootstrapConfig` + `startStorageSync` + `setupVideoBeta(true)`。

### 2. 视频页会「跳出」iframe，必须加 sandbox

实测：直接把 `www.bilibili.com/video/BV…` 塞进 iframe，**整个动态页会被导航到视频页** ——
B 站有反嵌入脚本（`top.location = 自己`）。响应头里没有 `X-Frame-Options`，是纯 JS 干的。

改法：iframe 加

```
sandbox="allow-scripts allow-same-origin allow-forms allow-popups
         allow-popups-to-escape-sandbox allow-presentation allow-downloads"
```

**关键是不要 `allow-top-navigation`**：浏览器会静默拦掉那次跳转，页面老实留在悬浮窗里。
`allow-same-origin` 必须留 —— 没有它 iframe 变成 opaque origin，登录态全丢，视频页会退化成
未登录；`allow-scripts` 是播放器本身。实测加了之后顶层地址一直是 `t.bilibili.com`，
视频页完整渲染（截图核对过标题 / UP 主 / 播放器 / 评论）。

### 3. videoBeta 的「嵌入模式」

`isEmbedMode()`（`blie_embed` 在 URL 上）→ `start()` 挂 `bili-elite-vb-embed`：

- `measure()`：`rail = 0`、`left = 视口宽 − 2×gutter`，左栏吃满；`--bili-vb-top-gap` 给 EDGE
  （没有 B 站顶栏了，顶部那道白要自己出）；
- `leftPinTop()`：顶栏高按 0 算（`headerH = EDGE`），左栏钉到窗口顶部；

## v017 视频悬浮做成下属开关 + 窗口大小一步到位 + 悬浮窗里的图全屏查看

### 1. 「动态里的视频也悬浮打开」单独控制

`features.ts` 新增 `dynamicFloatVideo`（`实验室`，默认开，`under: 'dynamicFloatBeta'`）——
挂在「动态悬浮打开beta」那张卡里，父开关关掉时整行变灰（`settingsPanel` 现成的 `under` 机制）。
`onClick` 的视频分支先判它：关掉时**直接 `return`，一个 `preventDefault` 都不做**，视频卡回到
B 站原本的「新标签页打开播放页」。

### 2. 窗口大小打开即最终值

**现象**：有的动态悬浮窗先按 1088 出现，等内容出来再变宽（用户说的「大小变换过程」）。

**原因**：图片分栏的窗口宽度要按「首图宽高比 × 舞台高度」算，而那个比例只有 iframe 里的
详情页加载完才知道 —— 打开时只能先用 1088 兜底。

**改法**：

- 把宽度公式抽成 `mediaWidthFor(ratio, stageH, stageW)`，`syncMediaWidth` 和 `open` 共用；
- `open()` 里用**动态流卡片里那张已经加载好的图**预判，并 `mediaWidthLocked = true` 锁住，
  之后不再重算；
- 卡片里的图分两种：单图是 `@420w_560h` 这种**按原比例**缩的，`naturalWidth` 可信；
  多图全是 `@264w_264h` 方形裁切，比例没用 → 按 3:4 竖图估一个（算出来正好是实测的 1264）；
- 纯文字动态本来就是 text 档、宽度由 CSS 定死，一直是一步到位。

实测宽度序列（每帧读 stage 的 rect）：布局宽度**从第一帧就是 1264**，采样里看到的
1050 → 1258 → 1264 全是入场 `scale(0.965 → 1)` 造成的 rect 变化，不是布局在变。

### 3. 悬浮窗里点图 → 父页面全屏看图器

**为什么不能直接用 B 站的**：动态悬浮窗里的图片在 iframe 里，B 站的 PhotoSwipe 只能铺满
iframe（也就是悬浮窗那一块），不是「全屏」；而且 `imageViewer` / `imageGlass` 只在顶层
页面装，iframe 里本来就没有。

**改法**（`dynamicOverlay.ts` + `dynamicOverlay.css`）：在 shadow 里加一层 `.dyn-viewer`，
由父页面自己画：

- **背景**：`backdrop-filter: blur(N) saturate(180%) brightness(1.02)` + 亮度遮罩色，
  参数取自 `getGlassParams()`（「高级材质 → 材质（评论区图片背景）」那组滑块），
  `imageGlass` 关掉时退回 `rgba(0,0,0,.86)`；
- **打开动画**：从被点击那张图在**屏幕**上的位置（iframe 内 rect + iframe 偏移）FLIP 到
  「铺满视口留 48px」，`IMAGE_DUR_OPEN` / `IMAGE_EASE` 与 `imageViewer` 同一套；
- **关闭**：反向 FLIP 回原图位置，动画结束再清 `fill`（否则下次打开会停在缩回那一帧）；
- **多图**：相册里所有图都进列表（`@264w_264h` 后缀去掉换原图），左右箭头 / `←` `→` 切换、
  底部 `2 / 5` 计数；单图时箭头和计数都不显示；
- **触发**：`decorateFrame` 里给 iframe 文档挂捕获阶段 `click`，命中
  `.bili-album__preview__picture img` / `.bili-album__watch__content img` 就
  `preventDefault` + `stopPropagation`（B 站那套「先内联展开、再点查看大图」直接跳过）；
  工具栏按钮（`.bili-album__watch__control`）不拦；
- **Esc**：看图器开着时先收看图器，再按一次才关悬浮窗；`←` `→` 只在看图器开着时接管；
- 关悬浮窗时直接收掉看图器（不播缩回动画 —— 窗口本身也在淡出，两条动画叠在一起反而乱）。

**坑**：`.dyn-viewer` 本身**不能**做 `opacity` 过渡 —— 祖先透明度 < 1 会成为背景根，
`backdrop-filter` 就采样不到后面的内容了（整层退化成一块纯色）。透明度只给

## v020 补：看图器的关闭动效 + 评论区图片也能全屏

### 1. 关闭动效被 `visibility` 掐掉了

**现象**（用户报）：点图有放大动画，关掉的时候是「啪」一下没了。

**原因**：`closeViewer()` 里第一件事就是 `classList.remove('is-open')`，而 `.dyn-viewer` 的基础规则是
`visibility: hidden` —— 摘类那一刻当场隐藏，图片缩回（290ms）和背景淡出（200ms）两条动画
一帧都没播出来。

那条用 `transition: visibility 0s` 覆盖 —— 打开时立刻显示，关闭时等动画跑完（320ms）才隐藏。
和 `.dyn-stage` 的写法完全一样（同一个坑）。

### 2. 评论区图片走同一个看图器

**改法**：

- 图片判定改成走 **`event.composedPath()`**（唯一能穿进 shadow 的通道），取路径里第一个
  `IMG`；
- 新增 `isZoomableImage()` 做过滤：排除头像（`.bili-avatar` / `.b-avatar` / `.bili-dyn-avatar`）、
  表情（`.emoji` / `.emoticon`）、**视频 / 直播 / 番剧 / 专栏卡的封面**（那几类点下去应该是
  「进内容」而不是「看封面大图」），以及小于 80×80 的小图（评论图至少 100 宽，头像 48）；
- `ViewerItem` 增加 `thumb`（页面上那张图的原始地址）：评论图偶尔只有 `@96w_96h` 这种缩略图，

## v021 修：看图器换图时比例错 / 闪一下上一张

**现象**（用户报）：一张图**第一次**打开时，可能先按上一张的比例摆出来，还闪一下上一张图。
视频评论区点图没有这个问题。

**根因**：`showViewer` 原来是「设完 `src` 立刻读 `naturalWidth` 决定尺寸」：

```js
v.img.src = item.src
if (v.img.naturalWidth && v.img.naturalHeight) { place(); return }   // ← 读到的是**上一张**
```

`<img>` 改 `src` 之后，浏览器会**继续显示旧图**，`naturalWidth` 也还是旧图的尺寸，直到新图
解码完成 —— 于是按旧比例算出 `contain` 位置，图片摆好之后新图才刷上来，观感就是
「比例错 + 闪一下上一张」。视频评论区的 PhotoSwipe 没这个问题，因为它从头到尾挂的是
占位图，从来不读旧图尺寸。

**改法**：

1. 换图前**先彻底清掉**：`opacity: 0` + `removeAttribute('src')` + `removeAttribute('srcset')`，
   旧图当帧消失，浏览器没有旧帧可留；
2. 用 `onload` / `onerror` 包成 Promise（缓存命中时 `complete && naturalWidth` 直接 resolve，
   不白等一次事件），**加载完再 `place()`**；
3. `place()` 里尺寸仍然是 0 就直接 return（宁可多等一帧，也别拿 0 / 旧值去算）；
4. 新增 `viewerToken`：连续切图 / 关掉看图器之后，旧那次加载的回调不许再动 DOM；
5. 原图取不到（评论图偶尔只有 `@96w_96h`）时退回 `item.thumb`，同样等它加载完再摆。

### 验收（`Temp/probe/probe10.mjs`）

打开 4 图动态的看图器，连点两次「下一张」，**每帧**对比 `naturalWidth` 比例与
`getBoundingClientRect` 比例（容差 3%）：

```
next-1  [0x0 / 475x808 / op 0]  →  [800x1297 / 498x808 / op 1]
next-2  [0x0 / 498x808 / op 0]  →  [800x1498 / 432x808 / op 1]
```

- 切换瞬间 `src` 已清空（`0x0`）+ `opacity: 0`，旧图不可见；
- 显示出来的每一帧比例都一致（800/1297 = 0.617 ↔ 498/808 = 0.616；
  800/1498 = 0.534 ↔ 432/808 = 0.535）；
- **可见帧里的不一致数 = 0**（加载中那几十毫秒 `opacity` 还是 0，尺寸沿用旧值但图片不可见，
  不计入）、页面异常 0。

## v023 动态视频悬浮窗：再放宽 + 直播不再进悬浮窗

### 1. 宽度上限 1800 → 2200，信息区预留 260 → 140

width: min(calc(100vw - 64px), clamp(760px, calc((88dvh - 140px) * 16 / 9), 2200px));

## v024 动态视频悬浮窗：修开头的爆音 + 宽度足够时排成「左视频 / 右信息」两栏

### 1. 悬浮窗视频开头那一声「轰」没了

**现象**（用户报）：动态里的视频在悬浮窗里打开时，先炸一下非常大的声音，随后才回到正常音量。

**原因**：悬浮窗里的播放页是被嵌进 `t.bilibili.com` 的第三方 iframe，Chrome 对第三方
iframe 的 localStorage 做了分区 —— 播放器读不到用户平时在 `www.bilibili.com` 存的音量，
`<video>` 先按默认音量（100%）开始出声，等播放器自己的初始化跑完才把音量写回来，
中间这几十到几百毫秒就是那声「轰」。

**改法**（`videoBeta.ts` 的 `guardEmbedAudio()`，只装在嵌入模式）：`<video>` 元素一出现
就先静音（只动 `muted`，不碰 `volume` —— 改 volume 会被播放器当成用户设置存下来），
盯 `volumechange` 等播放器把音量写进来、稳定 160ms 后解除静音；播放器一直没写
（用户本来就是 100%）就 1 秒后兜底解除。切分 P 换了 `<video>` 节点时观察器会再护一次。
全程不写播放器的音量设置，B 站自己的音量逻辑一个字节都不碰。

### 2. 宽度足够时，视频页排成「左播放器 / 右标题 + UP + 评论」两栏

v023 只是把窗口放宽、信息区留在播放器下面往下滚；这一版在宽度真正够的时候把信息区
（标题 / 播放数据 / UP 主 / 操作栏 / 简介 / 评论）整个搬到播放器右侧，
两边并排 —— 和图片动态「图片左 / 文字评论右」的分栏一个思路。

窗口宽度由 `dynamicOverlay.ts` 的 `videoWidthFor()` 按「左播放器（按窗口高反推 16:9）+
信息栏（clamp(440, 28%, 620)）+ 留白间距」算好写进 `--dyn-video-w`；算出来连
「播放器下限 600 + 信息栏」都放不下时退回 v023 的单栏公式，不为两栏白变宽。

iframe 里 `videoBeta.ts` 的 `measure()` 用同一组参数判单栏 / 两栏（带 40px 滞回，
滚动条出现消失不会来回切）：够宽就给 `<html>` 挂 `bili-elite-vb-embed-split`，
`videoBeta.css` §14 接管：

- `#playerWrap` 改 `position: fixed` 钉在 iframe 左上角 —— 页面滚信息栏时播放器不动；
- `.left-container` 仍在原来的流里，`padding-left` 撑成「播放器宽 + 间距」，
  标题 / 操作栏 / 简介 / 评论整体右移成为右栏；

## v025 动态视频悬浮窗：爆音换成「音量锚定」+ 禁用滚动小窗

### 1. 开头那一声「轰」还是没消掉

**现象**（用户复测）：v024 的护栏上过之后，悬浮窗里的视频**开头仍然会大声一下**。

**更正 v024 的根因判断**：悬浮窗 iframe（`www.bilibili.com`）嵌在 `t.bilibili.com` 里是
**同站**的，localStorage 并没有被分区 —— 播放器读得到用户的保存音量。真正的坑在时序：
打开悬浮窗是用户刚点过的一次点击，手势激活会传进 iframe，自动播放可能抢在播放器把
保存音量写进 `<video>` 之前出声；播放器启动早期还可能先写一个内置默认值。
而 v024 的两条解除路径都可能踩空：见到一个 <1.0 的写入就解除（那可能只是内置默认值），
或 1 秒兜底（可能赶在真正的恢复之前）—— 两条都会在错误音量上解除静音。

**改法**（`videoBeta.ts` → `guardEmbedAudio()`，只装在嵌入模式）：

- 我们自己从 `bilibili_player_settings.video_status.volume` 读保存音量，`<video>` 一出现
  就直接写进 `video.volume`（MutationObserver 回调是插入任务后的 microtask，必然抢在
  播放管线出声之前）；
- 之后谁把音量改走（播放器 boot 写 1.0 / 内置默认值 / 换 P 重建）就写回来，直到播放器
  自己写出与保存值一致的音量（说明它的恢复流程跑完了），1.5s 兜底收工；
- `volumechange` 之外加一条 100ms 轮询：兜住「元素插入前音量就被写好」（没有事件可听）；
- 全程**只写 `volume`、不碰 `muted`** —— 写的是用户自己的保存值（播放器就算当设置存回去
  也是原值 no-op），也不会替用户 / 播放器解除静音；
- 用户音量本来就是 100% 时一个字节都不动（没有「先大声后回落」可言）；
- 读不到保存值（首次访问 / 存储异常）才退回 v024 的静音护栏（1.2s 兜底解除）。

### 2. 悬浮窗里往下滚时视频变成右下角小窗

**现象**（用户截图）：悬浮窗里往下滚评论，左侧视频会变成右下角的小窗，左上角留一块黑洞。

**原因**：B 站的小窗逻辑按「滚过播放器」判，滚下去就把 `.bpx-player-container` 切成
`data-screen="mini"`：容器变 `position: fixed` 钉到右下角 320×180（内联 right/bottom +
样式表给尺寸），`#playerWrap` 原地留洞。全屏模式下视频确实会被滚下去，小窗是合理的；
但悬浮窗里播放器是钉住的（单栏 sticky / 两栏 fixed），视频根本没滑走，小窗就纯属多余。

**改法**（`videoBeta.css` 嵌入模式新增一节，DOM 不动）：`data-screen="mini"` 时按 normal 态
还原 —— 容器钉回原位（position / inset / 尺寸 / z-index 全部照 normal 态的 computed 值，
`!important` 压过内联 right/bottom），小窗专属控件（`.bpx-player-mini-warp` 关闭钮 /
进度条 / 拖拽把手）藏掉，被小窗态连带藏掉的正牌 UI（控制条 / 弹幕 / 顶栏 / 发送栏 /
结束面板等 16 个元素）逐个还给 normal 态的 display（2026-11-22 在真实播放页对两种状态
逐个量出来对比的）。滚回顶部 B 站自己切回 normal、清掉内联样式，本节随之失效；
进全屏 / 网页全屏时 `data-screen` 是 web / full，本节本来就不匹配。
