# CHANGELOG 怎么写

> 一个正式版本一个文件：`CHANGELOG/<版本>.md`。
> 这个目录只回答一件事 —— **这一版给了用户什么**。至于「当初为什么这么改、踩了哪些坑、量到多少」，
> 那是开发记录，只在开发期间存在，打包时整段归档到 `archive/`。

## 目录

```
CHANGELOG/
  README.md          本文件：规则
  <版本>.md          一个正式版本一份，正文 = 精简官方描述（开发中的版本额外带「开发记录」）
  archive/<版本>.md  打包那一刻被剥出来的开发记录原文，只读存档
```

## 一个版本文件的两种描述

| | A · 精简官方描述 | B · 开发记录 |
| --- | --- | --- |
| 谁看 | 用户（等价于设置面板「新版本改动」页） | 未来的自己 / 下一个 AI |
| 写什么 | 只写能体验到的变化 | 现象、根因、改法、量测、为什么否掉别的方案 |
| 长度 | 一节一条，一条一到两句 | 不限 |
| 存在多久 | 永久 | 只在开发期间；打包后进 `archive/` |
| 谁生成 | 从 `whatsNew.ts` 原样落盘 | 每改一次代码追加一节 |

## 生命周期

1. **开一版**：新建 `CHANGELOG/<版本>.md`，只写 A（骨架 + 一句话概览）。
2. **开发中**：每改一次代码，在 B 段追加 `## vNNN <一句话>`（`vNNN` 与 `settingsPanel.ts` 的 `DEV_VERSION` 同一个序号）。
   同时把用户能感知的变化写进 `src/contentScripts/modules/whatsNew.ts`。
3. **打包**（用户说「打包 / 出 zip / 发版」之后）：
   - 把 `whatsNew.ts` 的 `WHATS_NEW_INTRO` + `WHATS_NEW_SECTIONS` 抄进 A 段（**不另写一遍**，两边必须一致）；
   - 把 B 段整段剪到 `archive/<版本>.md`；
   - `<版本>.md` 只剩 A。
4. **开下一版**：新建下一个 `<版本>.md`，`DEV_VERSION` 回到 `v001`。

> 也就是说：**开发中的版本同时有 A 和 B；打包之后只剩 A。** 谁都不许把 B 留在主目录里。

## A 段的写法

就是 `whatsNew.ts` 的规矩，不重复发明：

1. 只写用户能体验到的（打开快了多少、哪里对齐了、点了之后什么反应），不写实现、不写毫秒级数字；
2. 只写**最终形态**：这一版里反复挪位置 / 反复改行为的东西只写一次；
3. **本版本新功能自己引入的 bug，修好了也不写**；
4. 用发布说明的书面语，一条一到两句，不写操作教程；
5. 本版本里被删掉 / 撤销 / 合并掉的东西一律不写。

分段固定用「新增 → 优化 → 修复」，空的节不写。

## B 段的写法

- 一节一个 `vNNN`，标题写**用户视角的现象**（「悬浮窗打开视频时开头被跳过一小段」），不写文件名；
- 正文按「现象 → 根因 → 改法 → 为什么不用另一种」写；量测数据、探针路径、复现次数都留在这里；
- 反复试错的中间版本也要留着（`v001 试过 → v002 撤掉`），这是 B 段最有价值的部分；
- 末节写「发版信息」：四处版本号、`DEV_VERSION`、`WHATS_NEW_VERSION`。

## 硬规则

- 主目录的 `<版本>.md` 里**不许**出现 `## vNNN` 这类开发小节 —— 出现就说明该归档了。
- `archive/` 只进不出：不修改、不删除、不再往里加内容。
- A 段与 `whatsNew.ts` 不一致时，以 `whatsNew.ts` 为准，回来改 A 段。
- 版本号四处一起改：`package.json`、`settingsPanel.ts` 的 `DEV_VERSION`、本目录的 `<版本>.md`、`blie-build/package.json`。
- 商店更新说明在 `RELEASE/`，那是另一件事（面向商店后台），不要和这里混。
