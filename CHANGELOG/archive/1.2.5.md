# 1.2.5

> 本次更新修复了动态悬浮窗播放视频时开头内容被跳过的问题，并统一了设置面板与顶栏浮层的点击动效。

## 优化

- 设置面板与顶栏悬停浮层里的按钮统一为 Material 涟漪：波纹从实际点击位置扩散，按住时保持、松手后完整淡出。
- 顶栏的动态、历史、收藏浮层改用与设置面板一致的颜色、胶囊圆角与选中态。
- 搜索页的筛选按钮（排序 / 更多筛选 / 直播筛选）改用与设置面板一致的胶囊圆角、配色、选中态与点击涟漪。
- 搜索页顶部的分类标签（综合 / 视频 / 番剧 …）改为文字标签页样式：悬停加深、选中变蓝，底部指示条随切换平滑滑动，并带点击涟漪。
- 设置面板的开关控件缩小一档，与旁边的胶囊按钮比例更协调。

## 修复

- 修复动态悬浮窗打开视频时，加载转圈期间视频已在后台起播，导致揭开画面后开头一小段被跳过的问题；现在视频自悬浮窗揭开的瞬间从片头开始播放。

## v001 修：悬浮窗打开视频时开头被跳过一小段

**现象**（用户报）：动态页里点视频卡，悬浮窗揭开时视频已经播过一小段了 —— 不是从
片头开始，画面和声音都过去了一两秒。

**根因：揭开等 `load`，起播不等。** 悬浮窗里的视频页是跨源 iframe（`www.bilibili.com`
嵌在 `t.bilibili.com` 里），父页面读不到它的文档，只能等 iframe 的 `load` 事件揭开
（`waitFrameContent` 的 crossNav 分支：`load` + 160ms）。但 B 站播放器的自动播放不赶
`load` —— 播放器 boot 完拿到 playurl 就开始播了，通常比整个页面的 `load` 早一截
（页面还有一堆图片 / 字体要等）。转圈的那一两秒里，视频在占位层底下已经出声走画面；
揭开时开头自然已经过去一小段。1.2.4 v025 的「音量锚定」让这段泄漏出来的是用户保存的
音量（不再炸响），但时间轴上的白过依然存在。

**改法：起播闸门 + 揭幕消息。**

- `videoBeta.ts` 新增 `holdEmbedAutoplay()`（只装在嵌入模式，`start()` 里与
  `guardEmbedAudio` 并排）：document_start 就在 `document` 上挂捕获阶段的 `play`
  监听 —— `play` 不冒泡，但捕获阶段会从 document 一路下来，内容脚本又比页面脚本早，
  播放器的第一次 `play()` 一定拦得到。命中主播放器（`#playerWrap, #bilibili-player,
  .bpx-player-container`，与音量护栏同一份判据）就 `pause()` 并记进 `heldVideos`
  （WeakSet，换 P 重建的节点也认）；推荐卡悬停预览之类的视频不碰。
- `releaseEmbedHold()` 放行：摘掉两个监听和兜底定时器，把 `heldVideos` 里的视频
  `play()` 回去。揭幕离用户那次点击通常不到 5s，手势激活大概率还在，带声放行没问题；
  真被自动播放策略拦下就保持暂停（播放器的大播放键还在，用户点一下就能放），
  `play().catch(() => {})` 不让 rejection 落进错误页。
- 播放器的 UI / 弹幕引擎本来就靠 video 元素自己的 `play` / `pause` 事件驱动，
  我们只是「play 里补一个 pause、放行时补一个 play」，不碰播放器内部状态；扣住期间
  整个 iframe 被占位的转圈盖着，暂停态的 UI 谁也看不见。
- `dynamicOverlay.ts` 的 `finishLoad()` 在挂 `is-loaded` **之前**发揭幕消息
  （`notifyFrameReveal()`，`postMessage({ type: EMBED_REVEAL_MSG })`）—— 先放行再揭开，
  视频正好在转圈还盖着的时候起播，用户看到的就是「揭开即片头」。只发 `crossNav`
  （视频模式）；消息发三发（0 / 400 / 1200ms，`scheduleFrameReveal()`），第一发理论上
  必中（内容脚本 document_start 就挂好了监听），后两发兜「消息落在导航提交边缘被吞」
  的意外；iframe 侧按类型幂等，收多发没有副作用。`close()` / 下一轮 `open()` /
  模块卸载时收掉重试定时器（`clearRevealTimers()`）。
- 兜底：iframe 侧 30s 后无条件放行（`holdFallbackTimer`）—— 父页面自己的 `loadTimer`
  20s 必发揭幕，这条只在父页面脚本整个没跑起来时生效，宁可揭开前白等几秒，
  也不能让视频永远扣在暂停上。`stop()` 里也 `releaseEmbedHold()`：中途关掉
  「播放页优化」不该把悬浮窗里的视频扣死在暂停。

**为什么不用「揭开后回卷到 0」**：那样转圈期间声音照放（用户已经听见一遍开头），
揭开瞬间音频再跳回 0，观感更差；暂停扣住则时间轴、音量、弹幕全都不用收拾。

**消息通道为什么是 postMessage**：跨源 iframe 里唯一的双向通道。发送方是父页面隔离
世界的 `frame.contentWindow.postMessage`，接收方 iframe 的内容脚本在 `window` 上收
（message 事件跨世界可见，仓库里「页面世界 ↔ 隔离世界」的老通道）；用
`event.source === window.parent` + 固定 `type` 双重校验，消息体只有一个字符串字段。

`EMBED_REVEAL_MSG` 从 `videoBeta.ts` 导出、`dynamicOverlay.ts` 导入 —— 两边共用一个值，
不会改漂。

`DEV_VERSION` → `1.2.5 v001`。

## v002 修：设置面板的涟漪显示不完整

**现象**（用户报）：Google 风格重绘之后按钮比例合适了，但按下时的涟漪「显示不完整」——
波纹像被切掉一块，或者刚点下去就没了。

**根因：动画挂在 `:active` 上。** 重绘时用 `::after` + `.xxx:active::after { animation: m3-ripple }`
做涟漪，这条路有两个死结：

1. 伪元素只能从元素中心 `translate(-50%,-50%)` 扩散 —— 点胶囊左端，波纹还是从正中炸开；
2. 更致命的是动画的宿主是 `:active` 这个**状态**：鼠标一松、选择器失配，伪元素立刻回到
   `scale(0)`，正在扩散的涟漪当场消失。0.6s 的动画通常只播了 100~200ms 就断了，
   这就是用户看到的「不完整」。**纯 CSS 无解** —— 无论怎么调时长 / 曲线 / `forwards`，
   松手那一刻一定被打断（`forwards` 只保证动画结束后停在终态，不保证动画不被取消）。

`panelButton.css` 里 ⚙ 按钮的 `::before` 涟漪也是同一个病：`width:100%; padding-bottom:100%`
尺寸够，但同样挂在 `:active` 上，抬手即断。

**改法：真正的 Material Ripple（JS 按坐标建节点）。**

- 新增 `ripple.ts`：`installRipple(shadow)` 在设置面板的 shadow root 上做事件委托，
  `pointerdown`（**捕获阶段**，避开面板自己的 `stopPropagation`）时按 `clientX/clientY`
  建一颗 `span.blie-ripple`，位置 / 直径通过 `--rp-x / --rp-y / --rp-size` 传给 CSS；
  直径取「按下点到最远角」的两倍，扩散到 `scale(1)` 时刚好铺满控件。
- 动画挂在**节点自己**身上（`blie-ripple-expand`，520ms，`cubic-bezier(.2,0,0,1)`），
  松手只是不再需要它，照常播完，`animationend` / `animationcancel` 后由 JS 摘掉。
- 面板整体有 `transform: scale(var(--bili-panel-scale))`，`getBoundingClientRect` 拿到的是
  **缩放后**的框，所以坐标要先乘 `offsetWidth / rect.width` 换算回元素像素；不换算的话
  130% 缩放下涟漪会整体偏左上，越靠右下偏得越多。
- 键盘 / 脚本触发（`click` 的 `detail === 0`）没有 `pointerdown`，补一颗从中心扩散的。
- `prefers-reduced-motion: reduce` 时整个不装：宁可没有涟漪，也不违背可访问性设置。
- 同一颗控件最多同时 3 颗，连点时把最早的顶掉，免得堆一层半透明圆。

**CSS 侧：**

- `.blie-ripple` 基础样式放在 `panelButton.css` —— 这份 CSS 首屏就注入，⚙ 按钮第一时间能用；
  `z-index: 0` 压在文字之下（面板控件的内容都挂了 `z-index: 1`，文字始终清晰）。
- 删掉 `panel.css` 里 7 处 `:active::after` 涟漪与 `@keyframes m3-ripple`
  （`.close` / `.nav-item` / `.text-btn` / `.confirm-btn` / `.key-cap` / `.we-chip-icon` / `.we-tile`）；
  `::before` 的状态层（hover 8% / press 12%）保留，涟漪只换实现、不换观感。
- `.btn` 的 `::before` 从「伪元素涟漪」改成 M3 状态层（白 8% / 16%）；奶睿键
  `color: transparent` 会让 `currentColor` 看不见，用 `--blie-ripple-color: #FFFFFF` 单独给白色。
- 涟漪容器补齐 `position: relative` / `overflow: hidden`：`.range-val`、`.cdn-row` 是新增；
  轮盘 chip 的涟漪画在 36px 的 `.we-chip-icon` 上 —— chip 本体 49px 装不下 51px 的内容，
  给它加 `overflow: hidden` 会切掉标签文字底部。

**为什么不用 CSS 变量 + `radial-gradient` 模拟**：坐标可以靠 `--x/--y` 传，但「松手不中断」
这一条纯 CSS 做不到 —— 没有 JS 就没有一个能脱离 `:active` 存活的动画宿主。

**实测**（探针 chromium 加载新产物，`bili-probe/ripple-check.cjs`、`ripple-detail.cjs`）：
- ⚙ 在 (10,12) 按下 → 涟漪 `--rp-x=10px / --rp-y=12px`，直径 93px（44px 圆铺满）；
  松手 150ms 后节点仍在、scale 继续推进，850ms 后自动清空；
- 分类胶囊左端按下 → `--rp-x=11.7px`（元素宽 176），直径 331px；松手后照常播完；
- 键盘触发 → 从中心（`--rp-x=88px` = 176/2）；
- 连点 5 次 → 同屏最多 3 颗，840ms 后清空；
- 无 `pageerror`。

`DEV_VERSION` → `1.2.5 v002`。

## v003 修：点完分类，胶囊被撑成大椭圆、文字变成「界面...」

**现象**（用户截图）：点一下左侧分类，那一项瞬间变成一个大椭圆（约 190×110），
浅蓝底 + 蓝描边，文字被压成「界面...」。

**根因：`.nav-item > *` 把涟漪节点的 `position: absolute` 覆盖了。**

`panel.css` 里有一批给「内容层」提层级的规则：

```css
.nav-item > * { position: relative; z-index: 1; }
.text-btn > * { ... }  /* 还有 .confirm-btn / .key-cap / .we-chip-icon / .we-tile */
```

涟漪节点 `span.blie-ripple` 是这些按钮的**直接子元素**，也被 `> *` 匹配到：
特异性 `.nav-item > *` (0,1,1) 压过 `.blie-ripple` (0,1,0)，`position` 从 `absolute`
变成 `relative` —— 于是那个「334px 的圆」不再是脱层节点，而是变成真实的 flex 子元素：

- 它的 `--rp-size`（按下点到最远角 ×2，nav-item 上约 180~334px）直接把 flex 主轴撑高；
- `.nav-item` 是 `.nav` 里的 flex item、`flex-shrink: 1`，被撑高后又被压回 110px 左右；
- 同一行里 `.nav-text` 被挤到只剩几十像素 → `text-overflow: ellipsis` 出「界面...」；
- `z-index: 1` 也一起被覆盖，涟漪从「压在文字下」变成盖住文字；
- `border-radius: 999px` + 110px 高 = 用户看到的大椭圆；蓝边是 `:focus-visible` 的 outline。

v002 的探针为什么没抓到：**点击后统一 sleep 900ms 才量**，那时涟漪已经 `animationend`
被摘掉了，尺寸早就恢复 40px。要看这个 bug 必须在按下后 30~100ms 内量。

**改法（两道）：**

1. 把 6 处 `> *` 改成 `> :not(.blie-ripple)` —— 从根上让内容层规则不再碰涟漪节点。
2. `.blie-ripple` 的选择器双写成 `.blie-ripple.blie-ripple`（(0,2,0)），以后谁再写
   `> *` 也压不住它 —— 这类「给所有子元素加层级」的规则在面板里很常见，光改一次不够保险。

**实测**（`bili-probe/ripple-fix.cjs`，按下后 30ms 量）：
- 分类胶囊：点击前 / 按下 30ms / 松手 120ms / 820ms 全部 `176×40`，`.nav-text` 恒为 67px；
  涟漪 `position: absolute`、`z-index: 0`，120ms 时扩散到 162px，820ms 自动清空；
- 「恢复默认」胶囊：`84×32` 全程不变，涟漪同样 `absolute`；
- 截图确认：点击中胶囊保持原高度、涟漪在内部扩散，文字清晰；点击后 8 项全是正常胶囊。

`DEV_VERSION` → `1.2.5 v003`。

## v004 涟漪按 M3 官方参数重做 + 开关收小 + 顶栏浮层统一

用户反馈四条：开关控件偏大；涟漪「还不是很完美」；「开始测速」「节点表」里的按钮没涟漪；
顶栏动态 / 历史 / 收藏浮层里的按钮还是老动效，颜色 / 圆角 / 动效要和设置面板统一。

### 1. 涟漪时序改成 Material Web 的原版

去读了 `@material/web` 的 `ripple/internal/_ripple.scss`，两个关键差异：

- **press 和 release 是两段独立的时序**：按下 **105ms linear** 淡入到 `pressed-opacity`(0.12)，
  松手 **375ms linear** 淡出到 0。v002/v003 是「520ms 一段动画、透明度自己从 0.16 掉到 0」——
  **按住不放时涟漪会自己消失**，松手和按住没有任何区别，这就是「不够完美」的根。
- **涟漪是径向渐变、不是硬边圆**：官方那行是
  `background: radial-gradient(closest-side, pressed-color max(calc(100% - 70px), 65%), transparent 100%)`，
  大按钮边缘有 70px 的柔和过渡。之前是 `border-radius: 50%` 的硬边圆，扩散时边缘一刀切。

改法：`ripple.ts` 里 press 阶段写内联 `transition: opacity 105ms linear` + `opacity: 0.12`，
松手改成 `375ms linear` → 0，`transitionend` 后摘节点；扩散仍用 `animation: scale(0)→(1)`，
时长按 M3 的 grow 取 450ms、曲线 `cubic-bezier(.2,0,0,1)`。CSS 里 `.blie-ripple` 的
`background` 换成上面那行渐变（原样照抄）。

顺带补了两个之前没有的行为：

- **轻点也要看得见**：按下不到 105ms 就松手时，等淡入走完再淡出（`MIN_VISIBLE_MS`），
  否则 opacity 才爬到 0.01 就开始掉，等于没有。
- **指针拖出去松手**：`pointerup` / `pointercancel` 挂在 `window` 上，不再是 root ——
  以前按住拖到面板外再松手，那颗涟漪会永远停在 0.12。

### 2. 浅色底按钮的涟漪换成深色

「开始测速」「查看」「开始」「管理」这些 `.text-btn` 实测**是有涟漪的**（`position:absolute`、
`--rp-size` 正常），但它们是「浅蓝底 #D3E3FD + 品牌蓝字」，`currentColor`(#1A73E8) 做涟漪
叠在同色系浅底上只有 12% 明度差 —— 在跑，但肉眼看不见，用户自然会以为没做。
按 M3 的 on-secondary-container / on-error-container 改成 `#041E49` / `#8C1D18`，
`.key-cap.is-listening`（深底白字）反过来用白色。`.range-val` 同样处理。

### 3. 开关收小

52×32 → **44×26**（thumb 14 → 选中 20），track 圆角 16 → 13，状态层光晕 8/12 → 6/9。
几何按 border-box 算：44×26 + 2px 描边 → 内容区 40×22，选中态 `left:2 + translateX(16) + 20 = 38`
正好留 2px。这样和旁边的 `.key-cap`(28) / `.range-val`(24) 同一档，不再比胶囊按钮显大一圈。

### 4. 顶栏浮层向设置面板统一

`selfTopbar.css` §4.1：

- `.tb-pop-card` 圆角 8 → 16、边框 `#DADCE0`、投影换成面板那套两级阴影；
- `.tb-pop-tab` / `.tb-fav-cat`：8px 圆角 + 蓝色擦除动画 → **999px 胶囊**，选中
  `#D3E3FD` 底 + `#1A73E8` 字，hover 统一 `rgba(60,64,67,.08)`；
- `.tb-pop-action`（查看全部 / 播放全部）：纯文字链接 → 胶囊按钮，`#5F6368` 字、hover 8% 底；
- `.tb-media`：8 → 12px 圆角，hover `#F1F3F4`；
- 新增 §4.1.6 的 `.blie-ripple`（页面 DOM 版，几何 / 软边 / 曲线与 panelButton.css 那份一致）；
  `selfTopbar.ts` 里 `installRipple(document, TOPBAR_RIPPLE)` 做事件委托，cleanup 里摘掉。
- 选中态是浅蓝底，tab / fav-cat 的涟漪颜色单独给 `#202124`（同 §2 的理由）。

**注意**：涟漪的 CSS 有两份（shadow 里的 panelButton.css、页面里的 selfTopbar.css），
因为 `?inline` 导入没法跨作用域共享。改参数时两边一起改。

### 实测（探针 chromium 加载新产物）

- 涟漪：按下 40ms `opacity 0.046` / `scale 0.12`；**按住 300ms 停在 `0.120`**（不再自己消失）；
  松手 150ms 降到 `0.073`；450ms 节点移除。轻点后 120ms 仍有 `0.112` 的涟漪。
- 开关：`44×26`（屏幕 53×31），track 圆角 13px，选中 thumb 20×20 / `left 2px`。
- 顶栏：`.tb-pop-tab` 999px / `#D3E3FD` / `#1A73E8`；`.tb-pop-action` 999px；`.tb-media` 12px；
  tab 与 media 按住 200ms 涟漪都停在 `0.120`。

## v005 修：级联开关点不动 + 级联默认关闭 + 静态节点行不再有按下反馈

用户反馈：①「面板卡片级联」的开关点不动（关不掉）；②「节点表查看」和节点表里的按钮没有涟漪。

### ① 开关点不动 = 命中区跟着尺寸一起缩了

v004 把 `.switch` 从 52×32 收到 44×26（屏幕上 53×31），**可点区域也一起缩了一圈** ——

## v015 悬浮窗没声音：音量键名换了 + 静音会被存成音量 0

**现象**：动态页的视频在悬浮窗里打开后**完全没声音**，点一下静音再取消静音才恢复。
之前修过的「刚打开时声音过大」不能回归。

**根因一（键名）**：`savedPlayerVolume()` 读的是 `bilibili_player_settings.video_status.volume`，
而现在的播放器已经改存 `bpx_player_profile.media.volume`（实测 `bilibili_player_settings`
这个键根本不存在）。于是「音量锚定」永远拿不到值，**每次**都掉进 v024 的静音兜底。

**根因二（静音有副作用）**：兜底里写 `video.muted = true`，播放器把「被静音的 `<video>`」
当成「用户把音量拖到 0」持久化 —— 实测档案变成 `volume: 0` / `nonzeroVol: 0.9`，
下次打开还是 0，形成死循环。这正是「点一下静音再取消就恢复」的来源（取消静音会恢复到
`nonzeroVol`）。

**改法**：

1. 读 `bpx_player_profile.media.volume`，旧键 `bilibili_player_settings` 兜底；
   读不到就**什么都不做**（播放器自己的默认音量就是最终音量，不替它猜）。
2. **永远不写 `muted`**。只写 `volume`：元素一出现就钉上保存音量，谁改走就写回来，
   播放器自己写出同值（说明恢复流程跑完）或 1.5s 后收工。「起播那一段别出声」仍由
   `holdEmbedAutoplay` 扣在暂停上，不需要靠静音压。
3. 一次性修复历史坏值：`volume === 0 && nonzeroVol > 0` 判定为「被静音写坏的」，
   按 `nonzeroVol` 修回去并写回档案；用 `bili-elite-audio-repair` 标记保证**只修一次**，
   之后用户真把音量拖到 0 不会被我们改回来。
4. 放行时补一道保险：`releaseEmbedHold` 里如果 `<video>` 是静音的、而档案音量非 0，
   顺手解开（播放器在「起播被扣住」那一两秒里自己静音是它的自动播放兜底，
   而它的 UI 还显示未静音 —— 这就是用户看到的样子）。

## v017 顶栏频道面板改成「悬停时才建」

**起因**：参考 bilibili-margin v0.29 的首页性能数据（脚本 2.02s → 0.32s、JS 堆 48.5MB →

**先量清楚我们自己的增量**（Chromium 1440/1600 宽、未登录、首页，关掉「首页预加载」控制

| --- | ---: | ---: |

| 其中 `#bili-elite-tb` | — | 483 |
| 其中 `#bili-elite-home-panel` | — | **389** |
| JS 堆 | 18.5 MB | 18.6 MB |
| 首屏 task | 1.42 s | 1.51 s |
| 空闲 5s 的扩展 CPU | — | **1.2 ms**（profile 里扩展只占 1.2ms，其余全是 idle） |

`mouseenter` / `focusin`（`bindEvents`）。网络该提前还是提前，插入那一刻字符串已在手里，
microtask 里同步完成 —— 用户感知不到。实测：首屏 `#bili-elite-tb` 483 → 97 节点，
整页 1973 → 约 1600（三次 1564~1609）；hover「首页」后 700ms 面板 389 节点、422 高、内容完整，无报错。

**试过但没采用**（实测数据留档，别再回头试）：

- `content-visibility: auto` 加到 `.feed-card` 上（配 `contain-intrinsic-size: auto 284px`）：

## v018 圆角弧线上的那条深色虚线

**现象**（用户报 + 截图）：v016 之后四角不黑了，但**圆角弧线本身**上多了一条 1px 的深灰
细线，断续成「虚线」状。用户截图里那块区域是浅粉色（视频画面正好是浅色），深灰线在浅底上

**根因：三层圆角的抗锯齿边缘没对齐。** 播放器里外一共三层圆角：

两者差出来的那一圈里，占位骨架的**黑底**露了出来 —— 视频画面是浅色时就是一条深色弧线，
量化成整像素后变成断续的「虚线」。直边上看不到，因为直边正好切在整像素边界上。

**诊断过程**（逐个染色排除，真实播放页、暂停态、在视频区里垫一层 `#EFDCE1` 的粉色 div
保证「浅色内容」这个前提，再把合成层排除掉）：

| 改动 | 左上角暗像素（亮度 < 200） | 最暗值 |
| --- | ---: | ---: |
| 基线 | 11 | 120 |
| `.bpx-player-video-area` 底色染绿 | 11（仍是中性灰） | 120 |
| `#bilibili-player-placeholder-top` 染红 | 11（红色不出现） | 120 |
| 隐藏 `<video>` | 11 | 121 |
| `isolation: auto` / `translateZ(0)` | 11 | 120 |
| 去掉 video-area 的 mask | 15（更糟） | 104 |
| `clip-path: inset(0 round 12px)` | 9（露出来的是 video-area 自己的底色） | 108 |
| 占位骨架圆角 11px / 10px | 15 / 21（更糟：骨架更方 → 露更多） | 68 / 60 |
| 占位骨架圆角 13px / 14px / **16px** | 8 / 4 / **0** | 149 / 183 / — |
| 占位骨架底色改透明 | 0（但播放器初始化前会闪白） | — |

+4 是量出来的（+2 还剩 8 个暗像素、+4 归零）；这层只在初始化前露出来、本身是纯黑骨架，

## v019 修：节点表里有 11ms 的节点，播放却一直挂在 1150ms 那个上

**现象**（用户报 + 两张截图）：节点表（26 个节点，`cn-lndl-ct-01-01` 11ms 排第一）里
明明有 11ms 的节点，播放页「当前节点」却标在 `mirrorbd` 1150ms 上，「生效中」也一直是它。

**先确认不是「没生效」**：在真实浏览器里（bsk，用户自己的 B 站登录态）往这一页的
`bili-elite-cdn-hosts` 里塞进两个更快的节点，再发一条 `/upgcxcode/` 分片请求 ——
请求真的被改到了 `cn-lndl-ct-01-01`，`bili-elite-cdn-applied` 也跟着更新了。
即 `rewriteMediaUrl()` → `preferredHostFor()` 这条链路本身是通的。

**根因有两个，叠在一起：**

### ① 本页分数表只测过一部分节点，却否决了整张长期表

`preferredHostFor()` 按「本页分数（30 分钟）> 长期表」顺序问表，旧代码**问第一张表就收工**：

```js
if (typeof curMs === 'number' && bestMs > curMs * 0.6) return ''
return best !== cur ? best : ''      // ← best === cur 时直接 return ''，第二张表一次都没问到
```

而本页分数（`scores`）只覆盖「测速那一刻这条流给的节点」。B 站一个视频常常只给
**1 个真 CDN 主机**（其余是 P2P），换清晰度 / 站内换视频后又换一批 —— 分数表里没有新主机，
于是「当前节点是分数表里唯一测过的」→ `best === cur` → `return ''` → 长期表里 11ms 的节点
根本没机会。整整 30 分钟（分数 TTL）都挂在慢节点上，节点表里却明明白白写着 11ms。

复现（真实页面、真实表）：

| 状态 | 旧逻辑 | 新逻辑 |
| --- | --- | --- |
| 分数表只测过 `mirrorbd` 1150ms，长期表有 `cn-lndl` 11ms | `''`（不换） | `cn-lndl-ct-01-01` |
| 分数表覆盖全部候选、当前确实最快 | 不换 | 不换 |
| 提升不到 40% | 不换 | 不换 |

**改法**：一张表只有在**测过全部候选**时才有否决权；覆盖不全就当它「没意见」，跳过它去问
下一张表。`applyPick()` 用的 `bestBy()` 同一个坑（挑出来的就是当前地址 → 调用方当成
「有结论」而 `continue`），一起改成返回 `null`，让它落到长期表。

### ② 候选只取「这个视频给的节点」，而 B 站常常只给一个

用户这一页的 `playurl` 里，真 CDN 只有 `upos-sz-mirrorbd` 一个，其余两个是 P2P
（`*.mcdn.bilivideo.cn`、`*.edge.mountaintoys.cn`）。所以就算逻辑全对，候选里也只有那一个
1150ms 的 —— 节点表里 26 个节点有 25 个「用不上」。

但**签名与主机无关**（重测就是拿一条签名地址换 26 个主机挨个测的，全部 206），
所以「这个视频没给」不等于「用不了」。实测：把这一页的真实分片地址换成
`cn-lndl-ct-01-01` → **206 + 1024 字节**，正常。

**改法**：候选 = 这个视频的 CDN 主机 ∪ 长期表里测过的 CDN 主机，仍然只在「比当前快 40%
以上」时才换。手动指定的节点也认「只在表里」的主机（以前 `t.urls[force]` 找不到就退化成自动）。

**只改了 `extension/guard.js`**（手写、不走构建），`src/` 一个字节没动 —— 重新加载扩展即可。

`DEV_VERSION` → `1.2.5 v019`。

### 1. 搜索页 / 右栏卡片补「已关注」

### 2. 看图器工具栏（缩小 / 放大 / 左旋 / 右旋 / 复位）

**需求**：图片打开后加一套和百度贴吧一样的按钮，Google 风格 + 点击涟漪，不做下载。

**关键发现**：B 站看图器是 PhotoSwipe 5，**实例挂在 `window.pswp` 上**（`pswp.element`
就是那个 `.pswp` 节点，关闭时一起销毁）—— 所以缩放直接走官方 `pswp.zoomTo()`，
尺寸、平移、边界都由它自己算。注意它是**改 img 的 width/height 实现缩放**的
（zoom=1 → 原图 2048px、zoom=2 → 4096px），不是 `transform: scale`。
`currZoomLevel` 初始是 `null`（B 站配的 fit 模式），这时取 `zoomLevels.min`
（实测 0.777）当当前值，否则 `null × 1.4` 会算出 0。

**旋转**：PhotoSwipe 没有 rotate，用 CSS **独立变换属性** `rotate` 做 —— 它和 `transform`

平移），rotate 绕左上角一转图片整张甩出视口（实测只剩左下角一块）；`<img>` 的
transform-origin 是默认的中心。

淡出，胶囊跟着淡出）。`pointerdown / click / wheel` 一律 `stopPropagation` —— pswp 的
拖动、点击缩放、关闭都挂在 `.pswp` 上（冒泡阶段），不拦的话点按钮会连带把图放大/关掉。

selfTopbar.css 那两份一致（`max(w,h)×2.2`、0.75s、`opacity .3→0`），**改参数三处一起改**。

用户反馈三点：① 标签栏下面还有一条多余的灰线；② **底部蓝色条缺失**；③ 对照 demo 少了东西 ——

### ① 多余的灰线 = B 站自己的 `hr.search-line`

## v038 修自绘查看器：第二次打不开 / 开合动画没从原位走

用户报两个 bug：① 看图器打开关闭只能一次，第二次点图打不开；② 打开 / 关闭动画

### 1. 第二次打不开（两个原因叠在一起）

- **透明的 `<img>` 把点击全吃了**：`pointer-events` 是继承属性，但子元素显式写的
  `auto` 能盖过父层的 `none` —— 关闭后 `.blie-iv` 已经是 `pointer-events: none`，
  可那张 `opacity: 0` 的图仍是 `auto`、还铺满视口，缩略图的点击全被它拦下
  （探针报 `subtree intercepts pointer events`）。改成 `.blie-iv.is-open .blie-iv__img`
  才给 `auto`，并给整层加 `visibility: hidden`（延迟 300ms，等关闭 FLIP 播完）。
- **同一张图第二次打开时 `src` 没变，`load` 不再触发**：`place()` 永远不跑，图片停在
  `opacity: 0`。改成先 `removeAttribute('src')` 再设，并用
  `complete && naturalWidth` 兜一道（缓存命中时直接摆）。

### 2. 动画没从原位走

- **缩略图被裁成正方形**：B 站动态图缩略图是 `@264w_264h_1e_1c`，`1e_1c` 会裁成
  正方形，比例和原图不同。拿它当占位会让 FLIP 的终点按正方形算，原图换上来尺寸一跳

- **先量、先起 FLIP，再显示图片**：原来是先 `is-ready` 再 `animate`，会先闪一帧铺满

- **关闭时不再整体淡出**：`.blie-iv` 原来有 `opacity` 过渡，180ms 就把整层淡没了，

- **起点 / 终点都用缩略图元素现量**：`SelfViewerItem` 里存了那张 `<img>` 的引用，

## v039 看图器渐进加载：裁剪缩略图 → 完整缩略图 → 原图

用户反馈：打开时原图慢，等待期间一片空白。要求用缩略图占位，并且
「裁剪缩略图 → 完整缩略图 → 完整大图」每一档变化都要有动画、不能突兀。

### 先探测了图床规则（这是三阶段的前提）

B 站图片后缀 `@264w_264h_1e_1c` 是「宽 264、高 264、居中裁剪」（正方形）；
只写 `@480w` 就是「宽 480、高度按比例」。同一个文件实测：

| 后缀 | 尺寸 |
| --- | --- |
| `@264w_264h_1e_1c.avif` | 264×264（裁剪） |
| `@264w.avif` | 264×428（等比） |
| `@480w.avif` | 480×778（等比） |
| 去掉 `@…` | 800×1297（原图） |

所以「完整缩略图」这一档直接用 `@480w` 构造，不用额外调 B 站接口。

### 三阶段 + 几何过渡

- 图片的 `left/top/width/height` 由 JS 写死（`placeImg` 按当前这张图的
  `naturalWidth/Height` 算 contain 后的 rect），不再靠 `max-width: 100%` 让浏览器自己算 ——
  三个比例不同的图之间，只有我们知道目标 rect 才能做补间。
- `.blie-iv__img` 的几何走 CSS transition（260ms），`transform` 留给缩放 / 平移 / 旋转。
- **`object-fit: cover` 是关键**：过渡中间区域比例和图片比例不一致的那一小段，图片始终
  填满区域、多出来的裁掉 —— 视觉上就是「裁剪的正方形慢慢展开成完整图」，没有黑边、
  也不会被拉伸变形。
- 打开时用 `placeImg(false)`（加 `is-snap` 关掉 transition），否则会看到图片从 0×0 长出来。
- `onFirst` 必须幂等：`complete` 兜底和 `onload` 会各触发一次，不挡就会跑两遍
  `loadHigher`，两组 upgrade 各带一份 `level`，原图上来之后又被等比缩略图盖回去
  （实测 src 在两者之间来回跳）。

## v042 修评论区图片接管：马赛克占位 / 关不掉 / 丢动画 + 缩放改加法 + 切图过渡

用户反馈：视频 / 动态评论区点开图片变成一张马赛克、关不掉、丢动画；缩放步进要**加法**

### 1. 评论区图片为什么是马赛克

`pswpTakeover` 原来把 `dataSource[i].msrc` 当缩略图 —— 那是 PhotoSwipe 自己的**占位
小图**（常常是 1×1 的 data URI 或几十像素），铺满全屏就是一坨马赛克；原图一旦加载失败
就永远停在那儿，看起来就是「关不掉、卡住」。

改成：
- 当前这张用**页面上那张缩略图**（`lastEl.currentSrc`，已经在缓存里、比例就是用户看到
  的样子）；
- 其它张用 `@480w` 现造一张等比缩略图；
- **完全不用 `msrc`**。

### 2. 关不掉 / 丢动画：shadow DOM 里拿不到 `<img>`

评论区的图在 `bili-comments` 的 shadow DOM 里，`e.target` 会被重定向成宿主元素，

改成用 `composedPath()` 逐层找 `<img>`，并排除 `.blie-iv` / `.pswp` 内部
（否则在查看器里点一下，就把「上次点的图」覆盖成查看器自己）。

### 3. 缩放步进改成加法

`stepFactor() / wheelFactor()` 是乘性（1.3 倍），改成增量 `scale + step/100`。
默认 30% 就是 100% → 130% → 160% → 190%。

### 4. 切图：首帧瞬时，「缩略图 → 完整图」保留动画

去掉 `loadHigher` 的 `instant`：切图首帧仍是 `placeImg(false)`（瞬时换图），但切过去

## v043 修：关掉图片后整页还是模糊（评论区）

## v046 修：偶尔一直糊着（低清不换原图）+ 加载阶梯加固 + 关闭回收大图 + 排查线索

### 1. 现象与根因

用户报：**打开图片后偶尔一直停在低分辨率，等多久都不换高清图**，不能稳定复现，但一定存在。

根因是 `loadHigher` 里两档（`@480w` 等比缩略图 / 原图）**各自 await 完就直接写 `u.img.src`**，
谁后回来谁生效，而档位变量 `level` 是「已请求」而不是「已上屏」：

| 顺序 | 结果 |
| --- | --- |
| 中档先到 → 原图后到 | 正常，最终原图 |
| **原图先到 → 中档后到** | 中档把原图**盖掉**，而 `level` 已被推到 2 → **再也不升级** |

谁先回来取决于缓存命中 / 网速 / 图大小 —— 所以偶发、不能稳定复现。

### 2. 改法：并行下载、串行上屏、只认「已上屏」

- `appliedLevel` 只在 `swapTo()` **成功之后**推进；上屏顺序被钉死成 1 → 2，低档永远盖不了高档。
- 两档仍然**并行预加载**（谁慢都不拖累谁），但 `pickLevel()` 做了一次 `Promise.race`：
  更高一档先就绪就**跳过中间档**，不会为了更糊的图再等一次（也不会出现「糊一下又清」）。
- 新增 `swapTo()`：换 src 后等 `load` + `decode` 才算成功，**decode 挂死也有超时兜底**
  （超时时只要 `naturalWidth > 0` 就按成功算）。失败时把上一档**放回去**，不会留白板。
- `show()` 里首帧的 `onload` / `onerror` 用完即摘：旧 handler 留着会在高档失败时把 src 改回去。
- 首帧本来就是原图（页面缩略图没有尺寸后缀）时直接记 `appliedLevel = 2`，不再走阶梯。
- 中档只在「页面缩略图比 480 更糊」时才插一档（`pageThumbWidth()` 优先读元素 `naturalWidth`）——
  `pswpTakeover` 里那张页面图常常已经是 `@1000w`，再换 `@480w` 就是先降级再升级。

### 3. 慢网 / 后台标签页：兜底重试

`preloadUrl` 超时只是「我们不等了」，请求还在后台跑 —— 所以重试多半直接命中缓存。
原图没上屏就排队重试（2s / 6s / 15s / 30s），并在 `online`、`visibilitychange → visible`
时立刻再试一次（后台标签页会被限速，用户切回来该看到的就是原图）。

### 4. 替换逻辑的另两处隐患

- **带签名的地址**：老的 `THUMB_SUFFIX = /@[^/\s,]+$/` 会把 `?sign=…` 一起当后缀吃掉，
  换出来的「原图」没有签名 → 403 → 这张图永远停在低清，重试多少次都没用。
  现在 `splitQuery()` 把 query 摘出来，**只动 path 段**（`toOriginalImageUrl` / `toMidThumbUrl` 同步改）。
- **`u.img.onerror` 兜底**改成直接把档位标成 2（屏幕上马上就是原图），否则阶梯会把 `@480w` 盖上来。

### 5. 缓存 / 内存回收

- 关闭后 `releaseImage()`：`<img>` 摘掉 `src`、几何清零。图层 `display:none` 时**解码后的位图
  仍然挂在元素上**（4K 图 30~50MB），看几张图内存就下不来；下次打开重新赋 src 命中 HTTP 缓存，不变慢。
- 关闭时清空 `items`（含页面 `img` 引用）、`appliedLevel`、重试定时器。
- 离屏预加载 `Image` 回调用完即摘，让它尽早变成垃圾。

### 6. 排查线索（这次的重点之一：下次再出现要能定位）

1. `?blie-debug` 刷新 → 控制台按 `[iv]` 过滤：`show` / `ladder` / `applied` / `preload-fail` /
   `swap-fail` / `retry` / `retry-ok` 都带毫秒时间戳与档位。
2. 同一开关下，查看器左下角出现 `L2 原图 · 800×1297` 小标签 —— 糊的时候截个图就知道卡在哪一级。
3. 关闭时若「看了 3 秒以上仍没升到原图」，把现场写进 `<html data-blie-iv-state>`（JSON：
   level / 实际像素 / src / thumb / thumbW / index / count / 最近 12 条 trace）。
   **刚打开就关、手快连切不记**，避免污染现场；正常看图不留任何痕迹。
4. `logger.ts` 新增 `isVerbose()`（调试 UI 按它决定要不要挂）。

### 7. 验证（探针 1440×900，动态页 4 图相册）

用 `ctx.route` 人为给某一档加延迟，**确定性地**造出两种到达顺序：

| 场景 | 结果 |
| --- | --- |
| `@480w` 延迟 1800ms（原图先就绪） | 直接 `L2 800×1297`，中间档被跳过（`hits.mid` 只有预加载那 1 次） |

## v047 看图器：高清图「加载好就换」——去掉上屏排队 + 请求提优先级 + 中间档不再抢镜

用户反馈：v046 换高清图**很慢**，网络没变。要求「高清图加载好了就换，但不能丢动画、不能加载不到」。

### 1. 慢在哪（实测）

v046 是「两档并行下载、**串行**上屏」：原图必须等中档那次 260ms 几何过渡 + 解码跑完才轮到。
抓 `[iv]` 轨迹看得很清楚：`preload{level:2, ms:74}` 之后 `swap{level:2, swapMs:0}` ——
**图早就下好了，卡在排队上**。对照（同机、清缓存、每轮开不同的图）：

| 版本 | 打开 → 原图上屏 |
| --- | --- |
| v045 | 231ms 到 480 后**再也不换**（就是用户报的偶发低清） |
| v046 | 126 / 103 / 251ms（且中间档先插一次） |
| v047 | **17 / 29 / 33 / 101ms**，多数情况直接从裁剪缩略图跳到原图 |

### 2. 改法

- **上屏不再排队**：每档自己一就绪就调 `applyLevel()`，谁快谁上。不降级改用**同步闸门**
  `claimedLevel`（高档一就绪立刻占位，之后到的低档直接丢），不再靠队列顺序。
- **抢占**：`swapSeq` 自增，在飞的低档回调全部作废（不许再动 DOM、更不许把 src 还原成低档）。
- **下载提前到 `show()`**：`buildSteps()` + `startPreloads()` 在打开那一刻就发出请求，
  不等占位缩略图 load 完（冷页面能省一整个缩略图往返）。
- **请求提优先级**：离屏 `new Image()` 在 Chrome 里默认 **low** 优先级，页面在刷缩略图 /
  视频时会被排到后面 —— `fetchPriority = 'high'`（要在赋 `src` 之前设）；换图那一下也设 high。
- **解码等待上限 120ms**：大图 `decode()` 是纯 CPU（100~300ms），超时也照上，
  几何过渡先跑，解码完自然画出来。
- **一 load 就重摆几何**：`naturalWidth` 到手就 `placeImg(true)`，否则会有一百多毫秒把原图
  塞进缩略图那个方框里（`object-fit: cover` 直接裁一刀），看起来「先跳一下再展开」。
- **中间档压 220ms 再上**（`MID_DELAY`）：快网 / 缓存命中时原图 100ms 内就到，
  中档紧跟着上只会让画面连跳两次（用户要求「不要丢动画」，连跳两次就是抖一下）。
  原图先到 → 中档被 `claimedLevel` 作废，整档跳过。
- **切图 / 关闭时中止在飞的预加载**（`abortPreloads()` + `preloadGen`）：掐掉的不许再发下一轮，
  别让切走的那张继续抢带宽。

## v048 修：看完图之后视频的 ←→ 失效（焦点没还回去）+ 按键只在真开着时接管

用户报：**打开一次图片后，播放页的 ←→（进度加减 / 长按加速）按了没反应**，要求顺带排查其它快捷键。

### 1. 先证明「不是按键被吞」

在真实 Chrome（用户自己的 profile，扩展已加载）上跑了完整复现：普通态 + 网页全屏，
两条入口（动态页相册 / `pswp` 接管模拟）各开关一轮，然后 `bsk press ArrowRight`：

| 场景 | 结果 |
| --- | --- |
| 关图后（普通态） | 30 → 36.0s，seek 正常 |
| 关图后（网页全屏，焦点在播放器按钮上） | 60 → 65.9s，seek 正常 |
| 事件是否到达页面 | `defaultPrevented: false`，`activeElement: BODY` |

所以**不是我们把 keydown 吃掉了**（`onKey` 第一行就是 `if (!open) return`）。

### 2. 真正的链路：焦点被抢走，iframe 里的播放器收不到键

看图器是一层盖在整页上的遮罩。用户点缩略图那一下（`mousedown`）浏览器就把焦点挪到了
顶层文档，而**焦点一旦离开 iframe，iframe 里的键盘处理就再也收不到按键**——
动态悬浮窗的播放器正是跑在 iframe 里的（视频页的播放器挂在顶层文档，所以它不受影响，
这也是我在视频页复现不出来的原因）。

用「iframe 里放一个可聚焦元素」做最小复现，旧版 vs 新版：

| | 打开前 | 打开时 | 关闭后 |
| --- | --- | --- | --- |
| v047 及以前 | `iframe` | `BODY` | **`BODY`（丢了）** |
| v048 | `iframe` | `BODY` | **`iframe`（还回去了）** |

修法：
- `pointerdown` **捕获阶段**记下 `document.activeElement`（等 `click` 再读已经晚了，
  那时焦点早被挪到 body），存在 `focusBack`；
- 关闭（动画结束、层藏起来之后）`focusBack.focus({ preventScroll: true })` —— 对
  `<iframe>` 调 `focus()` 能把它的文档重新激活。元素已从 DOM 摘掉就不还。
- 点在自己这层上的 pointerdown 不记（关图 / 切图 / 工具栏都会触发）。

### 3. 顺带修掉的两个隐患（复查改动时发现）

- **模态期间页面还会重复处理按键**：原来只 `preventDefault()`，按 ← 切上一张的同时
  **视频也会往后退 5 秒**。现在这 7 个键（Esc / ← / → / + / = / − / 0）用
  `stopImmediatePropagation()` 吃掉，其它键一个都不碰。
- **`aria-modal="true"` 一直挂在隐藏层上**：一个藏起来的对话框永远标着「我是模态」，
  别的脚本（含页面自己的）按这个判断会以为页面上一直开着弹窗。改成打开时挂、关闭时摘。
- `onKey` 再加一道闸：`!open || !ui || !ui.root.classList.contains('is-open')` 直接返回 ——
  哪怕 `open` 因为异常路径和 DOM 错开，也不可能出现「监听还在、键被吃了、界面上什么都没有」。

### 4. 其它快捷键排查结论

我们这层只认 7 个键，且只在打开时；`quickKeys` 只认用户配的「刷新 / 回顶部」；
`dynamicOverlay` 只在自己的悬浮窗 + 自己的看图器开着时认 Esc / ←→。**其余键（空格、
↑↓、M、W、F…）一个都没碰**。真正会「一整片键都失效」的只有焦点丢失这一类，已修。

### 5. 验证

- 焦点：`iframe → BODY → iframe`（新版）；旧版停在 `BODY`。
- `aria-modal`：打开 `true`、关闭 `null`。
- 阶梯 / 切图 / 关闭回归：`L1 → L2` 不回退；`ArrowRight` 切到 2/4 后仍到 `L2`；
  `verify-v045` 交互全绿（24 帧滑动 / 19 档尺寸过渡 / 关闭 21 帧缩回），`pageerror` 0。

## v049 修：评论图看完后 ←→ 永久失效（B站自己的查看器 isOpen 卡住）

用户复现路径：**有图评论的视频 → 打开评论图 → 关闭 → 播放页 ←→ 按了没反应**（稳定复现）。

### 1. 根因：不是我们吃键，是 B站 评论图查看器自己吃

评论图用的是自定义元素 `<bili-photoswipe>`（`bili-comments.js` 里 `customElements.define`），
它在 `initEvents()` 里挂了**一条 document keydown**：

```js
addEventListener(document, 'keydown', (t) => {
  const n = () => { t.stopPropagation(); t.preventDefault() }
  if (this.isOpen) switch (t.key) {
    case 'Escape':     this.close(); n()
    case 'ArrowLeft':  this.prev();  n()
    case 'ArrowRight': this.next();  n()
  }
})
```

`isOpen` 只在 **它自己的 `close()` 跑完**、或**元素被移除**（`disconnectedCallback`）时才复位。
只要有一次没收尾（`close()` 里 `await animateToClosedState()` 抛错/挂住、关闭时缩略图已被
信息流重渲染掉、被我们接管后它没走 close），`isOpen` 就永远停在 `true` ——
**整页的 ← → 被 `stopPropagation + preventDefault` 永久吞掉**，而画面上图早就关了。
这解释了「只有 ←→ 坏、别的键没事」，也解释了为什么视频页复现不出（那是播放器自己的键盘）。

### 2. 为什么之前几版都没修掉

v048 修的是**焦点**（iframe 里的播放器收不到键），那条是真问题但不是这个；
v046/v047 改的是加载阶梯，跟按键无关。真正吃键的是页面的查看器，不是我们。

### 3. 改法：自愈（不改 B站 组件）

- `dropStalePhotoSwipe()`：把「还连着、但已经没有 `visible` 属性」的 `<bili-photoswipe>` 摘掉。
  断开连接会跑它的 `disconnectedCallback` → `isOpen = false` + `disposables.dispose()`
  （监听全摘）。它的 disposables 只是个普通数组，下次 `open()` 重新挂回 DOM 时
  `connectedCallback → initEvents()` 会重新注册，**不会把组件搞坏**；正开着（有 `visible`）的一律不动。
- 两个触发点：
  1. **点击后 800ms**（`pointerup`）：用户「点背景关掉评论图」正是产生残留的那一下；
  2. **Esc / ← / → 被吞之后 700ms**：`setTimeout(0)` 等这一轮派发结束再看
     `defaultPrevented`（我们这个监听虽然挂在 document 冒泡，但注册得比页面早，
     当场看永远是 false）。
  两个都带 700/800ms 延迟，是为了不把正在正常回缩的 333ms 动画剪掉。

### 4. 验证

## v054 取证补「最近一次真实按键的命运」（合成探针有盲区）

用户回传的取证（视频正常播放 `readyState:4` / `paused:false`）里，**合成按键没被吞**
（`before.prevented:false`），但真实按 ←→ 确实没反应。这两件事能同时成立只有一个解释：
**吞键的处理器只认真实事件**（判 `isTrusted`，或只在真实交互路径里生效）。

`new KeyboardEvent(...)` 是 `isTrusted:false` —— 用它做的排除法永远看不到这种吞键，
所以前几轮「没人吃键」的结论其实是**探针的盲区**，不是真相。

### 改法：记真实事件

- `onKeyRecCapture`（document 捕获，注册得很早）记下 Esc/←/→ 的
  `{ key, trusted, at, tAt }`，`setTimeout(0)` 后回填 `prevented = e.defaultPrevented`，
  260ms 后回填 `tNow = video.currentTime`；
- `onKeyRecBubble`（document 冒泡）回填 `docBubble`；
- 报告里多一块 `lastKey` + `hasFocus`。

判读方式（写进注释了）：

| `lastKey` | 结论 |
| --- | --- |
| `prevented: true` | 有人 `preventDefault` 了 —— 真实事件才吞，合成探针看不到 |
| `docBubble: false` | 有人 `stopPropagation` 截在半路 |
| 两者都 false 且 `tNow ≠ tAt` | 播放器其实动了（观感问题） |
| 两者都 false 且 `tNow = tAt` | 播放器自己的键盘处理器没了 / 被禁用 |

### 验证

`iv-lastkey.cjs`：场景 A（没人吞）→ `lastKey{trusted:true,prevented:false,docBubble:true}`；
场景 B（挂一个**只吞 trusted** 的监听）→ `lastKey{prevented:true}`，而同一份报告里
`before{prevented:false}` —— 盲区被如实记录下来了。

## v056 修：评论图之后 ←→ 被永久吞掉（PS5 的 destroy 只调 close 就 return）

v055 的 `preventDefault` 调用栈直接点名了凶手：

```
at KeyboardEvent.wrappedPreventDefault [as preventDefault] (guard.js:961:25)
at t.value (https://s1.hdslb.com/bfs/seed/water-ui/common/bili-photoswipe.js:11:28542)
```

`bili-photoswipe.js` 就是 **PhotoSwipe 5.4.4 本体**。它的键盘模块在 `document` 上挂 keydown，
收到 ←/→ **无条件 `preventDefault()`**（`if (n) { t.preventDefault(); ... }`），
所以只要这个实例还活着，整页的 ←→ 就永远轮不到播放器。

### 为什么实例会「还活着」

PS5 的 `destroy()` 第一行是：

```js
destroy() {
  if (!this.isDestroying)
    return this.options.showHideAnimationType = 'none', void this.close();   // ← 只是调 close 就 return
  ...
  this.events.removeAll()                                                    // ← 真正摘监听在这里
}
```

真正摘监听要等**关闭动画结束后的第二次 `destroy()`**。而 `pswpTakeover` 的顺序是
`p.destroy()` → 立刻 `pswpEl.remove()` —— 元素没了，关闭动画永远跑不完，
`events.removeAll()` 永远不执行 → **document 上的 keydown 永久留着**。
用户看到的就是「图早就关了，视频按不动，按多少下都没反应」，而且「打开过一次图片之后」才出现。

### 改法（`guard.js`）

1. **§11 接管时补一刀**：`p.destroy()` 之后直接
   `p.events.removeAll()` + `p.keyboard.destroy()`（两者都是实例上的公开属性），
   把 DOM 监听一次性摘干净，不再依赖那个跑不完的关闭动画。
2. **§13 运行时补刀**：内容脚本发现「真实按键被 `preventDefault`」时派
   `blie-elite:kill-pswp`，页面世界立刻对 `window.pswp` 做同样的处理 ——
   已经中招的页面**不用刷新**就能恢复。
3. **§12 记录 `data-blie-pswp-alive`**：按键被吞那一刻页面上还有没有活着的实例，
   诊断面板里多 `pswpAlive` / `pswpKilled` 两个字段。

### 验证

## v061 修：首页控制台 `Permissions policy violation: unload`（报错指向 guard.js）

### 现象

`www.bilibili.com` 首页控制台一条红色报错，堆栈顶帧是 `guard.js:977` 的 `wrappedAddEL` ——
看起来像扩展自己在注册 `unload`。

### 根因

- 注册 `unload` 的是 **B 站自己的脚本**：`s1.hdslb.com/bfs/static/shanks/laputa-home/assets/index-*.js`
  对 `window` 调了两次 `addEventListener('unload', …)`（实测抓到两条调用栈）。
- `unload` 从 Chrome 117 起被弃用，新版浏览器（用户这台是 157）默认按 `Permissions-Policy: unload=()`
  把它禁掉 —— 此时任何 `unload` 注册都会打一条 violation，**而这条监听本来就不会触发**。
- 报错堆栈之所以指向我们：`guard.js` §13 为了记 keydown 包了
  `EventTarget.prototype.addEventListener`，B 站调进来时 wrapper 是调用原生的那一帧，
  于是 violation 的栈顶落在 `guard.js` 上（B 站自己注册的监听，锅看起来是我们背）。

### 改法

wrapper 里对 `unload` 做一次「文档是否禁了它」的判断，禁了就直接不注册：

```js
var blieUnloadIsBanned = function () {
  if (blieUnloadBanned !== null) return blieUnloadBanned
  try {
    var pol = document.permissionsPolicy || document.featurePolicy
    if (pol && typeof pol.allowsFeature === 'function')
      blieUnloadBanned = pol.allowsFeature('unload') === false
  } catch (e) {}
  return blieUnloadBanned === true
}
...
if (type === 'unload' && blieUnloadIsBanned()) return
```

- 只在**已经禁掉 unload** 的文档里跳过 —— 那里监听本来就不会触发，行为零变化；
  允许 unload 的文档（老浏览器 / 站点没设这条 policy）照旧透传。
- 结果缓存一份（同一文档 policy 不会中途变），不影响 keydown 的记录路径。

| 主文档加 `Permissions-Policy: unload=()`（模拟 Chrome 157） | 2 条 violation，`allowsFeature('unload') = false` | **0 条**，`unload` 注册尝试 0 次 |
| 不加这条 header（policy 允许） | 注册 2 次 | 注册 2 次（**行为不变**） |
