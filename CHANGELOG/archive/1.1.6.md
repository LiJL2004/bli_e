# 1.1.6

> 小版本：顶栏从「先放一条壳」走到「整条自己画」（界面优化 → 顶栏优化），不再等 B 站
> 那套 header 脚本，右侧图标连同悬停浮层都是我们自己的；进出全屏 / 宽屏的那段补间动画
> 收短了，切换帧里几处「白干的活」也去掉了。
> 曾经试过「把整轮布局计算推迟一帧」，逐帧验证发现会让 UP 卡飞出去一帧，已回滚（见下）。

## 优化 · 首屏顶栏「壳」：顶栏从第一帧就是完整的

**问题**：播放页打开后，顶栏要等 B 站自己那套 header 脚本跑完才渲染。实测（playwright +
真实构建产物，1600×900，BV1Qgn96oEUz）：

| 时刻 | 顶栏状态 |
| --- | --- |
| 485ms | 我们插入的骨架栏就位（logo + 两块灰块） |
| 750~950ms | 首帧绘制 |
| **4511ms** | B 站顶栏的导航项 / 搜索框 / 右侧图标一起出现，骨架栏退场 |

把扩展整个关掉量同一页面：导航项 **5060 / 5432ms** 才出现（两次采样）—— 也就是说慢的不是
我们，是 B 站自己的顶栏渲染。但用户看到的观感是「顶栏四秒钟长不出来」：骨架栏只有 logo
和灰块，和真顶栏的结构差得远，一眼就是「还没加载完」。

BewlyCat 之所以「一打开顶栏就在」，是因为整条顶栏是它自己画的、根本不等宿主。
这里学同一件事，但不动现有架构：**把骨架栏升级成一条和真顶栏同尺寸、同布局的「顶栏壳」**。

- 结构：logo + 「首页 ∨ / 动态」+ 居中搜索框 + 右侧图标占位（`ensureSkeleton()`）。
- 数字全部照真顶栏量（1584 视口）：logo 起 24、首页 120（宽 43）、动态 178（宽 28）、
  搜索框 `500×40` 绝对居中于整条 bar、右侧占位贴右 24。实测壳与真顶栏逐项一致：

  | | 壳 | 真顶栏 |
  | --- | --- | --- |
  | 首页 | 120 / 43 | 120 / 43 |
  | 动态 | 178 / 28 | 178 / 28 |
  | 搜索框 | 534,12 / 500×40 | 534,12 / 500×40 |
  | 右侧 | 1423…1543（3 个灰圆点） | 1193…1543（8 个真图标） |

  所以真顶栏就位时只有「右侧灰圆点换成真图标」这一处变化，整条顶栏不会跳。
- **壳里能点的都是真的**：logo / 首页 / 动态是链接，搜索框是 `form`（回车直接走
  `search.bilibili.com/all?keyword=`）。不放点不动的假控件 —— 假界面看着像加载完了、
  点上去却没反应，比空着更糟。空白处仍是 `pointer-events: none`，只有这三个可点元素开
  `auto`，不挡页面。
- **壳里打的字会交接**：真顶栏就位时如果壳的搜索框里已经有内容，就写进真顶栏那颗
  `input` 并聚焦。必须派发 `input` 事件 —— 那颗是 Vue 受控输入框，直接改 `value` 会
  在下一次重渲染时被它自己的状态覆盖（实测立刻变回空）。
- 夜间模式（`night.css` §1.3）同步补了壳里的导航文字 / 搜索框 / 占位圆点配色，
  否则深底上是黑字看不见；窄窗口（≤1100）右侧占位整组让出去，搜索框跟着收窄。

## 优化 · 切换补间动画时长

进入 280 → 200ms，退出 240 → 180ms（`videoFullscreen.ts` 的 `VIDEO_DUR_OPEN` / `VIDEO_DUR_CLOSE`）。

用户说的「切换速度慢」里，最直观的那一段就是这段 FLIP 补间：点击之后还有 B 站自己
100~200ms 的整页重排，280ms 叠上去整段接近半秒。200ms 仍然能看清「从哪儿来、到哪儿去」，
再短就开始显得生硬。

## 优化 · 删掉退出网页全屏时多出来的一次强制排版

`videoFullscreen.ts` 里 `window.scrollTo()` 之后有一句 `void document.documentElement.offsetHeight`，
而紧接着的 `getBoundingClientRect()` 本来就会把这次滚动刷进布局 —— 那是一次纯粹的重复
同步排版，正好落在切换那一帧上。已删除。

## 优化 · 写 CSS 变量前先比一下

`measure()` / `layoutUp()` 以前无条件往 `<html>` 上写变量。`<html>` 的自定义属性一变，
整棵树都要重新匹配样式 —— 而多数时候（拖窗口、滚动条出现 / 消失、观察器重复回调）
那几个数一个都没变。现在统一走 `setRootVar()`：值一样就不写。

## 优化 · 左栏行内 top 的观察器只跑钉住逻辑

`watchLeftSticky()` 的 `MutationObserver` 以前一变就跑整轮 `layoutUp()`（6 个
`getBoundingClientRect` + 2 次 `getComputedStyle`，全是强制同步排版）。它唯一要跟的就是
B 站写在左栏上的行内 `top`，所以改成只调 `syncLeftTop()` + `syncUpPin()`（4 个尺寸 + 1 个变量）。
这个观察器在滚动里也会响，收益是持续的。

## 回滚 · 「切换那一帧不做我们的布局计算」（v001 试过，v002 撤掉）

v001 的做法是：屏幕模式一变只切类，`measure()` / `layoutUp()` / `ensureSendingBar()` 全部
推迟到下一帧。**逐帧采样直接否掉了它**（1100×620 / BV1DUYx63EGw / 真实 Chrome / 144Hz）：

| 帧 | 时间 | 模式 | `up.top − title.bottom` |
| --- | --- | --- | --- |
| 57 | 397ms | web | −50（B 站原生位置，正常） |
| 58 | 530ms | normal | **−363 ← 卡片飞到标题上方** |
| 59 | 738ms | normal | 8（正确） |

也就是退出沉浸式的那一帧，卡片带着空的 `--up-top` 画了出来，下一帧才回位 —— 正是
1.1.5 v008 修掉的「UP 卡窜一下」。而且推迟**并没有缩短总耗时**，只是把一个长任务拆成两个
（进：86+106ms；出：192+132ms），用户多等一帧，收益为负。

现在 `handleScreenChange()` 同步做完，和 1.1.5 的行为一致；文件里留了注释，别再往这个方向改。

## 未改动（查过，确认不是瓶颈）

- **在网页全屏里保留我们的页面布局**（只把播放器交回 B 站）：实测切换耗时没有变化，
  而它会把「页面在播放器底下到底是哪套布局」变成一个需要长期维护的前提 —— 不值得，没做。
- **推荐卡封面放大、UP 卡 sticky、左栏栅格**：逐条摘掉再量，切换耗时没有明显变化，
  开销是「我们的布局比 B 站自己的高 28%（3400 vs 2657px）」带来的整体差异，摘单条规则无效。
- **同一会话内 A/B**（开关「播放页优化」直接对比，长任务毫秒）：

  | | 进入网页全屏 | 退出网页全屏 |
  | --- | --- | --- |
  | 开 | 64 / 75（两次采样 75、76） | 146 / 179 |
  | 关 | <50（无长任务） | 75 |

  剩下的差距是上面那条结构性的（布局整体更高），不是某一处代码能单独消掉的。

## 修正 · 浮层里点按钮会把自己关掉

切「视频 → 直播」、换收藏夹、点「主题」之后浮层直接消失。原因是那一下会把整块内容
重渲染：被移除的按钮正握着焦点，浏览器甩出一个 `focusout`，我们把它当成「用户离开浮层」
排了一次关闭。修法两条：

- `focusout` 时如果正在重渲染（`popPending` 里还有这个 key）就不排关闭；
- 关闭定时器到点时再确认一次指针是否还在这一项里（`:hover`），还在就不关；
- 顺手把焦点还回去：重渲染后按 `data-pop-act + data-value` 找回同一个控件并 `focus()`，
  键盘用户按 Enter 切完 tab 不会掉焦点。

## 删除 · 首屏「顶栏壳」（等 B 站元素的那一版）

骨架栏是 1.1.6 v003 做的：document_start 先画一条和真顶栏同尺寸的壳，等 B 站那套
header 脚本渲染出来再整条退场。现在整条顶栏都是我们自己画的，这层壳再也不会露面，
连带着把「让原生顶栏看起来像我们的」那一整套补丁一起下线：

- 删掉 `ensureSkeleton` / `retireSkeleton` / `ensureLogo` / `ensureDynamicEntry`
  （番剧改名「动态」）/ `ensureHomePanel`（原生频道面板）/ `ensureRightEntryHidden`
  （藏创作中心）/ `syncSearchKeyword`（搜索页关键词回填）/ `foreignTopbarReady`；
- 删掉 `topbar.css` §1.2 的整套骨架栏样式、night.css 里骨架栏那一段、
  以及各处 `#bili-elite-topbar-skeleton` 选择器。
- 原生顶栏上那套「让它看起来像我们的」CSS 也一起删了：`margin-left: 96px` 的 logo 留白
  （没有自绘 logo 之后就是一条 96px 空白）、隐藏 `.big-logo` 与「首页」小图标、
  只留「首页 + 动态」而把其余导航项 `display:none`、藏掉原生频道面板、把原生下拉箭头
  换成我们的伪元素、以及给原生导航项画的「当前页短横」（`syncNavMark` 一并删掉）。
  实测关掉之后：`.left-entry` 回到 x=24、`首页/番剧/直播/游戏中心…` 全部可见，
  与不装扩展的基线逐项一致。

**现在的语义就是两个状态**：打开「顶栏优化」= 我们这条自绘顶栏；关掉 = **B 站原版**
（原生树上一个节点都不动，导航项还是「番剧」、右侧还是原样）。

## 修正 · 「高级材质 → 顶栏」只对我们的顶栏生效

以前 `html.bili-elite-glass` 会同时改原生 `.bili-header__bar` / `.fixed-header` 的底色、
`::before` 毛玻璃和渐变。既然关掉顶栏优化就该是原版，这些规则全部删掉 —— 材质现在只作用在
`#bili-elite-tb` 上（样式本体在 `selfTopbar.css` §5，变量还是那组 `--bili-topbar-*`）。

## 修正 · 顶栏渐变对自绘顶栏不生效

自绘顶栏抄「渐变」时只抄了白纱那条 `background-image`，漏了原生那版最关键的一段：
`::before` 上的 **`mask-image` 竖向渐变**。没有它，白纱在变淡、`backdrop-filter` 的模糊
却还是满格 —— 底边留一条「清晰的玻璃」，看起来就是一条实心白条，正是「效果不如以前」。
现在把那段 mask（`#000 0% → 44% → … → transparent 100%`）原样补上，模糊跟着一起淡，
才是「化开」而不是「切断」。

## 修正 · 搜索框聚焦动效对齐 BewlyCat

上一版是照 BewlyCat 的「形」抄的，但参数没对上，实际观感是「先不动、最后一下跳」：

| | 上一版 | BewlyCat 原版 / 现在 |
| --- | --- | --- |
| 聚焦圆角 | 8px（`--bili-radius-md`） | **12px**（`--bew-radius`） |
| 半径过渡 | 320ms `cubic-bezier(.4,0,.2,1)`（先慢后快） | **300ms `cubic-bezier(.22,.61,.36,1)`**（起步就快） |
| 静息半径 | `999px` | **20px**（= 高 40 的一半，视觉同样是胶囊） |
| 面板开合 | 220ms `--bili-ease` | **300ms ease-in-out**（`result-list` 那套） |

两条关键：

1. **静息半径不能写 `999px`**。胶囊看起来一样，但插值要从 999 一路降到 12，
   半径 > 20（= 高的一半）的那 2/3 时间**视觉上毫无变化** —— 实测 50ms 时 704px、
   120ms 才 104px，看上去就是「卡住然后突然变方」。改成 20px 后 50ms 已经是 16.6px、
   120ms 到 12.75px，圆角从第一帧就在变。
2. **聚焦光环从 `box-shadow` 挪到 `::after` 的 opacity 上**。box-shadow 的过渡是逐帧重绘，
   和半径一起做会掉帧；`::after` 只动透明度（走合成层），观感一致但顺得多。
   `border-radius: inherit` 让它跟着半径一起变；`z-index` 排到 input / 放大镜下面，

## 新增 · 悬停预取：点进播放页快 ~450ms

「首页点视频」「播放页点右栏推荐」两处都是整页导航，慢的大头是那份 SSR 文档。
实测（chromium 1105，同机同网络，各跑两轮）：

| | TTFB | FCP | DOMContentLoaded |
| --- | --- | --- | --- |
| 直接导航 | 386 / 329ms | 830 / 721ms | 843 / 749ms |
| 先 `rel=prefetch` 再导航 | **1 / 1ms** | **371ms** | 398 / 383ms |

导航时 `transferSize = 0` —— 文档直接从 Chrome 的 prefetch 缓存里拿。
关键：B 站的 HTML **没有 Cache-Control / Last-Modified**，进不了普通 HTTP 缓存
（第二轮直接导航照样 329ms），但 prefetch 缓存是单独一份，紧接着的同地址导航会直接命中。
所以 preconnect / Speculation Rules 的 prefetch 在这里都没用，只有 `rel=prefetch` 有效。

`modules/hoverPrefetch.ts`：`pointerover` 委托 → 命中 `/video/BV…` 或 `/bangumi/play/…`
→ 停住 80ms 才发（鼠标扫过一排卡片只预取最后停住的那张）→ 一次会话最多 6 个地址；
`saveData` / 2G 弱网直接不预取。只预取文档本身，不带子资源。

## 优化 · 顶栏右侧浮层的开合动画

以前是「纯淡入 + 6px 位移 + 弹簧曲线」。6px 太小、弹簧在这么短的行程里只会让最后那一下
「顿一下」，观感接近「一块白突然出现」；而且打开用 spring、收起用标准曲线，来回扫几下
就能感觉到手感不一致。

现在改成从图标那个角「落」下来：

- 位移 6 → 10px，配 `scale 0.98 → 1`，`transform-origin` 顶到图标那侧
  （头像那个居中的面板单独改成顶边中点，否则会「从右上角斜着摊开」）；
- 打开 180ms、关闭 120ms —— 关得快，是因为「收」不需要被看清，拖久了像卡住；
- 打开时 opacity 走 120ms、位移 / 缩放走 180ms：先看见、再落位；
- 两条曲线都用「起步快、收尾缓」的 ease-out，关闭换成 ease-in（加速离场）；
- `visibility` 的延迟严格等于关闭总时长。以前 opacity 160ms 就结束、visibility
  220ms 才切，中间那 60ms 元素看不见却还在吃事件，鼠标移回来会从中间状态重新过渡、闪一下。
- 已经有一块浮层开着时，挪到相邻图标**不再等那 120ms 的悬停意图确认**（那只防「扫过去
  顺手带开」）。以前连着挪三个图标像卡住了。

实测（rAF 采样，144Hz）：

| 时刻 | opacity | translate | scale |
| --- | --- | --- | --- |
| 0（关） | 0.00 | -10px | 0.980 |
| 18ms | 0.31 | -7.9px | 0.984 |
| 46ms | 0.73 | -4.4px | 0.991 |
| 81ms | 0.94 | -1.9px | 0.996 |
| 123ms | 1.00 | -0.5px | 0.999 |
| 186ms | 1.00 | 0 | 1.000 |

收起时 opacity 125ms 归零、visibility 201ms 切 hidden（120ms 延迟 + 一帧）。

## 修正 · 半顶栏下 UP 主那一行整体低 64px，压在简介卡上（v012）

用户截图：UP 主头像 / 名字 / 粉丝数 / 关注按钮 / 话题标签叠成一团，标题下面空着一大片。

根因是**两个坐标系差了一个顶栏高**。UP 卡一直没搬 DOM，还留在右栏的流里，靠三个数画到左栏：

- `--bili-vb-up-y` = 标题底边 − **左栏**顶边 + 8（卡片在左栏里该画到哪儿）；
- 卡片的 `margin-top` 是 `--bili-vb-up-y`，而 margin 是从**右栏**顶边量的。

窗口态两边都从 64 起算，差 0，所以一直没暴露。半顶栏把左栏上移了 64px、右栏没动 ——
这个差立刻变成 64，卡片整体低 64px（实测 1703×544：标题底 672、卡片顶 734，该是 680），
于是压在简介卡上：名字和粉丝数被简介正文盖住，话题串正好落在关注按钮那一行。

修法：新增 `--bili-vb-half-shift`（= 顶栏高 64 − 上方空隙 10 = 54，由 `measure()` 写，
`measure()` 之外没有第二个写入方），左栏上移和卡片的 `margin-top` 都减它：

```css
.left-container { margin-top: calc(-1 * var(--bili-vb-half-shift, 54px)); }
.up-panel-container { margin: calc(up-y - half-shift) 0 calc(-1 * (up-y - half-shift + up-h)) 0; }
```

两个 margin 一起减同一个数，相加仍然 = −卡片高，右栏的排版一个像素都不动。
`--bili-vb-up-y` 的定义（相对左栏顶边）和 `--bili-vb-up-top`（左栏钉住位置 + up-y）
都没变，`syncUpPin` 一行没改 —— 只有「自然位置」那条换算补上了。

顺带两处观感（同一次改动，用户一起提的）：

- **顶栏左边缘去掉 +8px 的缝和 14px 左下圆弧**，直接贴住视频右边缘（`--bili-vb-left` +
  `--bili-vb-gutter`），和右边栏连成一整块；
- **播放器上方留 10px**：以前左栏上移 64px，播放器第一行像素直接咬在窗口边框上。

验收（1703×544 / 2560×1215 两个尺寸都量过）：`up.top − title.bottom = 8`、
`desc.top − up.bottom = 10`、`顶栏.left === player.right`、`player.top = 10`。

## 修复 · 浮层切换按钮的擦除动效不生效（v019）

现象：v018 把浮层 tab / 收藏夹换成「淡蓝擦除」后，**点下去只是颜色瞬间换位，擦除动效看不见**。

原因不是 CSS，是 DOM 被整块重建：切 tab / 换收藏夹走 `refreshPop()` → `fillPop()` →
`body.innerHTML = html`，旧节点连同「已经长到 100% 的蓝底」一起被删掉，新节点一出生就是
`background-size: 100%`。CSS transition 需要**同一个节点**从 0% 变到 100%，节点换掉就没有「变化」可补间。
（另外接口要几百毫秒，等它回来再变色还会有「点了没反应」的空窗。）

两处修：

- `activateNow()`：点下去的当下就在**现有 DOM** 上切 `is-active`，动画立刻开始，旧的那格同时擦除消失；
- `patchPopList()` + `fillPop(..., soft)`：数据回来时**只替换 `.tb-pop-list`**，头部（tab 条 / 收藏夹栏）
  保持原节点 —— 否则 320ms 的擦除会被提前到来的重渲染拦腰砍断（接口快时只看得见几十毫秒）。
  新 HTML 里没有列表（未登录 / 没有收藏夹这类空态）时自动退回整块替换。

已验证：本地 harness 里对同一节点切类，`background-size` 实测 0% → 26% → 73% → 95% → 100%（约 320ms），
旧节点同步从 100% 收到 0%。

## 修复 · 半顶栏下播放器右侧一条黑边（v020）

现象：开启「视频页半顶栏」后，播放器最右边贴着一条 1px 的黑线（左侧没有，关掉半顶栏就消失）。

根因是**取整**，不是半顶栏的几何：

- 播放器高度写的是 `Math.round(left * 9 / 16)`。1885 宽时正确值是 1060.3125，取整成 1060，
  容器宽高比 1.77830 就和视频的 1920:1080（1.77778）差了一点点；
- B 站的 video 是 `object-fit: contain` —— 比例不匹配时按高度贴合，视频实际只画到 1884.44，
  最右边那 0.56px 露出 `.bpx-player-video-area` 的 `background: #000`；
- 取整误差最大 0.5px 高 → **0.89px 宽**，所以它永远只是一条 1px 的竖线（不是大黑边）。
- 为什么开半顶栏才看见：半顶栏把 `left` 多给 12px，改变了小数部分。四舍五入**进位**时误差
  落在下边，被控制栏的深色渐变盖住；**舍去**时就跑到右边，对着页面白底一眼就看见。

修法：高度不再取整（`left * 9 / 16`），容器宽高比与视频严格一致，`contain` 正好铺满，零黑边。
高度是 0.0625 的整数倍（如 1060.3125px），分数高度在 grid 里没有副作用。

## 修复 · 番剧 / 纪录片等特殊播放页被「播放页优化」改坏（v021）

现象：`/bangumi/play/ss39481`、`/bangumi/play/ep7247352` 这类番剧 / 纪录片 / 影视播放页
整块排版错乱 —— 播放器被撑成窗口算出来的宽度，压过右边的剧集列表。

根因：`isVideoPage()` 当时放行了 `/video/` **和** `/bangumi/play/`，可这两类页面**不是同一套 DOM**：

| | `/video/BVxxx` | `/bangumi/play/*` |
| --- | --- | --- |
| `#mirror-vdcon` | 有 | **没有** |
| `.left-container` / `.right-container` | 有 | **没有** |
| 播放器 | `#playerWrap` 包着 | `#bilibili-player` 直接挂在剧集布局里 |

而 `#playerWrap` / `#bilibili-player` 的尺寸规则（`--bili-vb-left` × 16:9）是**不分页面**的，
root class 一挂上就把播放器按窗口宽度改写。实测同一页：`668×432` → `1099×618`，
播放器直接压过剧集列表；`measure()` 还会照常算出一整套 `--bili-vb-*`，半顶栏的类也跟着挂上。

修法：`isVideoPage()` 只认 `/video/`，`/bangumi/play/*` 一个字节都不碰
（这类页面的排版差异太大：剧集列表 / 分集 / 追番 / 评分卡，没有统一的接管方式）。
验证：同一页摘掉 `bili-elite-video-beta` / `bili-elite-vb-half` 后播放器回到 `668×432`。
