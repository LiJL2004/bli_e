## v019 设置面板左侧分类列可滚动

**现象**：窗口高度不够时（或「界面优化 → 设置面板缩放」拉大），左侧分类列下面几项
（个性设置 / 实验室 / 新版本改动）被面板底边裁掉，**点不到** —— 用户截图里
「个性设置」只剩半行。

**根因是布局，不是点击被拦**：`.panel` 是定高卡片（`height: min(62vh, 92vh/z)`）+
`overflow: hidden`，`.panel-main` 是 `align-items: stretch` 的 flex 行，`.nav` 只是
`flex: 0 0 176px` 的列、**没有滚动**。8 个分类 ≈ 348px，视口矮于 ~700px 时内容区只剩
一百多像素，超出的部分连同 `.nav-item` 一起被 `.panel` 裁掉；被裁掉的区域连命中测试
都进不去（`elementFromPoint` 在那里拿不到按钮），所以是「看得见一半、点不动」。

**改法**（`panel.css` §3 `.nav`，纯 CSS，JS 一行没动）：

```css
.nav {
  min-height: 0;                /* flex 拉伸项默认 min-height:auto，会被内容撑高，overflow 就不生效 */
  overflow-y: auto;
  overscroll-behavior: contain; /* 滚到底不要带动下面的页面 */
  scrollbar-width: thin;        /* 与 .panel-body 同一套（实测同为 11px） */
  scrollbar-color: rgba(60, 60, 67, 0.28) transparent;
}
```

- **不写 `::-webkit-scrollbar`**：Chromium 里一旦写了 `scrollbar-width`，webkit 伪元素的
  width 就被忽略（实测 `.nav` / `.panel-body` 都是 11px）—— 抄一份过去是死代码。
- **不用 `scrollbar-gutter: stable`**：实测它会让分类按钮常驻窄 11px（211→198 @ scale 1.2），
  而面板高度在打开那一刻就定死了、滚动条不会自己忽有忽无，没必要付这个代价。
- 夜间模式补 `.panel.is-night .nav` 的浅色拇指（与 `.panel-body` 一致）。
- 分类名最宽的「新版本改动」只占 ~118px，滚动条占掉 11px 后仍有 47px 余量，不会截断。

**验证**（真实 Chrome 探针，`panel-nav-scroll.cjs` / `panel-nav-tall.cjs`）：

| 窗口 | 分类列 | 结果 |
| --- | --- | --- |
| 1200×520（视口 373） | clientH 114 / scrollH 348 | `scrollTop` 能滚到 234（正好到底）；滚到底后最后一项 rect 落在列内（bottom 251 = 列 bottom 251），命中测试返回 `新版本改动`，点一下正常切页 |
| 1400×900（视口 753） | clientH 350 / scrollH 350 | 不出现滚动条，最后一项照常可点，无一项文字被截断 |

## v002 悬停提示被下面的卡片遮住

**现象**：把鼠标放在某一行标签右边的感叹号上，提示卡朝下弹出，下半截被**下面那张
白卡**切掉，只剩顶部一条（「半隐藏操作浮钮」那颗最明显，因为它下面是整行的
「设置面板缩放」卡）。

**根因是层叠顺序，不是 overflow**：`.setting-block.is-tip` 早就放开 `overflow: visible`
了（提示确实探出了卡片边界）。但 `.setting-block` 是 `position: relative`、`z-index: auto`，
在同一个层叠上下文里，**DOM 靠后的卡片就画在前一张之上** —— 提示探进下一张卡的地盘，
自然被它盖住。

`.hint-tip` 自己的 `z-index: 5` 救不了：它只在**本卡内部**排序，卡与卡之间的顺序由
`.setting-block` 这一层决定（`.item` / `.hint-dot` 也都没有创建层叠上下文）。

**改法**（`panel.css` §6 附近，紧跟 `.setting-block.is-tip` 那三条）：

```css
.setting-block.is-tip:hover,
.setting-block.is-tip:focus-within { z-index: 3; }
```

悬停 / 聚焦时把**整张卡**抬一层。同尺寸、同位置，除了让提示露出来没有任何视觉变化；
平时保持 `auto`，不改变卡片原有的叠放顺序。`:focus-within` 是给键盘用户留的
（感叹号有 `tabindex="0"`，Tab 到它时提示同样会弹）。

**验证**（真实 Chrome，`bsk`）：往 shadow 里注入等效规则
（`.setting-block.is-tip{z-index:3}` + 强制显示提示）前后各截一张 ——
注入前「只收起设置键，返回顶部与刷新始终留在原位」被「设置面板缩放」那张卡切掉下半截，
注入后三张提示卡都完整。注入的样式已移除，没留在页面里。

## v003 4K 播放时不再和播放器抢带宽

**现象**：看 4K 视频时偶尔卡住，关掉扩展就没有。

### 排查（真实 Chrome，用户本机 / 用户网络，`bsk` 驱动）

1. **先证伪最像的那个嫌疑人**：`playBoost`（播放页开启加速）在播放页**一个请求都不发**。
   实测播放页上 `link[rel=prefetch]` 恒为 0，`.bili-video-card a[target="_blank"]` 也是 0
   —— 右栏推荐卡是同页 SPA 跳转（`target` 为空），`prefetchFirstScreen` 和悬停预取都按
   「只认 `_blank`」放行掉了。
2. **半顶栏 + 毛玻璃顶栏压在视频上**（`playerTop=10`、顶栏 64px、`backdrop-filter: blur(8px)`
   + 渐变遮罩）：A/B 各播 8s，关掉模糊前后都是 **481 帧 / 0 丢帧**，不是它。
3. **4K60 稳态 30s**：`longtask` **0 条**、丢帧 **0/1800**、缓冲领先量最低 **31.2s**、
   没有 `waiting` / `stalled`。在这台机器 + 这条链路上，扩展本身**不制造卡顿**。
4. 剩下的唯一可能：**链路余量不够时，扩展在起播阶段插进去的那点请求把缓冲压穿**。
   播放页上扩展唯一会主动发的网络请求就是**评论预加载**（1 个 JSON + 20 个头像），
   而它的时机是 `canplay + 0.4s` —— 4K 起播时 `canplay` 来得很早（只要两帧能播），缓冲却
   还很薄。实测那条链路上一个 7MB 的 4K 分片要 1s 多（p50 1016ms，整段 44 个分片 324MB）。
   「有时」= 链路松时没事，紧的时候那一下就是卡住。

**注意**：第 4 条是推断，不是复现 —— 本机链路够宽，压不出这个场景。所以改法不是「调参数
让它更快」，而是**把这一类竞争从代码里删掉**：以后不管链路多紧，扩展都不会在播放器饿着
的时候往上加请求。

### 改法

只让「预加载 / 预取」在动手前先看播放器状态，播放器与布局一个字节都不动。

- `commentPreload.ts`：新增 `loadVerdict()` —— 没有在播的视频（暂停 / 已结束 / 还没播放器）
  直接放行；在播则要求 `readyState >= 3` **且缓冲领先量达标**（普通 8s，≥2K 的 20s），
  不达标每 500ms 再看一次、最多等到 40s，一直不达标就这次不做。位移期间播放器一旦
  `waiting` / `stalled` 立刻复位（`SHIFT_MAX` 那 4s 不再硬扛）。
  - 为什么是「缓冲领先量」而不是再加一道 `canplay`：`canplay` 只代表「有两帧能播」，
    跟「链路有余量」完全是两件事，4K 起播时前者来得早、后者还很远。
  - `WAIT_BUFFER`（40s）比 `WAIT_APP`（20s）宽一倍：4K 缓冲从薄到厚本来就要十几秒，
    卡在 20s 等于把这个功能在 4K 上直接废掉。
- `hoverPrefetch.ts`：本页在放视频时不做首屏预取；封面预取只在缓冲 ≥10s 时做
  （`POSTER_BUFFER_MIN`）；播放页 / 番剧页直接收工（那里没有列表可预取）；
  `downlink < 5Mbps` 一律不预取（`effectiveType` 在 8Mbps 的链路上照样报 `4g`）。

### 顺带修掉的三处（同一个文件）

- `prefetch()` 改成返回 `boolean`，`prefetchFirstScreen` 只数**真的插进去**的那几张。
  以前上限满了也照样 `done++` —— 「首屏 3 张」会一张都没预取、还把额度算掉。
- 首屏预取套一层 `requestIdleCallback`：`setTimeout` 只代表「时间到了」，不代表「这帧没事干」，
  而它跑在首页水合最忙的那一段。
- `selfUrl()` 按 `location.href` 缓存本页的规范化地址：指针扫过一屏 20 张卡就是 20 次
  `new URL()` + 正则 + 逐个删参数，算的全是同一个值。**按 href 缓存而不是只算一次** ——
  站内 SPA 换页会改 `location.href` 但**不重跑内容脚本**，只算一次从第二个视频开始就全判错。

### 验证

`tsc --noEmit -p tsconfig.check.json` 只剩 1 条既有报错（`topbarOptimize.ts` 的 NodeList）；
产物 315.6KB（+1.2KB）。阈值来自实测：4K 下缓冲领先量 31.2s > 20s，功能照常触发，不会被
这道闸门误伤。真机 4K 复测需要重载扩展后再看一次 —— 这次没法用探针代替（探针内核播不了
H.264，见 `DEVELOPMENT.md`）。

## v001

### 新增 `quickKeys.ts` / `quickKeysConfig.ts` / `pageActions.ts`

三个文件各管一件事，别合并：

| 文件 | 职责 |
| --- | --- |
| `quickKeysConfig.ts` | 两枚键的存储（`bili-elite-quick-keys`，`{ refresh: 'KeyX', backtop: 'KeyZ' }`），与轮盘键（`bili-elite-wheel`）、面板键（`bili-elite-panel-hotkey`）**三份独立** |
| `quickKeys.ts` | 唯一的 `document` 捕获 keydown，命中后调动作 |
| `pageActions.ts` | `refreshPage()` / `scrollToTop()` 的唯一实现，浮钮与快捷键共用 |

存 `KeyboardEvent.code` 而不是 `key`：默认的 X / Z 都是字母键，用 `key` 在中文输入法下
拿到的是小写、Shift 按下是大写，判定会莫名其妙失效。

### 让路规则（少一条就是「莫名其妙帮我刷新了」）

`quickKeys.ts` 的 onKeyDown 依次排除，任何一条命中都**不接管**：

1. `e.defaultPrevented` —— 轮盘（window 捕获）与设置面板（先注册的 document 捕获）已经
   处理过这一下。**这就是 `setupQuickKeys()` 必须排在 `setupSettingsPanel()` 之后的原因**：
   面板的「绑定按键」要先把这一下吃掉，我们靠这个标志让路，而不是靠监听器先后。
2. 带 `ctrl / meta / alt / shift` —— Ctrl+X 是剪切、Ctrl+Z 是撤销、Shift+X 是大写。
3. `isWheelKeyCapturing()` —— 面板里任何一颗胶囊正在等按键。
4. 设置面板开着 —— 面板里的按钮、输入框都要能正常用键盘。
5. `isPlayerFullscreen()` —— 网页全屏 / 全屏时键盘归播放器。**宽屏不算**（它只是把
   播放器拉宽，页面还能滚，Z 在宽屏下仍然有用）。
6. 功能轮盘正开着（`.stage.show`）—— 用户这时在选格子，随手按到 X / Z 不该刷掉页面。
7. 输入框 / contenteditable —— 评论框、搜索框、动态发布框里 x / z 是打字。

### 刷新走哪条路

`refreshPage()`：首页点 B 站自己的 `.flexible-roll-btn.refresh .flexible-roll-btn-inner`
（只重取推荐流、不重载整页），其它页面 `location.reload()`。

**实测：首页刷新后滚动位置会回到顶部** —— 推荐流是整块替换的，换完 B 站自己就把位置
夹回去了（这也是它那个按钮原本的行为）。所以面板文案里不承诺「保留滚动位置」。

`floatingButtons.ts` 的 `onRefresh` 改成调它 —— 原来那段逻辑是内联的，再抄一份到快捷键
里迟早会漂移（「点按钮保滚动、按快捷键却整页重载」）。

### 面板：按键绑定从两个布尔改成一张表

原来是 `listeningKey` / `listeningPanelKey` 两个布尔 + `setListening` / `setPanelListening`
两套几乎一样的代码。这版要加到四颗胶囊（轮盘 / 面板 / 刷新 / 回顶），照原样写就是四份：

```ts
type KeyTarget = 'wheel' | 'panel' | 'refresh' | 'backtop'
const KEY_CAPS: Record<KeyTarget, HTMLButtonElement>     // 四颗胶囊元素
const KEY_SOURCES: Record<KeyTarget, { get, set }>       // 四份配置的读写
let listening: KeyTarget | null                           // 同一时刻只有一颗在等
```

`setListening(target | null)` 一处负责 `is-listening` 类名、胶囊文字、`setWheelKeyCapturing`
标志；`paintKeyCaps()` 负责把四颗刷成当前配置。**新增一颗胶囊只需要往两张表里各加一行。**

撞键处理集中在 `assignKey()`：设成某个已被占用的键时，被占用者拿到这颗键的旧值（**互换**），
四颗键永远不会重复 —— 重复的话排在前面的那个会永远先吃掉按键，另一颗等于失效。

### 开关

`shared/features.ts` 的「快捷功能」组末尾加 `quickRefresh` / `quickBackTop`，**默认开**：
X / Z 在 B 站页面上没有别的用途（播放器用的是 空格 / D / F / M / W）。

设置面板「快捷功能」页多一张卡：两个开关各带一行 `快捷键` 胶囊（`data-under` 挂在自己
那个开关上，关掉时整行变灰，沿用 `applyToggleDeps`）。

### 恢复默认

`restoreDefaults()` 里加 `resetQuickKeys()`（回到 X / Z），并把原来的
`setListening(false) + setPanelListening(false)` 换成 `setListening(null)`。

## v004 实验室「4K 流畅加速」：让 4K 走 HEVC，码率降到 1/2.6

**现象**：部分冷门 4K 稿件在电脑端（**一个插件都不开也**）一路卡缓冲，同一台机器上手机不卡。

**不是 CDN 节点不一样，是编码不一样。** 拿 `BV1M2sL6WE3X` 在真实 Chrome（登录态）
里读 `window.__playinfo__`：

| 流 | m4s 文件 | codec | 码率 |
| --- | --- | --- | --- |
| AVC 4K | `-1-30120.m4s` | `avc1.640034` | **15.99 Mbps** |
| HEVC 4K | `-1-30121.m4s` | `hvc1.1.6.L156.90` | **6.21 Mbps** |

两条流挂的是同一批节点（`upos-sz-mirrorcos` / `upos-sz-estghw`，`backupUrl` 也重
叠），所以「换节点」不是解法。对这两条 URL 各做 4MB 的 Range 测速，单连接都在
~2.4MB/s（≈19Mbps）：**16Mbps 那条几乎没有余量**，网络抖一下就断供；6.2Mbps 那条
有三倍余量。移动端 App 默认 HEVC，这就是「手机不卡、电脑卡」的全部原因。

**根因**：B 站播放器把编码偏好存在 `localStorage.bilibili_player_codec_prefer_type`，
取值来自播放器 bundle 的 `USER_CODEC_PREFER_TYPE`：

```
0 = RECOMMEND（推荐/自动）  1 = HEVC  2 = DISABLE（禁用 HEVC，只剩 AVC）  3 = AV1
```

这台机器上是 `2`，于是 4K 永远只拿得到 AVC 那条 16Mbps 的流。

**改法**（两半，缺一不可）：

- `extension/guard.js` §6 —— MAIN world + `document_start`，把该键写成 `1`。
  必须是 MAIN world 且必须这么早：播放器脚本初始化时就把这个键读走并据此过滤 dash 流。
  写之前把原值记进 `bili-elite-codec-prev`，关掉开关时还回去。
  判据跟 B 站自己（`isBwpHEVCSupported`）保持一致：`MediaSource.isTypeSupported(
  'video/mp4; codecs="hev1.1.6.L120.90"')` 过不了就不写，`sessionStorage.enableHEVCError
  === '1'`（播放器标记「HEVC 播崩过」）也不写 —— 否则只是把「卡缓冲」换成「软解卡帧」。
- `codecBoost.ts` —— 只维护镜像键 `bili-elite-codec`（`chrome.storage` 是异步的，
  MAIN world 连 `chrome.*` 都没有，只能靠 localStorage 传话），用户切换时重载播放页。

**为什么 setup 里不先 `apply()` 一次**：页面刚打开时 config 全是默认值（这一项默认关），
先跑一次就会把 guard.js 刚写好的镜像和编码偏好一起抹掉 —— 和 1.2.0 v006 那个
「首页无限刷新」是同一个坑：**副作用只认 `isUserEdit()`**。

**验证**：把 `codec_prefer_type` 置 `1` 后重载，网络里只剩 `-1-30121.m4s`
（`bw=6206930`），`videoWidth/Height` 仍是 3840×2160；播放 20s 后 `buffered` 领先
72.6s。置回 `2` 的那一轮**没能复现 AVC**：播放器在 `bilibili_player_codec_prefer_reset`
版本号对不上时会把 `2` 自动改回 `0`（bundle 里 `applyHEVCStrategy` 的
`h().then(... setLocalStorage(s, RECOMMEND))`），所以现场状态可能被它自己改掉过 ——
下次再查这个问题先读一遍这三个键的实际值，别信「用户选过 AVC」这个前提。

## v005 实验室「播放节点优选」：AVC 原码率不动，只换更快的节点

**用户的追问**：v004 切 HEVC 是拿画质换带宽（4K 从 16Mbps 掉到 6.2Mbps），
能不能保住 AVC 原码率、只把卡顿解决掉？

**节点确实有差，而且默认那个是最慢的。** 在页面里（不是 curl）对「当前清晰度」的每个
节点发 `Range: 128KB` 的 XHR，连跑三轮、每轮所有节点取**同一段**字节：

| 节点 | 第 1 轮 | 第 2 轮 | 第 3 轮 |
| --- | --- | --- | --- |
| `upos-sz-mirrorhwb` | 63ms | 98ms | 84ms |
| `upos-sz-mirrorhw` | 347ms | 271ms | 240ms |
| `upos-sz-mirrorcos` | 548ms | 433ms | **656ms** ← 播放器默认用的就是它 |

排序三轮一致，`mirrorhwb` 稳定快 6 倍。而 B 站播放器**只用 `baseUrl`**，
`backupUrl` 只在请求失败时兜底 —— 慢不会切。所以「换节点」这条路对 AVC 是成立的：
不动编码、不动清晰度，白捡带宽。

**但要说清楚它救不了什么**：21:00 在同一个链路上用 curl 测，单连接只有 **19 Mbps**
（晚高峰），那时三个节点全被压在 19Mbps 以下 —— 瓶颈在家宽，换节点等于零收益。
这个开关的定位是「节点是瓶颈时有效」，不是「治所有卡顿」。

**实现**（`guard.js` §7，全部在 MAIN world）：

- 20ms 轮询等 `__playinfo__` 出现，按缓存分数**重排 `baseUrl`**，原 baseUrl 推进
  `backupUrl`（一个都不丢）。只重排顺序，播放器自己的失败兜底照旧。
- 测速：对**当前清晰度**的每个节点（上限 4 个）发两次请求 —— 第一次
  `Range: bytes=0-0`（只为把 DNS/TCP/TLS 建起来），第二次取 128KB 计时。
  串行，避免互相抢带宽。
- 分数写 `localStorage['bili-elite-cdn-scores']`，30 分钟有效；**有新鲜分数就不再测**
  （否则每打开一个视频页都白花 0.5MB）。
- 只有「快 40% 以上」才换 —— 单次测速噪声很大，阈值松了会来回跳。
- 起播后 2.5s 才测，不在最吃带宽的那几秒插一脚。

**踩过的三个坑（都改在代码里了）**：

1. **`defineProperty` 拦 `__playinfo__` 拦不住**：B 站自己又 `defineProperty` 了一次，
   实测最后 `getOwnPropertyDescriptor` 是数据属性。改成 20ms 轮询 —— 播放器读到它
   至少是内联赋值之后几百毫秒，轮询赶得上。
2. **同一段字节反复测会命中浏览器 HTTP 缓存**：三个节点全变成 7~8ms，测了等于没测。
   改成每轮随机换一段。
3. **随机取到 8GB 深处测的是「回源冷数据」**：三个节点在 156/660/1338ms 之间乱跳，
   和播放体验对不上。改成只在**文件开头 8MB 内**随机（那才是起播真正读的地方）。

**验证**：在真实页面上把 §7 单独注入跑通 —— 标记 `data-blie-cdn="on"`、分数写入
localStorage、`__playinfo__` 里两条 4K 流的 `baseUrl` 都从 `mirrorcos`/`mirrorhw`
换成 `mirrorhwb`、`backupUrl` 保留原节点；换完之后播放正常（4K 画面、进度正常走）。

**没验证到的**：`document_start` 那一步的时序（需要重新加载扩展才能测，见下）。

**关于内容脚本缓存**：改 `extension/guard.js` 之后**必须去 chrome://extensions 点一次
「重新加载」**，Chrome 不会自动重读（这次加了 `data-blie-ver` 标记实测确认：
同一个文件里新增的 `setAttribute` 没生效，而老的 `data-blie-pic` 还在）。
`index.global.js` 那次看起来「不 reload 也生效」，是因为当时用户刚好自己点过重载。

## v006 实验室 ·「播放节点优选」下面加一个节点测速工具

v005 的测速是**自动、静默**的：用户只看到开关，看不到测了什么、当前用的是哪个节点，
也没法自己指定。这一版把它摊开：

```
节点测速
  AVC 4K 节点                        [开始测速]
  ┌─────────────────────────────────────────┐
  │ mirrorhwb                      84ms  ✓生效中 │
  │ mirrorhw                      240ms        │
  │ mirrorcos                     656ms        │
  └─────────────────────────────────────────┘
  已生效：mirrorhwb · 刚测过
```

**点一行 = 手动指定这个节点**（再点最上面那行「自动」回到用测速结果）。
手动指定优先于分数，且**不做 40% 门槛** —— 那是用户自己的选择，不该被算法否掉。

**「生效中」就是验证结果**：`guard.js` 把节点写进 `baseUrl` 之后会记一条
`bili-elite-cdn-applied`（哪个清晰度、哪个 codecid、最终用的是哪个 host），
面板拿它和用户指定的 host 比 —— 对得上才算真生效，对不上就明说
「已保存，刷新播放页后生效（当前还是 xxx）」。**不拿「点了按钮」当成功。**

**为什么测速不在面板这一侧跑**：两个硬约束。

1. CDN 是 `*.bilivideo.com`，扩展 host 权限只有 `*.bilibili.com`，
   内容脚本发 XHR 会被 CORS 挡掉；
2. `__playinfo__` 在页面世界，内容脚本读不到（隔离世界）。

所以「开始测速」只是 `document.dispatchEvent(new CustomEvent('bili-elite-cdn-probe'))`
—— DOM 事件跨世界可见 —— 由 guard.js 那边执行，结果写进 localStorage，面板 400ms 轮询一次
（最多 15s）刷新。**这条通道是这次唯一新增的跨世界接口**，只传一个空事件，不传数据。

**测速口径改了**：v005 测「当前清晰度」的两条编码，v006 只测 **AVC、清晰度最高的那条**
（`codecid === 7`，取 `id` 最大的）。用户要的就是「AVC 原码率不损失」，
拿 HEVC 的节点套到 AVC 上没有意义。没有 AVC 的稿件（少数只转码了 HEVC/AV1）退回最高清晰度那条。

**顺手修的两个坑**：

- `paintCdnCard()` 在 `syncUI()` 里被调用，而它依赖的几个 `const` 元素在 50 行之后才声明 ——
  首次 `syncUI()` 发生在 1681 行（元素已就位），所以没有 TDZ 问题，但注释里写清楚了这个顺序依赖。
- 测速期间按钮文案变「测速中…」并禁用，靠 `readCdnState()` 的 `running` 判断，
  15s 后自动作废（万一 guard.js 那边没写回 done，按钮不会永远卡住）。

## v007 节点优先级表 + 「当前节点」显示（回答「能不能点开视频那一瞬间测速」）

**先回答：不能，也不该。** 点开视频那一刻我们手里只有 BV 号 —— 没有签名过的分片地址
（那要 playurl + wbi 签名 + cid，等于把播放器开局要做的事再做一遍）；真测一轮是
2 个节点 ×（1 字节预热 + 128KB），实测 **0.3~1.2s、约 0.5MB**。放在导航前就是给
「打开视频」直接加半秒 —— 正好是用户要避免的事。

**所以改成「先查表、后台校准」**：

- `bili-elite-cdn-rank` = `{ host: 毫秒 }`，**没有 TTL**，每次测速用 EMA（老 0.6 / 新 0.4）
  更新。节点主机是固定的那一批（mirrorcos / mirrorhw / mirrorhwb / estghw…），
  所以一个视频测出来的结果对下一个视频直接有效。
- 优先级：**手动指定 > 本次测速分数（30 分钟）> 长期表 > B 站默认 baseUrl**。
  后两档都过「比当前快 40% 才换」的门槛。
- 查表是同步的、零延迟 —— 播放器读到 `__playinfo__` 之前就已经改好了。

**为什么不内置一张写死的「好节点表」**：节点快慢跟地区、运营商强相关。我们在这台机器
测出来 `mirrorhwb` 最快（84ms）、`mirrorcos` 最慢（656ms），换个人换个省很可能反过来。
把某台机器的排序塞成默认值，对别人就是负优化。所以表从空开始，看两个视频就学出来了。

**新增「当前节点」**：卡片第一行，显示这一页实际在用的节点（`applied.host`）。
- 只在 `/video/` 页面显示，其它页面留空（用户要求）；
- 靠 `applied.page === location.pathname` 判断记录是不是「这一页的」——
  站内路由换了视频、pathname 变了，就自动留空，不会显示上一个视频的残留；
- **开关关着也显示**：§7 现在无条件安装，关着时只记录不改流、不测速、不花流量，
  这时它显示的就是「B 站默认给了哪个」，正好可以拿来对照。

## v008 节点表（可展开 / 可重测）+ 策略门控 + 切视频识别

### 1. 小字贴边

`.cdn-note` 之前没有内边距，说明文字顶到卡片左边线上（用户截图）。补 `padding: 0 10px`，
和上面每一行文字左对齐。

### 2. 「节点表」：可展开、按延迟排、延迟蓝色

原来是隐式的 `bili-elite-cdn-rank`，现在摊开成一张表：

- 点「节点表 → 查看」展开，**按延迟升序**，左边节点名、右边延迟（蓝色，和上面测速结果的
  灰数字区分开）；
- 只读，不可点（能点的是上面那张「测速结果」——那里的节点一定在当前流的候选里）；
- 计数写进状态行（`节点表 N 个`）。

**顺手清掉一类脏数据**：B 站 playinfo 里混着 P2P 主机（`*.mcdn.bilivideo.cn:8082`、
`*.edge.mountaintoys.cn`），那些测出来不是「节点快慢」而是「打洞成没成功」——
实测有一条 44835ms、一条 5ms，放进表里既没意义又难看。加了 `isCdnHost()`：
只认 `*.bilivideo.com` / `*.akamaized.net`，测速收集、重测收集、写表、读表四处都过一遍，
老数据也会在下次写表时被清掉。

### 3. 重测全部节点（2~6 次，默认 3）

表里的节点不一定在当前 playinfo 里（换过视频），所以**拿当前流的一条签名地址换主机**去测
—— 签名与主机无关（实测换 host 仍 206），这是唯一能测「表里老节点」的办法。

每个节点：先 `Range: 0-0` 建连接，再取 N 次 128KB 求平均（失败的那几次不计入分母）。
串行，进度写进 `STATE.done / total`，面板显示「重测进度 3/14」。次数存
`bili-elite-cdn-retest-times`。

### 4. 站内切视频后「当前节点」不更新

**根因**：SPA 换视频时 `__playinfo__` **不会更新**（B 站走 XHR 重新拉 playurl），
而「当前节点」原来只从 playinfo 推。改成**直接看实际发出去的分片请求**：
在 `XMLHttpRequest.prototype.open` 上挂一个钩子，认出视频分片（`-1-30xxx.m4s`，
排除 `30216/30232/30280` 三个音频码）就记下主机，连 `page` 一起写进 `applied`。

**踩到的坑**：自己的测速请求也会走这个钩子，所以用一个 `probing` 计数跳过。第一版只在
`onerror/ontimeout` 里减计数 —— **切视频 / 换清晰度会把在飞的请求 abort 掉，而 abort
只触发 `onabort` 不触发 `onerror`**，计数永远减不回去，之后所有真实分片都被当成
「自己的测速请求」跳过，「当前节点」就再也不更新了。改成 `onloadend`（load / error /
abort / timeout 都会触发）才彻底解决。

### 5. 策略门控：AVC 才优选

- 判据与 B 站一致：`bilibili_player_codec_prefer_type` 为 `1`(HEVC) / `3`(AV1) 时算「非 AVC」；
- **非 AVC 时**：不自动挑节点（改了也用不上）、**不写节点表**；测速与手动指定照旧；
- 面板状态行会明说「当前播放策略不是 AVC，节点优选已暂停（测速与手动切换仍可用，但不写入节点表）」。
- 「AVC 4K 节点」改名为「节点测速」—— 它现在按当前清晰度测，不再专指 4K。

## v009 修：单节点不能测速 / 节点表溢出与滑块消失 / 切视频后列表不换

### 1. 只有一个节点时点测速没反应

`probe()` 原来卡 `names.length < 2` 就直接 `state: 'one-host'` 收工。有些稿件 B 站只给
一个 CDN，于是永远测不了。改成 `!names.length` 才放弃；结果判定也从 `n >= 2` 放宽到 `n >= 1`。
实测：单节点流 → `state: done, n: 1`，`scores` 里一条 174ms。

### 2. 节点表偏右 / 滑块消失

两个都是 CSS 的锅：

- **偏右**：`.cdn-row` 是 `width: 100%` + 左右 10px 内边距。测速结果那几行是 `<button>`，
  Chrome 的 UA 样式给按钮自带 `box-sizing: border-box`，所以没事；**节点表的行是 `<div>`**，
  content-box 下等于 100% + 20px → 整行比卡片宽 20px，看着就是「偏右、顶出卡片」。
  给 `.cdn-row` 补 `box-sizing: border-box`。
- **滑块消失**：直接写了 `<input class="range">`。`.range` 的拇指尺寸用的是
  `var(--range-thumb)` / `var(--range-rim)`，这两个变量**定义在 `.range-wrap` 上** ——
  没有那层包裹，`width: var(--range-thumb)` 是无效值 → 拇指宽度 0；轨道也是
  `.range-wrap::before/::after` 画的，同样没有。包一层 `.range-wrap`（`.cdn-times__wrap`，
  108px），并在初始化 / 拖动时调 `updateRangeFill()` 刷 `--pf` 填充。

实测（真机，面板打开状态下量）：`rowW === rowParentW`（644.14 / 644.14，不再溢出）、
`--range-thumb` 解析成 `16px`、滑块圆点可见。

### 3. 站内切视频后测速列表还是旧视频的节点

`bili-elite-cdn-scores` 是「上一次测速」的结果，换视频后它还挂在列表上。
现在列表按可信度三级取：

1. **这一页刚测过的分数**（`scores.page === location.pathname`）→ 灰数字；
2. 否则用 **`bili-elite-cdn-hosts`**：guard.js 在 `XMLHttpRequest.prototype.open` 上认出
   `x/player/.../playurl`，`load` 时解析响应，把「AVC 最高清晰度」那条流的 baseUrl +
   backupUrl 按主机收进 localStorage（带 `page`）。**SPA 切视频时 `__playinfo__` 不会更新，
   这是唯一能拿到新视频节点列表的地方。** 数值取长期表 → 蓝色；
3. 都没有 → 「还没测过」。

`probe()` / `retestAll()` 也改成走 `currentTarget()`（优先这份 hosts，退回 playinfo），
所以切完视频点「开始测速」测的是**新视频**的节点。

## v010 修：「当前节点」不在「节点测速」列表里（跨标签页串数据）

用户截图：当前节点 `x5zz10k.edge.mountaintoys.cn`，列表里只有 `estgoss 115ms`，
两个完全对不上。用户自己猜「是不是多个视频页互相串了」—— **猜对了一半**。

### 1. 真正的两个原因

**原因 A：localStorage 是全站共享的。** `scores` / `hosts` / `applied` / `state` 这四个键
写的是「这一页」的临时状态，但存在 localStorage 里 —— 开两个播放页时后写的盖掉前一个，
面板读到的就是**另一个视频**的节点列表。

**原因 B：P2P 主机被过滤掉了。** dash 里除了 CDN 镜像还混着 P2P 主机
（`*.mcdn.bilivideo.cn:8082`、`*.edge.mountaintoys.cn`），v008 为了不让「44835ms」这种
脏数据进长期表，在**收集节点时**就把它们过滤了 —— 于是播放器真的在用 P2P 节点时，
「当前节点」有值、列表里却没有它。

### 2. 改法

**每页的键搬到 sessionStorage**（每标签页独立、刷新仍在、新标签页从空开始）：

| 键 | 存哪 | 为什么 |
| --- | --- | --- |
| `-hosts` `-scores` `-applied` `-probe-state` | **sessionStorage** | 只对「这一页」有意义 |
| `-rank` `-force` `-retest-times` | localStorage | 长期表 / 手动指定 / 偏好，本来就该跨页 |

老版本写在 localStorage 的同名键在 guard.js 安装时删掉，避免两套数据并存。

**列表改成三个来源取并集**（少一个就会漏）：

1. `-hosts`：这条流的全部节点 —— 首屏从 `__playinfo__` 写一份，
   站内切视频后由 playurl 响应覆盖；
2. 本页刚测过的分数；
3. **实际在用的那个节点**（P2P 不一定在 dash 列表里，但播放器真的在用）。

**收集节点时不再过滤 P2P**（过滤只保留在「长期表」和「重测」上）：
P2P 主机名是按文件生成的（`x5zz10k.…`），换视频就换一批，进表永远用不上；
但列表要的是「当前视频的全部节点」，必须包含它。

### 3. 顺手补的两处

- **首屏没有 playurl 请求**，所以 `-hosts` 原来是空的，列表只剩「当前节点」一个 ——
  现在首屏也从 `__playinfo__` 写一份（有 playurl 记录就不覆盖）。
- **面板开着时站内切视频**不重载页面，「当前节点」会一直是旧值 ——
  guard.js 记完节点会派 `bili-elite-cdn-applied` DOM 事件，面板收到就重画。
- 面板读分数也加了 30 分钟有效期，与 guard.js 的 TTL 对齐（过期数值不该再当「刚测过」）。

## v011 删「4K 流畅加速」/ 节点表改弹窗 / 节点优选的开销与缓存 / 搜索框清空后空白

### 1. 删掉「4K 流畅加速」

它是拿画质换带宽：HEVC 4K 只有 6.2Mbps，而 AVC 4K 是 16Mbps。v005 的「播放节点优选」
已经能在**不动编码**的前提下解决同一件事（节点是瓶颈时白捡带宽），留着这个开关只会让人选错。

**收尾**（`guard.js` §6 只保留还原逻辑）：老版本改过 B 站自己的
`bilibili_player_codec_prefer_type`，原值存在 `bili-elite-codec-prev`。功能删了但键还在 ——
不还回去用户就永远停在 HEVC，而面板里再没有开关能改回来。现在只要发现 `-prev` 存在，
就把原值写回去、清掉三个键；没改过（没有 `-prev`）就什么都不碰。

### 2. 「播放节点优选」到底占多少资源

| 项 | 数字 |
| --- | --- |
| 一次测速的流量 | 每个节点 1 字节（建连接）+ 128KB（计时）；4K AVC 一般是 3 个节点 → **约 384KB** |
| 一次测速的耗时 | 串行，每个请求 60~700ms（看节点）→ **0.3~1.5s 墙钟**，不阻塞任何东西 |
| 重排 baseUrl | 纯内存、同步，**0 网络请求、0ms** |
| 打开视频变慢了吗 | 没有。它只改 `__playinfo__` 里 `baseUrl` 的顺序，播放器该什么时候开始还是什么时候 |

**但有两个真问题，这一版都改了：**

1. **缓存堆积**。B 站的分片响应带很长的 max-age，XHR 会把每次探测的 206 片段
   **写进 HTTP 磁盘缓存** —— 每测一个视频就多两三份 128KB「永远用不到」的条目，
   还挤掉真正有用的封面 / 脚本。改成 `fetch(..., { cache: 'no-store' })`：
   既不读缓存也不写缓存，顺带解决「同一段字节反复测会命中缓存」那个老坑。
   （fetch 的 then 在响应头到达时就 resolve，所以必须 `arrayBuffer()` 读完再计时，
   否则量到的是 TTFB 而不是传输时间。）
2. **跟起播抢带宽**。原来固定 2.5s 后开测，正好落在播放器刚开始缓冲的那几秒。
   现在等 `buffered ahead ≥ 6s`（最多等 10s）再测；隐藏标签页里直接不测
   （定时器被节流，测出来也没意义）。

**再加一条「不用测就不测」**：这条流的节点全都已经在表里 → 完全不发请求（零流量）。
这也是「打开视频不变慢」的关键 —— 表是同步查的，查得到就直接用。
想刷新数字就点「开始测速」或「重测全部节点」。

### 3. 节点表：任何播放策略都能开，改成独立弹窗

- 「节点表」从卡片里内联展开改成**独立弹窗**（和「恢复默认」那个确认弹窗同一套材质与开合手感，
  420px 宽、左对齐、表体自己滚），弹窗里放管理功能：**重测次数（2~6，默认 3）**、
  **重测全部节点**、**清空节点表**（两步确认，防误触）。
- **不再受播放策略与开关影响**：表是长期数据，跟这一页用什么编码无关。
  非 AVC 时只在弹窗顶部写一句「新测速不会写入这张表」。
- 「重测全部节点」也不再跟着开关变灰 —— 它只受「正在测」限制。

### 4. 搜索框：删空文字后热搜 / 历史不显示

`renderSuggest('')` 原来只切 `hidden`，内容靠「上一次」留在 DOM 里。只要这个页面打开时
输入框里本来就有字（**搜索页会回填关键词**），首次打开面板走的是联想分支 ——
历史从没渲染过、热搜也从没请求过，于是删空文字后只剩两个空标题（用户截图）。

统一走新的 `renderDefaultPanel()`：历史重画、热搜按需拉。

## v012 节点表延迟只取最新一次测速（不再与历次结果加权）

节点表原来用 EMA（老 0.6 / 新 0.4）更新，节点变快或变慢都要好几轮才反映得出来 ——
用户看到的数字总是落后于实际。现在 `guard.js` 的 `bumpRank()` 直接用**本轮测得的数值覆盖**：
单次测速就是这一轮的读数，重测本身就是 N 次取平均，所以表里显示的就是「最近一次测到的延迟」。
「节点表」弹窗顶部那行说明同步改成「最近一次测速的读数（重测取多次平均）」。

## v013 节点测速只在播放页可用

节点测速原来在**任何页面**都点得动。首页上 `__playinfo__` 还留着上一个视频的对象（站内切回
首页时 `window` 不会重建），所以「开始测速」真的会去测旧视频的节点、写进长期表 ——
既花流量，数字也不是当前页面的。

- `guard.js` 新增 `isPlayPage()`：`/video/`、`/bangumi/play/`、`/medialist/play/`、
  `/cheese/play/`、`/list/`（稍后再看 / 收藏夹播放）。`probe()` / `retestAll()` /
  自动测速排队 / 首屏 `applyPick()` 全部先过这一道；不在播放页直接 `no-stream` 收工。
- 设置面板同一份判定（`cdnBoost.ts` 的 `isCdnPlayPage()`）：「开始测速」「重测」置灰，
  列表写「当前不是播放页 —— 打开视频后才能测速」，状态行也明说已停用。
  节点表仍可「查看 / 清空」，手动指定仍可改回自动。
- 顺带把「点一行手动指定后自动刷新」的判定从 `/video/` 扩到同一份播放页判定，
  番剧 / 合集 / 稍后再看也能立刻重载生效。

## v014 修：测速测出更快的节点，但当前播放不切过去

用户截图：列表 `mirrorhwb 60ms` / `mirrorhw 144ms` / `mirrorcos 185ms`，
「生效中」却挂在最慢的 `mirrorcos` 上。

**根因不是选错，是「选完之后没有再选一次」**：

1. `applyPick()` 只在**页面加载时**跑一次，那时只有长期表（旧数据，cos 当时最快）；
2. 「开始测速」/后台自动测速写完 `scores`、`bumpRank()` 之后，
   **没有任何地方再把新结果应用到当前这条播放**；
3. `__playinfo__` 是播放器启动时读走的，事后改它也不会影响已经在播的流 ——
   所以只能刷新页面才生效，用户看到的就是「明明 hwb 更快却不换」。

**改法：在分片请求这一层再选一次（`rewriteMediaUrl()`）**。

- `XMLHttpRequest.prototype.open` / `fetch` 上，对 `/upgcxcode/` 的视频分片
  （`-1-<qn>.m4s`，排除音频 30216/30232/30280）现算一次 `preferredHostFor(url)`
  再 `swapHost()`；签名与主机无关（v005 实测过换 host 仍 206）。
- 优先级与 `applyPick()` 一致：手动指定 > 本页分数（30 分钟）> 长期表；
  自动只在 AVC 下启用，40% 门槛照旧；**只换真 CDN 镜像**，P2P 主机名是按文件
  生成的，换过去必 404（`scores` 里 P2P 的数值仍参与 40% 比较，只是不作为目标）。
- 这样「开始测速」一结束，当前播放的**下一段**就换到更快的节点，面板
  「生效中」也会跟着移到那一行；站内切视频后新 playurl 拉的地址同样走这道，
  不再只认首屏那份 `__playinfo__`（v013 里提到的那个缺口一并补上）。
- 顺序很重要：先换 URL 再 `noteMedia()`，否则「生效中」还是会记成 B 站默认节点。

## v015 非播放页不再列节点 / P2P 不再触发自动测速

### 1. 非播放页「节点测速」下面不该有节点

v013 只把按钮置灰，列表还是照常构建。可有些页面（动态详情、活动页等）也能内嵌播放器，
`sessionStorage` 里会留下「这一页」的 `hosts` / `applied`，于是卡片下面冒出一排
和当前页面无关的节点（用户截图：首页/非播放页却列着 `mirrorhw 115ms 生效中` 等）。
现在 `paintCdnCard()` 在非播放页**直接清空列表并返回**，状态行只保留
「当前不是播放页，测速与重测已停用 · 节点表 N 个」；节点表弹窗仍可查看/清空。

### 2. P2P 主机不再被当成「没测过的节点」

`hasUnknownHost()` 原来遍历这条流的**全部**节点，而 P2P 主机名是按文件生成的
（`x5zz10k.edge.mountaintoys.cn`），永远不会写进长期表 → 这个判断永远为真，
每个新开的播放页都会白测一轮（~384KB），和「表齐了就不测」的设计相反。
现在只统计真 CDN 镜像（`isCdnHost`）；纯 P2P 的流不再自动测速，手动「开始测速」照旧。

## v016 重测在任何页面可用 / 节点表「清空」改成「节点管理」

### 1. 「重测全部节点」不再要求当前页是播放页

v013 把测速和重测一起锁在播放页，理由是「重测要拿当前流的签名地址换主机」。
但签名地址只跟它自己的 `deadline` 有关、**跟页面无关**（换 host 仍 206），页面只是
「去哪儿拿地址」而已。所以现在把最后见到的一条视频分片地址存进
`localStorage` 的 `bili-elite-cdn-retest-ref`（`guard.js` 在真实分片请求、
`capturePlayurl` / `capturePlayinfo` 三处都会刷新它），重测时按
「本页 / 本标签页 hosts → 首屏 playinfo → 这份存档」的顺序取，取到且 `deadline`
没过期（留 1 分钟余量）就测。

- `guard.js` 的 `retestAll()` 不再看 `isPlayPage()`；节点表里「重测全部节点」的「开始」
  不再按页面置灰，点击时也不再检查 `cdnBoost` 开关（重测本来就是独立工具）。
- 非播放页没有 guard 的自动测速，面板改用轮询定时器判断「测速中…」（否则按钮会一直显示「开始」）。
- 真的没有任何可用地址时仍写 `no-stream`，面板会提示「先随便打开一个视频播一下」。
- 「开始测速」保持原样：它测的是**当前这条流**，仍然只在播放页可用。

### 2. 「清空节点表」改成「节点管理」

- 行标题改为「节点管理」，右侧按钮是「管理」；点一下按钮变「取消」，按钮左边出现红色「删除」。
- 管理态下节点行可点：选中的行红框 + 浅红底，节点名加删除线（可多选）；再点一下取消选中。
- 点「删除」把选中的节点从长期表移除（`cdnBoost.ts` 的 `removeCdnRankHosts()`），
  随后自动退出管理态；点「取消」只退出、不动数据。删空后连 `localStorage` 键一起清掉。
- 关弹窗（✕ / 点遮罩 / Esc）也会退出管理态，下次打开不会残留红框。
- 删除按钮在没有选中时是禁用的；夜间模式单独配了红色与强调色。

## v017 面板卡片级联默认开启 / 确认恢复默认不动节点表

### 1. 「面板卡片级联」默认开启

- `src/shared/features.ts` 里 `panelCascade` 的 `default` 从 `false` 改成 `true`，标签右边
  挂上感叹号说明「设置卡片淡入淡出效果」。
- **只改默认值，不做强制迁移**：配置快照里已经存着 `panelCascade` 的老用户保持自己的值；
  本次没有写 epoch、没有 `writeSync`。
- README 个性设置的默认值表同步改成「开」。

### 2. 版本升级 / 改默认值对已有设置的影响（备忘）

- `config.ts` 的 `applyValues()` 只覆盖存储快照里**存在**的 key；`paramStore` 的
  `applyValues()` 同样只在存储里有该字段时才覆盖。所以改 `default` 不会改写已保存的值。
- 但 `persist()` 写的是**整包**：开关写整份 config、参数写整组 defs。于是用户只要改过
  任意一项，他**所有**开关 / 该组参数都会在那一刻被固化下来 —— 之后再改 `default`
  对这个人不再生效。从没存过设置的用户（首次安装、从没动过）才跟着新默认值走。
- 要把某项**强制**写进所有用户的存储：用 `storage.ts` 的 `writeSync()` + 一个 epoch
  记号（`snapshot` 只有首次 `get(null)` 那次会给），参考 `panelScaleConfig.ts` /
  `wheelGlassConfig.ts`。本次按用户要求**没有**这么做。

### 3. 复查：恢复默认设置不删节点表

- `restoreDefaults()` 只做两件事：`persist(DEFAULT_CONFIG)` + 各 `*Config` 的
  `reset*()`；没有任何 `bili-elite-cdn-rank` / `clearCdnRank` 调用。节点表是跨视频累积的
  测速数据，不属于「设置」，恢复默认后仍然保留。
- 顺手删掉已无入口的 `clearCdnRank()`（v016 起「清空节点表」已改成「节点管理」），
  并在 `restoreDefaults()` / `removeCdnRankHosts()` 的注释里写明这条约束，防止以后被接回去。
