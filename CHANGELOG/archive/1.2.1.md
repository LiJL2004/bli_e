## 修正 · 顶栏左右边距跟页面内容对齐（v001）

**现象**：首页 / 搜索页 / 播放页上，自绘顶栏的 logo 比第一列卡片多缩进一截，右侧那颗
「历史」又比卡片右边缘往里收一截 —— 同一条竖线上，顶栏和内容各走各的。

**根因**：顶栏的 `padding` 写死 24px（`selfTopbar.css` §1，那是照 B 站原生顶栏量的内边距），
而三种页面的内容区左右留白早在 1.2.0 v005 就统一成了 `--bili-edge`（10px）：

| 页面 | 内容区左留白 | 顶栏左内边距 |
| --- | --- | --- |
| 首页 `main.bili-feed4-layout` | 10（`--bili-home-gutter`） | 24 |
| 搜索页 `.search-layout .i_wrapper` | 10（`--bili-search-gutter`） | 24 |
| 播放页 `#mirror-vdcon` | 10（`EDGE`） | 24 |

差的那 14px 就是「顶栏比内容缩进一格」。

**修法**：这三种页面顶栏的左右内边距直接取 `var(--bili-edge, 10px)`，别的地方（动态 /
消息 …）内容边距本来就不是 10，保持 24px 不动。

页面判定用 `location` 挂一个 root 类（`bili-elite-tb-edge`，`selfTopbar.ts` 的 `isEdgePage()`），
**不用 `:has(main.bili-feed4-layout)`**：边距首帧就得是对的，而 `:has()` 要等 feed 节点
出现才匹配 —— 那一下顶栏会从 24 横跳到 10，比一直不对齐还难看。`location` 在
document_start 就是最终值。

实测（1600×900，构建产物）：首页顶栏 `padding: 10px/10px`、logo 左 10、右侧图标区右
1573 = `clientWidth − 10`，与信息流栅格的左右边缘逐像素对齐；搜索页 `.i_wrapper`
`padding: 0 10px`，同样对齐。

半顶栏（`selfTopbar.css` §8）有自己的一套内边距（左 16 / 右 12，贴着视频右边缘），
规则写在文件末尾、优先级相同 → 后写的赢，不受这条影响。

## 修复 · 搜索页右侧的两根滚动条（v001）

**现象**：搜索结果页右侧并排两根竖向滚动条 —— 外侧一根粗的（页面），内侧一根细的，
两根各自都能拖。

**根因**：`html.bili-elite-home-only { overflow-y: scroll }`（1.2.0 v008 为首页首帧防横移
加的，见 `homeOptimize.css`）跟着 `bili-elite-home-only` 走，而那个类**全站都挂**。
B 站搜索页的 `body` 自己就是滚动容器（`overflow-y: scroll`，`body.clientHeight` 恒等于
视口高），于是搜索页变成：

- `html` 一条（我们加的，`overflow-y: scroll` 强制常驻）；
- `body` 一条（B 站自己的）。

两条并排，内侧那条还把内容挤窄了 17px。

**修法**：滚动条常驻只在**首页**需要，单独拆一个 root 类 `bili-elite-home-scroll`
（`topbarOptimize.ts`），只有「首页 + 首页优化开着」才挂。判定同样走 `location`
（`isHomePage()`），首帧就位。

实测（1600×900，构建产物）：

| | 修复前 | 修复后 |
| --- | --- | --- |
| 搜索页 `html` 的 `overflow-y` | `scroll` | `visible` |
| 搜索页滚动条数量 | 2 | 1（`body` 那条，落在视口最右边） |
| 首页 `html` 的 `overflow-y` | `scroll` | `scroll`（首帧防横移不变） |

## 修正 · 非半顶栏时播放器和顶栏之间的白缝（v001）

**现象**：关掉「播放页半顶栏」后，播放器上边缘和顶栏下沿之间空着 10px 白条，像顶栏
没贴住画面。

**根因**：1.2.0 的「统一白边」把 `#mirror-vdcon` 的 `padding-top` 固定成 10px
（`--bili-vb-top-gap`），两种模式都留。半顶栏时左栏上移 64px，这 10px 是给窗口边缘的
呼吸；但非半顶栏时顶栏还实打实占着上方那 64px，再留 10px 就成了一条缝。

**修法**：`--bili-vb-top-gap` 按半顶栏状态写（`videoBeta.ts` 的 `measure()`）：半顶栏
`10px`、非半顶栏 `0px`。左栏 sticky 的上限（`leftPinTop()`）跟着改用同一个数 ——
非半顶栏时是「顶栏高 + 0」，钉住那一刻播放器顶部也贴着顶栏，不会滚一下就多出 10px。

实测（1600×900，BV1GJ411x7h7）：

| | 半顶栏 | 非半顶栏 |
| --- | --- | --- |
| `--bili-vb-top-gap` | 10px | 0px |
| `#mirror-vdcon` 的 padding | `10px 10px 0px` | `0px 10px` |
| 播放器上边缘 | 10 | **64**（= 顶栏下沿） |

## 修改 · logo / 「首页」在本页打开首页（v001）

**现象**：点顶栏左上角的 logo 或「首页」，右边会多开一个首页标签 —— 从播放页「回家」
之后，原来那个还在播的标签页留在那儿。

**修法**：这两个链接去掉 `target="_blank"`，改走 `onHomeClick()`（`selfTopbar.ts`）：

- 本页不是首页 → `location.href = '//www.bilibili.com/'`（本页导航）；
- 本页就是首页（`/` 或 `/index.html`）→ `location.reload()`；
- 带修饰键（Ctrl / Cmd / Shift / Alt）时**不拦**，交给浏览器 —— 那是用户明确要新开标签。

顶栏其余导航（动态 / 消息 / 收藏 / 历史 / 头像 / 投稿）仍然是 `target="_blank"`
（1.2.0 v012 的要求，不打断当前页）。

实测（探针 + 构建产物）：搜索页点 logo → `https://www.bilibili.com/`，标签数 1 → 1；
首页点 logo / 「首页」→ 页面重载（标记变量消失）；播放页（全顶栏）点 logo → 首页，
标签数 1 → 1；Ctrl+点击 → 新开一个标签，当前页不动。

## 修复 · 大窗口下简介「展开更多」是多余的（v003）

**现象**：大屏上简介正文只有两三行，收起态就已经把全文露出来了，可左下角还挂着「展开更多」；
点它（变成「收起」）卡片反而矮一截 —— 用户看到的「点开却收起了一些」。小窗口下一切正常。

**根因**：B 站只在简介数据到的那一下判一次要不要折叠（`checkIfDescInfoCanBeFolded`），
折叠高度写进行内 `height`（3.5 × 行高）。之后窗口变宽，正文从 4 行缩到 2 行，
那个 px 还是旧的 —— 收起态装得下全文，按钮就成了摆设，点开等于把 3.5 行的框缩回 2 行。

**修法**：判定权收回来，但**不动 B 站的折叠机制**（`videoBeta.ts` 的 `needDescFit`）：

- 判据只读两个跟结论无关的量：折叠高度（B 站行内 px；展开态退回 3.5 行）+ `scrollHeight`。
  **不能拿 `clientHeight` 比** —— 我们自己会把行内高度放开，比出来永远是「装得下」，缩窗口就收不回去。
- 装得下 → 挂 `bili-elite-vb-desc-fit`：CSS 把行内 `height` 放开、`.toggle-btn` 藏掉，
  同时不挂 `bili-elite-vb-desc-folded`（不再有指针 / 悬停高亮，点卡片没反应）。
- 装不下 → 什么都不做，仍是 B 站那套（收起态 + 展开更多）。
- 没有按钮却留着行内 px（B 站量的时候窗口还没定下来）→ 也放开，否则正文被永久裁掉又没法展开。
- 宽屏 / 网页全屏（沉浸式）整块交回 B 站，一条规则都不挂。

**性能**：`scrollHeight` 是强制排版，而这条路径被叫得很勤（播放量每秒都在变）。所以加了两道闸：
`ResizeObserver` 盯 `#v_desc` 的尺寸（窗口宽度、栅格变化都会改它），外加一把「形状」缓存
（节点代数 / 行内高度 / 按钮在不在 / 文字长度 / 是否沉浸式）—— 形状没变就直接用上次结论，
一个布局都不读。RO 回调甩到下一帧再写类，避免 `ResizeObserver loop` 警告。

**实测**（探针 2200×1000，造 214 字单段简介、行内 `height: 91px`）：`fit` 生效，卡片 136px、
正文 3 行全部可见、按钮 `display:none`；缩到 1200 后 `fit` 撤销。真实 7 行简介在 2200 下
仍判「装不下」，按钮照旧显示 —— 大窗口不该折叠的只有真的装得下的那些。

## 修复 · 数字藏品头像的 UP 主，控件上下空隙比正常头像大（v004）

**现象**：用了「数字藏品头像」的 UP 主，头像那一行的上下空隙明显比普通 UP 主大一圈 ——
头像上下各空出一截，简介卡被整体推下去，卡片比正常的高 32px（用户截图：
UP 主「飞行雪绒」的稿件 `BV1Udxz6tEdr`）。

**根因**：B 站给这类头像的容器加了 `is-nft`（`.up-avatar-wrap.is-nft`），CSS 把 wrap 撑到
**80×80**，可头像本身只有 54：`.bili-avatar` 行内 `54.24px` + `translate(-3.12px,-3.12px)`
（= 48 × 1.13，放大后居中），`.up-avatar` 47×47，右下角再挂一枚 27.5% 的 `nft-label.gif`
（`.bili-avatar-nft-icon`）。**画出来 54、占位 80** —— 多出的 26px 全是死空间，
比「头像框（挂件）」那种更冤：空隙更大，头像本身还更小。

**修法**：和挂件那条并成一条规则（`videoBeta.css` §6）—— `.up-avatar-wrap` 不管带
`.has-pendant` 还是 `.is-nft`，wrap / `.up-avatar` / `.bili-avatar` 三层一律按无装饰的原样
钉回 48（行内 style 只能 `!important` 压）。位移一起归零（挂件 `+3.6px`、NFT `-3.12px`）。
挂件图（72×72）整张藏掉；**NFT 那枚小角标留着** —— 它是百分比尺寸，跟着缩到 13px，
本来就是 B 站全站通用的「数字藏品」标记，藏掉等于抹掉信息。**不删节点**：
`.has-pendant` / `.is-nft` 都是 Vue 的 class，摘 DOM 会踩它的 patch。

`--bili-vb-up-h` 是实时量的（`layoutUp`），卡片瘦回 48 之后左栏第 3 行占位、
简介卡位置、sticky top 全部自动跟着走，不需要另改 JS。

**实测**（探针 1600×900）：`BV1Udxz6tEdr`（数字藏品头像）与 `BV1Qgn96oEUz`（普通头像）
`--bili-vb-up-h` 都是 48、卡片顶边都在 630、wrap 和头像都是 48×48 —— 逐像素一致；
改动前数字藏品那篇是 wrap 80 / 头像 54 / 卡片 80 高。

## 调整 · 顶栏搜索在新标签页打开搜索结果（v005）

**需求**：在自绘顶栏的搜索框里搜完，搜索结果**在新标签页打开**，原来那页留着。

**为什么**：搜索页不是「当前这页的下一页」。用户在播放页 / 首页搜完，还要回到刚才那篇稿子、
那个列表接着看 —— 本页跳走等于把位置丢了（顶栏的 logo / 首页是唯一「本页打开」的入口，
其余导航项本来就是新标签页，这次把搜索也对齐）。

**修法**：`selfTopbar.ts` 的 `go()` 改成 `window.open(url, '_blank')`。
四条路（回车提交 / 点联想行 / 点热搜 / 点历史）本来就都走 `go()`，一处改完全覆盖。
不用 `window.open(url, '_blank', 'noopener')`：带 noopener 时规范规定返回 `null`，
就没法判断「是不是被弹窗拦截了」—— 拦了要退回本页跳转，否则用户看到的是「点了没反应」。
所以先不带 noopener 拿句柄，拿到再把 `opener` 掐掉（效果等价于 noopener，且跨源写不上时
静默跳过），拿不到才 `location.href` 兜底。触发点全是用户手势（submit / keydown / click），
不会被弹窗拦截。

**实测**（探针 1500×900，扩展加载）：首页按回车搜「卡提希娅」→ 页面数 1 → 2，
新标签是 `search.bilibili.com/all?keyword=...`，原标签仍是 `www.bilibili.com/`；
再点一条联想行 → 3 个标签，原标签依旧没动。

## 新增 · 播放页优化 → 评论预加载（v006）

**需求**：播放页的评论预先加载一部分，但**不能拖慢视频打开**。

**为什么评论区本来要等**：B 站的评论区是 `<bili-comments>`（lit 写的 web component），
元素上带 `lazy-load="true"`，组件内部拿 IntersectionObserver 观察自己，**1px 进入视口
才发第一页请求**。实测（探针，1600×900）：

| 时间 | 发生了什么 |
| --- | --- |
| 3.4s | `<bili-comments>` 已经挂进 `#commentapp`，shadow root 里只有一圈 spinner |
| 12.6s（滚到评论区） | 才发出 `/x/v2/reply/wbi/main`，`#commentapp` 高度 154 → 722 |

**为什么不能替它发请求**：那个接口的响应头是 `Cache-Control: no-cache`（实测），我们取
回来的那份进不了任何缓存，B 站组件也不会认 —— 白花流量。preconnect / prefetch 同理。

**做法**：让它**真的进入一次视口**。首帧就绪之后，把 `#commentapp` 整块
`translateY` 到视口顶部、`opacity: 0` 掉（`videoBeta.css` §13），它自己的 IO 就判定
「可见」，第一页开始下载；区块长高（= 数据回来了）立刻复位，全程用户看不到任何东西。

为什么用 transform 而不是 `position: fixed`：它是 `.left-container` 栅格里的一格，
transform **不改布局** —— 页面高度、滚动条、其它块的位置一个像素都不动；fixed 会让这一格
塌陷（未加载时 154px），复位时又长回来，滚动条要抖两下。

**「不影响视频打开速度」靠四条**（`commentPreload.ts`）：

1. 只在**首帧就绪之后**动手：`canplay` 捕获阶段（不冒泡，播放器又是异步挂上来的，只能
   捕获）+ 0.4s。首帧已经拿到，视频不再和首屏抢那几帧带宽。`playing` 只是补一刀 ——
   浏览器从缓存起播时 `canplay` 会一闪而过，两个谁先到都行。
2. 页面 `load` + 2s 兜底：自动播放被拦时不会有 `canplay`，但首屏这时已经画完。
3. 6s 硬兜底：用户暂停着看简介 / 视频一直没就绪 —— 这时视频根本没在下东西。
4. 省流量 / 2g 网络不做（判据与 `hoverPrefetch.ts` 一致）；页面在后台不做，切回前台再来。

**为什么不再早一点**（`loadedmetadata` / `DOMContentLoaded`）：那会儿视频正在下首帧数据，
评论请求（第一页 JSON + 20 条评论的头像）插进去就是实打实地抢首屏带宽 —— 用户要的是
「评论早点好」，不是「视频晚点开」。

三个来源（`canplay` / `load` / 硬兜底）用同一个排期函数，**只允许提前、不允许推迟**。
不能「先到先排」：`load` 通常比 `canplay` 先到，先到就排 2s 的话，后面 `canplay` 说的
「0.4s 就行」会被守卫挡掉，反而更晚。

另外两道保险：位移最长保持 4s（到点无条件复位，宁可这次没加载完）；位移期间用户自己
滚动超过 24px 也立刻复位，不会让他看到评论区挂在视口顶上。评论区已经加载过、或者已经
在视口里（B 站自己会加载）时一律不插手。

**实测**（探针 1600×900，构建产物，不滚动）：

| 时间 | 状态 |
| --- | --- |
| 5.0s | 挂上 `bili-elite-vb-cp`，`--bili-vb-cp-shift: -772px`，`#commentapp` 顶边 780 → 8 |
| 5.2s | `reply/main` 发出（位移与请求几乎同时） |
| 5.4s | `#commentapp` 154 → 722、shadow root 出现 `bili-comments-header-renderer`，类与变量已摘掉 |
| 全程 | `document.scrollHeight` 3099 不变，`scrollY` 0 不变 |

也就是从「位移」到「评论就绪」约 330ms，而用户滚下去时这一页已经在手里了。开关关掉时
一个字节都不动（同一套探针：`#commentapp` 停在 154、无根类、无请求）。

> v006 首版是「起播 + 1.5s / 12s 兜底」，实测偏晚（探针里 12.9s 才动手）。v007 改成
> 上面这套，同一条探针路径提前到 5.0s；真实环境走 `canplay` 那条会更早。
> 探针播不了 H.264、`<video>` 元素根本不存在，所以测的是 `load + 2s` 这条中间档。

开关挂在「界面优化 → 播放页优化」那张卡里（`features.ts` 的 `under: 'videoBeta'`），
默认开；播放页优化关掉时整行变灰、CSS 也整段失效。

## 调整 · 顶栏左侧「首页 / 动态」也有悬停衬底（v007）

**需求**：左侧「首页」「动态」要有和右侧图标一样的灰色悬停衬底。

**原来**：右侧 `.tb-icon` 是 50×43、8px 圆角，悬停时 `rgba(0, 0, 0, 0.04)` + 文字变蓝；
左侧 `.tb-entry > a` 是 `height: 100%`（整条 64px），悬停只变文字颜色 —— 直接给它加背景
会变成一根贯穿顶栏的长条，和右边那几颗小方块完全不是一回事。

收到 2px —— 间距改由 `padding` 出（10 + 2 + 10 = 22px），gap 还留 15 的话两段文字会被
推成 35px。夜间模式（`night.css`）同步补上 `rgba(255, 255, 255, 0.08)`，与右侧图标一致。

**实测**（探针 1600×900，构建产物）：

| | 高 | 宽 | 圆角 | 悬停底色 |
| --- | --- | --- | --- | --- |
| 首页 | 43 | 63 | 8px | `rgba(0,0,0,0.04)` |
| 动态 | 43 | 48 | 8px | `rgba(0,0,0,0.04)` |
| 右侧图标 | 43 | 50 | 8px | `rgba(0,0,0,0.04)` |

## 修正 · 广告屏蔽改为「认骨架」而不是「认名字」（v010）

**现象**：搜索页第一屏又出现广告 —— 一张封面是「豆包深度检查」的卡，长得和普通结果卡一模一样。

**根因**：旧规则全是按「广告叫什么」写的 —— `.video-page-operator-card-small`（运营推荐小卡）、
`a[href*="playrecommendByOp"]`（推广链接参数）。B 站一旦把广告做成**普通卡片的样式**
插进信息流，这些名字一个都不命中。

**做法**：换成认「广告才有的骨架」。一张广告卡和普通卡的区别全在**底部那行统计**里：

| | 普通卡 | 广告卡 |
| --- | --- | --- |
| 统计行 | `[播放] 2.7万 [弹幕] 264` | `[广告] 4000+人感兴趣` |

于是三条互相独立的特征（任意命中即广告）：

1. `.bili-video-card__stats--ad` —— 那枚「广告」标本身；
2. `.ad-feedback-entry` —— 「反馈 / 撤销」的广告反馈入口；
3. `a[href*="cm.bilibili.com"]` —— 广告曝光 / 点击上报（`cm` = 商业广告），
   普通视频链接只会指向 `/video/BV…`。

**实测（2026-11-07）**：

| 页面 | 广告卡 | 命中 | 说明 |
| --- | --- | --- | --- |
| 搜索 · 视频 | 3 | 3 | 三条特征全中（每卡 3 个 cm 上报） |
| 搜索 · 综合 | 3 | 3 | 同上 |
| 首页信息流 | 6 | 6 | **只有 cm 链接** —— 没有「广告」标、没有反馈入口（魔兽世界 / LibTV / 千问 / 豆包），所以第 3 条不能省 |
| 播放页右栏 | — | — | 走原来的 `.ad-report` / `.video-pod-above-modules` |

**顺带修掉「摘卡留洞」**：卡片外面还包着一层栅格壳（搜索页 `.video-list > *`、首页
`.bili-feed-card`），只摘卡片的话栅格不重排，第一屏就是一个空格。现在连壳一起摘，
后面的卡片自动补位 —— 实测首页 4 列每行 4 张、搜索页第三格被摘掉后第四张直接顶上来。

**试过但否掉的特征**：`data-loc-id`。首页 11 个命中里 0 个是广告卡（普通活动横幅也带这个
属性），拿它当判据会误伤。

课程卡（带「课程」标、指向课堂）不摘 —— 那是 B 站自己的付费内容，不是广告位。

## 新增 · 网络预热：DNS / 握手提前做，以及「记住视频 CDN 主机」（v011）

**需求**：加快首页 / 播放页的打开速度。思路是「App 快，是因为它在后台提前把 DNS 解析和
连接握手做完了，插件能不能照做」。

**先量了首屏请求时间线**（真实 Chrome 157、1600×900、登录态）：

| 页面 | 首次出现时间 |
| --- | --- |
| 首页 | `s1.hdslb.com` 541ms → `i0.hdslb.com` 542ms → `api.bilibili.com` 684ms → `passport` 985 → `api.live` 1281 → `api.vc` 1711 |
| 播放页 | `s1` 550 → `i0` 591 → `cn-lndl-ct-01-01.bilivideo.com` 810 → `api` 855 → `interface` 1853 → `passport` 2140 |

两类域名要分开看：`s1` / `i0` 是 HTML 里就写着的标签，浏览器的 preload scanner 在字节到达
的同一刻就开连了，我们再 preconnect 只会排在它后面 —— **这两个一个字节都不发**（也不做
dns-prefetch，那是同一份查询再做一遍）。值得管的只有 `api.bilibili.com` 和视频 CDN：它们
不在 HTML 里，是 B 站脚本跑起来之后才发出的第一条请求。

**做法**（`netHints.ts`，设置面板「界面优化 → 网络预热」）：

1. 每个页面 `preconnect` 一个 `api.bilibili.com` —— 首页 17 条 / 播放页 23 条请求全在这
   一个 origin 上，一条连接就够；
2. 播放页再 `preconnect` **上次实际用到的视频 CDN 主机**。这个主机名是按地区 + 运营商分配
   的（本机是 `cn-lndl-ct-01-01.bilivideo.com`），写死一份列表没有意义，所以自己记：起播后
   用 `PerformanceObserver` 认出 `*.bilivideo.com` 的主机、存进 `storage.local`，下次打开
   播放页直接预热。换网络 / 换地区后第一次会打偏，代价只是多开一条没人用的连接；
3. 其余 1~2 秒后才用到的域名只做 `dns-prefetch`：只发一个 DNS 查询，不占连接。

不带 `crossorigin`：B 站的 XHR 全是 `withCredentials`，不带 crossorigin 建的正是
credentials include 那一档，而 include 档的连接可以服务 omit 档的请求、反过来不行。

**实测（这一条必须写清楚：省不到多少）**

chromium 123 探针，冷 profile，播放页，同一份产物只切「注入 / 不注入」各 5 轮，用 CDP 的
`Network.responseReceived.timing` 判连接复用（判据先用「同主机连发三张图片」校准过，
第 2、3 次确实是 `connectStart = -1`）：

| | 第一条 api 请求 connect/TLS | 复用 |
| --- | --- | --- |
| 不注入 | 12/46 16/50 1/34 3/36 1/36 | 0/5 |
| 注入 preconnect | 1/34 1/36 1/33 12/45 0/34 | 0/5 |

Chromium 确实处理了这条提示（`<link>` 处理完会从 DOM 里消失），但那条连接没有交到页面
自己的请求手上 —— TLS 那 30~50ms 一分没省。换挂载位置（`<head>` / `<html>` / load 之后再插）、
带不带 `crossorigin`、走不走代理，全都不复用；只有换成 `preload as=fetch`（真发一条请求）
才偶尔出现 `connectStart = -1`，但那要多打一条 `nav` 接口，30ms 不值这个代价。
DNS 那半段在本机也量不出来：每次跑之前 `Clear-DnsClientCache`，`dnsStart == dnsEnd`（0ms）
—— 本机走代理，DNS 由代理缓存。

**所以这一版落地的是「代价为零」的那部分**：`dns-prefetch` 与 CDN 主机记忆保留，preconnect
按标准写法留着（换 Chrome 版本 / 换机器可能就生效，失效时只是多一条闲置连接），面板里的
说明写「下次打开页面生效」。**没有**拿它当卖点 —— 「点开就出来」这件事在 1.2.1 之前就已经
由 `hoverPrefetch`（`rel=prefetch as=document`，实测 TTFB 380ms → 1ms）做掉了，这一层
只是把「冷启动那一次」的 DNS / 握手尽量摊平。

**什么时候有感**：只在冷启动（刚开浏览器 / 隔了很久 / 刚换网络）那一次；暖会话里 Chrome
的连接池本来就会留几分钟，开了也感觉不到。开关默认开，因为它最坏情况只是多一条闲置连接。

**真实 Chrome 157 里的验证**（本机、重载扩展之后）

`<html>` 上留了一条 `data-blie-net`，记录这一页到底预热了哪些域名 —— 因为 Chrome 处理完
一条 preconnect 会把 `<link>` 从 DOM 里摘掉，光看 DOM 分不清「注入成功」和「压根没注入」，
播放页那条异步读 storage 之后才发的提示最容易让人怀疑没生效。实测拿到：

    首页    p:api.bilibili.com d:passport.bilibili.com d:api.live.bilibili.com
            d:api.vc.bilibili.com d:message.bilibili.com d:interface.bilibili.com
    播放页  p:api.bilibili.com d:（同上 5 条）
            p:cn-lndl-ct-01-03.bilivideo.com p:upos-sz-mirrorcoso1.bilivideo.com

播放页那两台是**上一次播放时记下来的**（`storage.local` 的 `bili-elite-vcdn`，日志里陆续写过
`upos-sz-mirrorbd` / `upos-sz-mirrorcos` / `upos-sz-estgcos` / `cn-lndl-ct-01-03`），
说明「认 CDN 主机 → 下次预热」这条链路是通的。

**但要如实说**：B 站每次 playurl 分配的 CDN 主机在 `upos-sz-mirror*` 和
`cn-<地区>-<运营商>-<n>-<n>` 之间来回换，记住的两台未必是下一次用的那两台 —— 命中率大概一半，
打偏的代价只是多一条闲置连接。真实 Chrome 里首条 `nav` 请求的 timing 是
`connectStart = dnsStart = sslStart = -1`（全复用），但那个会话本来就有别的 B 站标签页开着、
连接早在池子里了，不能算到预热头上 —— 真正干净的对照还是上面那张 chromium 123 的表。

## 新增 · 实验室「CDN 优化」+ 网络预热的两个隐患（v012）

### 一、上一版（v011 网络预热）复查出来的两个问题

**① `data-blie-net` 一条一写。** 那一串标记原来在 `addHint()` 里逐条写进 `<html>` 的
`data-blie-net` —— 给 `<html>` 写属性会让整棵树样式失效，一页 6~7 条提示就是 6~7 次全量
重算（本仓库 1.2.0 踩过一次：3293 个元素 10.5ms/次）。改成攒到微任务里只写一次。

**② B 站站内跳转之后就不再学习了。** 原来是「起播后固定 8 秒写一次，`flushed = true`
锁死」。但 B 站换视频是 SPA，文档不重新加载、`setupNetHints()` 不会重跑 —— 第二个视频
用到的 CDN 主机永远记不下来；反过来，用户看两秒就关掉时那一次写又根本不会发生。
改成「发现一台新主机 → 3 秒防抖写一次」，SPA 换视频自然产生新主机、自然再写；
主机集合本身只有 1~2 台，写盘次数仍然是个位数。

顺带把 `PerformanceObserver` 的重复代码抽成 `cdnSegments.ts`（`netHints` 与
`cdnOptimize` 共用一份），并去掉了「找到两台就 disconnect」—— 那个断连正是 ② 的一半原因。

### 二、实验室新增「CDN 优化」（默认关）

**它解决的是哪一段**：B 站 playurl 只给一台 primary，其余塞在 `backupUrl` 里「出错才换」，
所以默认情况下你会一直用分给你的那台 —— 好不好全看运气。实测同一个 m4s 的 path + query，
只换主机名（curl 带 Range，同一时刻）：

| 主机 | 首字节 |
| --- | --- |
| `cn-lndl-ct-01-03` | 44ms |
| `cn-lndl-ct-01-01` | 212ms |
| `upos-sz-mirrorbd` | 230ms |
| `upos-sz-estgcos` | 275ms |
| `upos-sz-mirrorcos` | 375ms |

**差 3~8 倍**。而且 `*.bilivideo.com` 之间**互相接受对方的 path + query**（签名不绑主机，
全部 206），响应头也一致（`Access-Control-Allow-Origin: https://www.bilibili.com`）——
所以换节点对播放器是完全透明的。反例：`upos-hz-mirrorakam.akamaized.net` 换过去直接 403
（akamai 的签名绑自己），所以候选名单只在这个域内取。

**做法**（`modules/cdnOptimize.ts` + `background/cdnOptimize.ts` + `shared/cdnScore.ts`）：

1. 播放页起播后 4 秒，拿当前分片的 path + query、只换主机名，向「当前这台 + 分数表里
   已有的 + 4 台常用镜像」各取 32KB，量首字节时间；
2. 分数表存 `storage.local`（EWMA，7 天过期），后台读它挑出最快的一台；
3. 后台用 `declarativeNetRequest` 装一条动态规则把 `*.bilivideo.com` 的分片重定向过去，
   `excludedRequestDomains` 排除最优那台自己（否则等于让它重定向到自己）；
4. 开关关掉 → 规则立刻删掉。

**两个必须踩过才知道的坑**：

- **不能并行探**。并行时几条请求抢同一条带宽，测出来全是被平均的数 —— 实测 5 台全落在
  146~147ms，节点差异被抹平。串行才拉得开（12 / 28 / 62 / 120）。
- **不能只探一轮**。播放器正在用的那台连接是热的（TCP + TLS 早建好了），其余是冷的，
  光握手就要 100~150ms —— 第一轮比出来永远是「当前这台最快」（实测 12ms 对其余 146~442ms），
  那这个功能就永远不会切。现在先每台取 1 个字节把连接建起来（顺带缓存 CORS 预检），
  第二轮才是公平比较。

**实测（chromium 123 探针，同一份产物、只切开关）**：

| 项目 | 结果 |
| --- | --- |
| 探测结果（串行两轮） | `cn-lndl-ct-01-01:12ms mirrorhw:28ms mirrorbd:62ms mirrorcos:120ms` |
| 装上的规则 | `^https://[a-z0-9-]+\.bilivideo\.com/(.*)` → `https://<最快>/\1` |
| 重定向是否真生效 | 请求 `upos-sz-mirrorcos` 的地址 → `status=206`、`final=cn-lndl-ct-01-01`、body 可读 1024B |
| 开关关 / 再开 | 规则条数 1 → 0 → 1 |

**代价与边界**：每支视频探测一次，4 台 × 32KB + 4 个 1 字节预热（约 128KB），在起播后
4 秒做、串行约 1 秒；只优化**首字节延迟**（选近的节点），不保证吞吐 —— 播放中的真实速度
量不了（`*.bilivideo.com` 不带 `Timing-Allow-Origin`，跨域 `transferSize` 全是 0）。
默认关：它要动网络层，属于「想清楚再开」的东西。

**权限**：`declarativeNetRequest` + `*://*.bilivideo.com/*`。开关关着时规则不存在，
这条 host 权限一个请求都不会碰。

### 三、真实 Chrome 157 里跑通（本机、重载扩展之后）

面板「实验室」里出现「CDN 优化」（`1.2.1 v012`），打开后到播放页，`<html data-blie-cdn>`
上留下这一次的探测结果：

    data-blie-cdn="cn-hljheb-ct-01-03:23ms upos-sz-estgoss:23ms cn-lndl-ct-01-02:25ms upos-sz-mirrorbd:25ms"

四台都在 23~25ms，`pickBest` 要求「最快比第二快至少快 25%」才切 —— 所以这里**正确地不切**：
B 站这次分给这台机器的节点本来就够快。分数表（`storage.local` 的 `bili-elite-cdn-score`）
同步写进了真实数据，说明「探测 → 打分 → 交给后台」这条链路在 Chrome 157 上是通的。

顺带一个观察：同一台机器两次打开，CDN 主机在 `cn-lndl-ct-01-0x`（辽宁）和
`cn-hljheb-ct-01-0x`（哈尔滨）之间换过 —— 又一次说明「记住上次那台」命中率有限，
而「每次重新测」才是对的做法。

**收窄了一处风险**：规则原来匹配 `^https://[a-z0-9-]+\.bilivideo\.com/(.*)`，会把**直播**
分片（同域下的 `live-bvc/…`）也导到点播节点上，大概率 403。现在只认点播的
`upgcxcode/` 路径前缀，直播、封面图这些一概不碰。

## 撤销 · 「CDN 优化」整项删除（v013）

v012 加的那个实验室功能（探节点 + `declarativeNetRequest` 重定向）**实测是负提升**，整项撤掉：

- `modules/cdnOptimize.ts`、`background/cdnOptimize.ts`、`shared/cdnScore.ts`、`modules/cdnSegments.ts`
  全部移进 `_bli_e_trash/2026-11-08-cdnopt/`；
- `features.ts` 删掉 `cdnOptimize`，`manifest` 收回 `declarativeNetRequest` 与
  `*://*.bilivideo.com/*`（权限回到只剩 `storage` + `*.bilibili.com`）；
- 已装上的动态规则会随权限一起被浏览器回收，`storage.local` 里那张分数表最多 400 字节，无害。

为什么负：探测本身要多花 4 台 × 32KB、起播后 4 秒抢一次带宽，而它换来的只是「首字节快一点」；
更关键的是**大多数时候它判断「不用切」**（B 站分给你的那台往往已经是最快的），
于是纯粹变成白付成本。分数表还观察到同一台机器在辽宁 / 哈尔滨节点之间来回换，
「记住上次那台」的命中率也不高。结论：这条路不值得，删。

## 修复 · 悬停预取其实从来没命中过（v013）

**这是「有些视频打开很快、有些很慢」的真正原因。**

**现象**：`hoverPrefetch` 从 1.1.x 起就在跑，模块注释里还写着「TTFB 380ms → 1ms」。但那个
数字是**探针里直接导航到预取地址**测出来的，不是真实点击路径。

**根因**：预取的是 `a.href` 原样，而点下去落到的根本不是这个地址：

| | 预取地址 | 真实落到的地址 |
| --- | --- | --- |
| 首页卡片 | `/video/BVxxx` | `/video/BVxxx/?spm_id_from=333.1007.tianma.1-1-1.click`，而且 `/video/BVxxx` 还会 **301** 到带斜杠的版本 |
| 播放页右栏 | `/video/BVxxx/?…&trackid=….1794115275060.512` | 同上，`trackid` 里是**时间戳**，每次刷新都变 |

prefetch 缓存是**按完整 URL 精确匹配**的，所以一次都命中不了。实测（chromium 123，同一张卡）：

    直接点    TTFB 1287ms / 427ms    重定向 1 次
    悬停 700ms 再点  TTFB 475ms / 544ms   重定向 1 次   ← 和直接点没区别

**修法**（`hoverPrefetch.ts`）：预取和点击都走同一个 `canonicalVideoUrl()` ——
去掉埋点参数（`spm_id_from` / `vd_source` / `trackid` / `from` / `share_*` / `timestamp` …）、

就在捕获阶段接管、直接导航过去（`stopPropagation` 拦掉 B 站自己拼埋点的那一次跳转）；
没预取过就完全放行，行为一点不变。

## 修复 · 卡片整体化后，播放页点白区会甩出新标签页（v013）

## 修复 · 点播放页右栏视频有「响应延迟」（v014，v013 引入的回归）

**现象**：v013 之后点播放页右栏的视频，要等一下才切过去。

**根因**：B 站**播放页右栏是 SPA 跳转** —— 点下去 `location.href` 变了，文档并不重载。
v013 的点击接管把它变成了 `location.assign()`，等于把「瞬时的前端路由切换」换成一次
整页加载（重新拉 HTML、重新解析、重新初始化播放器），这就是那一下延迟。

**怎么确认的**：在页面里打一个 `window.__mark`，点完再读 ——

| | 点完 `__mark` | 说明 |
| --- | --- | --- |
| 无扩展·封面 | `alive` | B 站自己走 SPA |
| v013·封面（悬停→接管） | `(整页加载)` | 我们把它改成了整页加载 |
| v014·封面 | `alive` | 恢复 SPA |

**修法**（两处）：

1. `hoverPrefetch.ts`：判据收紧成**只处理 `target="_blank"` 的视频链接**。首页 / 搜索页的
   卡片就是这种（新标签页打开 → 必然整页加载 → 预取真的省 TTFB）；播放页右栏的链接
   没有 target（同页 SPA）→ 我们完全不碰，预取和点击接管都不做。
2. `cardWholeClick.ts`：白区点击不再自己 `location.assign()`，改成 **`anchor.click()`
   把这一下转给卡片自己的链接** —— SPA 路由、`target` 语义、B 站自己的埋点全按原样走，
   我们只负责把白区变成可点。这也正是「和点封面 / 标题一样」的字面意思。
   `target="_blank"` 的卡仍然直接 `window.open` 到预取过的规范化地址。

顺带省掉一块**白烧的流量**：SPA 不拉 HTML，所以在播放页预取右栏那 3 张卡本来就没用。
现在首屏预取只挑 `_blank` 的链接，播放页一页少约 200KB 无用请求。

**实测（v014）**：

| 场景 | 结果 |
| --- | --- |
| 播放页·点封面（悬停过） | SPA，`__mark` 还在，无整页加载 |
| 播放页·点白区 | SPA，同页切到目标视频 |
| 首页·悬停再点 | 新标签页，`redirects=0`，TTFB **11ms** |
| 首页·直接点（首屏预取） | 同上，TTFB **11ms** |
| 搜索页 | 卡片也是 `_blank`，首屏 3 张已预取 |

## 修复 · 卡片整体化：按「灰色衬底」的实际范围判定 + 恢复 SPA 快路径（v018）

**两件事一起修**（前面几版各修对了一半，来回折腾了三次，记在这里免得再踩）：

### 一、可点范围 = 灰色衬底画到哪儿 = 卡片 rect 各边 +6px

那块灰底是**我们自己画的**（`topbar.css` §12）：`background-color` 铺满卡片自己的 rect，
`box-shadow: 0 0 0 var(--bili-card-spread, 6px)` 再把同一块颜色向外扩 6px。所以肉眼看到的
灰底 = **卡片 rect 各边 +6px**。

`elementFromPoint` 只认卡片 rect —— 点在多出来那 6px 里命中的是列表容器（`DIV.rec-list`），
`closest(CARD_SELECTOR)` 匹配不到，于是「灰底明明亮着，点下去没反应」。

修法：`cardAtPoint()` —— 先按命中元素找卡片，找不到再按「rect 各边 +6px」补一次。
**再往外就不是灰底了，那里不响应。**

> 顺带纠正 v016 的错误：那一版把这块当成「卡片之间的缝隙」，按 20px 容差找最近卡片 ——
> 判据应该是「衬底画到哪儿」，不是「离卡片多近」。那段逻辑已整段删掉。

### 二、打开方式必须走 B 站的 SPA 路由（否则就是「点击延迟」）

- v013 / v016 / v017 用 `location.assign()` → 整页加载，重新拉 HTML、重新初始化播放器，
  点下去那一下明显能等出来 —— 用户报的「点击延迟」就是它。
- 正确做法是 `replayAnchorClick(anchor)`：`anchor.click()` 会触发 B 站挂在链接上的 SPA 路由，
  前端切页、不重载文档。

之前把「转手不生效」怪到 `anchor.click()` 头上是误判 —— 真正原因是那 6px 灰底边缘没被算进
可点范围（点在边缘上，我们连卡片都没找到，自然什么都没发生）。两件事一起修才对。

### 实测（chromium 探针，真实鼠标点击）

| 点击位置 | 命中元素 | 在卡片内 | 结果 | 是否 SPA |
| --- | --- | --- | --- | --- |
| 卡片下边缘 **+4px**（灰底边缘） | `DIV.rec-list` | ❌ | 跳到该卡对应的视频 ✅ | **SPA ✅** |
| 再往下（已出灰底） | — | — | 不响应 | — |

`SPA` 的判据：点击前在页面里打 `window.__m = 'alive'`，点完标记还在 = 文档没重载。

**性能**：没有新增监听器、定时器、合成事件（`replayAnchorClick` 只是一次 `anchor.click()`）。
`cardAtPoint()` 只在「点下去且没落在卡片上」时跑一次，遍历当页那 20 个卡片的 rect。

## 修复 · 首页推荐流「概率刷出空洞」（v023）

**现象**：首页信息流偶尔出现一整格空白 —— 位置留着，封面、标题、UP 主全没有，
后面的卡片也不补位。概率出现（刷新几次才撞上一次）。

**根因**：v010 的「认骨架」规则摘的是**内层卡片**，不是栅格那一格。

首页推荐栅格（`.recommended-container_floor-aside .container`）是 `display: grid`，
直接子项是 `.feed-card`，里面才是 `.bili-feed-card` → `.bili-video-card`。v010 的规则 2
写成 `.bili-feed-card:has(…) { display: none }`，只摘到中间那层：

- 规则 1 摘掉 `.bili-video-card`、规则 2 摘掉 `.bili-feed-card` → 内容高度变 0；
- 但 `.feed-card` **仍然是栅格的直接子项**，默认 `align-self: stretch` 会把它撑到
  同行其它卡的行高（实测 299px）—— 格子照样占位，里面全空，就是那个洞。

为什么是「概率」：B 站自己有时会把广告卡的外层藏掉、有时不藏。实测同一个页面 102 个
子项里 30 个被摘掉，只有 1 个漏成洞（外层没被藏的那个）。v010 之前按名字摘
（`.video-page-operator-card-small` 之类）摘的是整卡，不会留壳 —— 所以这个问题是
1.2.1 之后才看得见。

**修法**（`adBlock.css` 规则 2）：判据不变，把作用对象提到**栅格直接子项**：

```css
.recommended-container_floor-aside .container > *:has(:is(…)) { display: none !important; }
```

判据必须与规则 1 逐字一致 —— 内层命中什么，外层就得命中什么，否则又会出现
「内层摘了、外层留下」。`.bili-feed-card` 那条留着（首页之外的场景仍在用）。

**实测**（真实 Chrome 157、登录态、用户首页标签，102 个格子）：

| | 修复前 | 注入新规则后 |
| --- | --- | --- |
| 那个洞的格子 | `display: block`、高 299 | `display: none`、高 0 |
| 命中格数 | — | 13（12 个本来就被藏 + 这 1 个漏的） |
| 可见格子里带 cm 链接的普通卡 | 0 / 72 | 0 / 72（无新增误伤） |
| 残留空洞 | 1 | 0 |

与列数无关（用户截图是两列、实测页是四列，机制一样）。

### 1. 窗口变窄之后简介丢掉「展开更多」（v003 的尾巴）

**现象**：1200 宽加载（正常折叠）→ 拉宽到 2200（`fit` 生效、按钮隐藏）→ 再缩回 1200：
`fit` 撤销了，但「展开更多」**再也不会出现**，简介一直整段展开，直到下一次窗口变化。

**根因**：B 站自己的 resize 处理跑在**我们更新左栏宽度之前**。那一刻栅格还是 2200 的宽度，
正文看起来「装得下」，它就把按钮摘掉、行内 `height` 写成 `auto`；等我们把宽度改小，
它不会再判第二次。`needDescFit` 这边没有按钮也没有行内 px，只能什么都不做。

**修法**（`videoBeta.ts` 的 `scheduleDescRejudge`）：`measure()` 发现**宽度真的变了**、
而且刚才 `descFit` 是 true 时，260ms 后补发一个 `resize` 事件，让 B 站用正确宽度重判一次。
只补一次：dispatch 出来的 resize 会让 `measure()` 再跑，那时宽度没变、不会再排。
`stop()` 里清掉定时器。

**实测**（BV1Xi4z6NEr2，1200 → 2200 → 1200）：缩回后 ~200ms 内按钮回来、行内 84px、
`folded` 重新挂上；再拉宽又回到 `fit`。全程 0 报错。

### 2. 只开「首屏空闲预取」白花每页约 200KB

**现象**：先开「预取命中修复」、再开「首屏空闲预取」，然后把父项关掉 —— 子项在面板里
变灰，但存储里仍是 `true`；`prefetchFirstScreen()` 只判了 `prefetchIdle`，于是照样预取
3 条**规范化**地址。可点击接管（`prefetchExact`）关着，B 站点下去落的还是带
`trackid` / `spm_id_from` 的原地址 —— 这 3 条一次都命中不了。

**修法**（`hoverPrefetch.ts`）：新增 `idlePrefetchOn()` = 两个开关都开；首屏预取和预取
上限（8 / 6）都改用它。父项关掉时行为与 v005 完全一致。

**实测**：`{prefetchIdle:true, prefetchExact:false}` 首页 load 后 `link[rel=prefetch]` 为空；
两个都开仍是 3 条、点击直达规范化地址。

### 3. 播放页右栏悬停仍然预取文档（纯浪费）

**现象**：打开「预取命中修复」后，播放页右栏的推荐卡**没有 `target`**（同页 SPA 切换，
文档不重新加载），但 `onPointerOver` 不区分，悬停 80ms 就 `prefetch as=document` 一次
（每张 ~65KB，上限 6 张）。v014 只把**首屏空闲预取**收窄到 `_blank`，悬停这条路漏了。

**修法**：`prefetchExact` 开着时，同页链接只预取封面（同页换视频时播放器要用那张图），
不再预取文档。关着时保持 v005 原样（那一版本来就没区分）。

**实测**：播放页右栏悬停 → 只有 1 条 `as=image`、0 条 `as=document`；首页悬停仍是
1 条 `as=document` + 1 条 `as=image`，点击直达规范化地址（无 301）。

> 复查里**确认不是 bug** 的两处，记在这里免得以后当问题查：
> ① 评论预加载在站内 SPA 换稿后不会对第二支视频再跑一次（模块是一次性 setup，
> `done` 已经置位）——只是「第二支不预加载」，不影响第一支和页面本身；
> ② 顶栏边距的 `--bili-edge` 与「首页 / 搜索页 / 播放页优化」是解耦的：关掉对应优化后
> 内容区回到 B 站原版留白、顶栏仍是 10px。这是 v001 有意的选择（顶栏是全局导航），
> 不是回归。

## 新增 · 实验室「控制面板新材质」：雷柏网页驱动那套磨砂玻璃（v025）


- 新开关「实验室 → 控制面板新材质」（`panelFrosted`，默认关，`cardBreak` 单独一张卡）；
- `.panel.is-frosted` 直接照抄上面四个值：`background-color:#d9d9d959` /

  不换成 `border-image` —— 渐变 border 在 36px 圆角处会缺一段；

  里面再铺纯白卡等于把玻璃盖回去。这一项原站没有对应物（它的卡里不嵌套卡），是自己定的；
- 确认弹窗同材质（圆角仍 16px）；
- 夜间模式单独一档：`rgba(24,25,29,.55)` / 卡片 `rgba(32,34,38,.55)` —— 35% 的灰白
  铺在深色页面上会发亮发灰；
- 与「高级材质 → 设置面板」（`is-glass`）**互斥**，同时开着时新材质赢（`applyPanelGlass()`
  里先摘 `is-glass`）。两套都写 `backdrop-filter` / `border` / `box-shadow`，靠 CSS 权重

**实测**（真实 Chrome 157，1690×733，注入新样式后 `getComputedStyle`）：

| border-radius | 36px | 同 |

夜间档：面板 `rgba(24,25,29,0.55)`、卡片 `rgba(32,34,38,0.55)`、标签 `#e6e8ec`，规则

1. 这层材质本身很淡 —— 原站那张卡底下是深红战斗场景，35% 灰白 + 80px 模糊才显得「雾」；

## 修复 · 滚轮把搜索面板关掉（v029）

**现象**：点搜索框、搜索面板展开后，滚一下鼠标滚轮面板就收了。

**根因**：`selfTopbar.ts` 的 `onScroll` 里有一条「页面一滚就收面板」的规则 ——
当初的想法是「用户去滚页面了，说明不看面板了」。但面板里的历史区本身就是 172px 的
滚动容器，热搜 / 联想也可能要滚：滚轮一动就触发 `window` 的 scroll，面板当场消失，
等于「想滚列表反而把它关了」。

**修法**（两处）：

1. `onScroll` 不再关搜索面板，只保留「滚走时收悬停浮层」（浮层是鼠标悬出来的，
   页面滚走了本来就该收）。关面板的入口仍然够用：点面板外（`pointerdown` 捕获）、
   Esc、选词之后。
2. 新增 `onPanelWheel`（`panel` 上 non-passive 的 wheel 监听）：从事件目标往上找，
   只要有容器「还能朝这个方向滚」就放行，交给浏览器自己滚；一层都滚不动才
   `preventDefault()` —— 否则滚轮会顺着滚动链把页面滚走，面板钉在顶栏下不动、
   内容却在跳，看着像面板卡住了。

`unbind()` 里同步摘掉这个监听。

**实测**（探针 1400×900，`chrome.storage.sync` 清空）：

| 场景 | 面板 | 页面 scrollY |
| --- | --- | --- |
| 点搜索框 | 打开 | 0 |
| 鼠标在面板上滚轮 | **仍然打开** | 0（被拦住，不带动页面） |
| 鼠标在页面内容上滚轮 | 仍然打开 | 500 |
| 点面板外 | 关闭 | 500 |
| 面板内放一个 80px 可滚容器再滚 | 仍然打开 | 0（滚的是那个容器，`scrollTop` 200） |

控制台无报错。`whatsNew.ts` 的「修复」节补了第一条，打包已重出。
