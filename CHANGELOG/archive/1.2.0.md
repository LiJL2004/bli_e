# 1.2.0

> 小版本：先把首页控制台那条 `Cannot read properties of undefined (reading 'toLowerCase')`
> 修掉 —— 它每次按键都可能复现，而且一抛就把同一事件上后面的键盘处理全带断。

## 修复 · 合成 keydown 事件让全屏动画的按键监听抛错（v001）

**现象**：打开 `https://www.bilibili.com/` 后控制台报

```
Uncaught TypeError: Cannot read properties of undefined (reading 'toLowerCase')
```

堆栈落在 `contentScripts/index.global.js` 里 `videoFullscreen` 那一段（展开后能看到
`webscreenAnim` / `wideAnim` 的判断）。

**根因**：为了在「按 W 切网页全屏」的那一下先量下播放器的旧位置（FLIP 的起始 rect），
`videoFullscreen.ts` 在 `document` 上挂了捕获阶段的 `keydown`，里面直接取 `key` 转小写：

```ts
const k = (e as KeyboardEvent).key.toLowerCase()
```

真键盘事件永远带 `key`，但页面上（以及别的扩展）会 `dispatchEvent` 合成事件 ——
`new Event('keydown')` 出来的是普通 `Event`，上面根本没有 `key`，于是 `.toLowerCase()`
抛 TypeError。

这条特别扎眼的原因有两条：

- 它挂在 `document` 的**捕获**阶段，等于拦在所有人前面，抛错会中断这次事件后续的监听处理；
- 首页也在跑（模块不按页面类型关），所以随便按个键都可能复现，跟播放页没关系。

**修法**：取到 `key` 先判类型，不是字符串就直接 `return`，后面的比较一个字不动。

```ts
const k = (e as KeyboardEvent).key
if (typeof k !== 'string') return
if (k.toLowerCase() === 'w') snapshotVideo()
```

**影响面**：只有「按 W 时提前存一份 rect」这一个副作用会被跳过（它本来也只在播放页有意义，
首页 `snapshotVideo()` 内部也是空转）。播放页真实按键的行为、全屏 / 宽屏动画都不变。

`DEV_VERSION` → `1.2.0 v001`，产物已写回 `extension/dist/contentScripts/index.global.js`。

## 优化 · 播放页「统一白边」：左右 / 中间 / 顶部都是 10px（v002）

**问题**：窗口态同一屏里有三种「白」——

- 左右两侧留白 `clamp(8px, 0.6vw, 14px)`（1678 窗口下 10、1920 下 11.5、2300 以上 14）；
- 左栏与右栏之间 24（半顶栏 12）；
- 播放器顶部：半顶栏时 10、**非半顶栏时 0**（播放器直接顶到顶栏下沿）。

于是窗口一宽两侧就比中间窄，半顶栏一关顶部干脆没有 —— 看着就是没对齐。用户要的是
「四边同一圈白」，而且不管半顶栏开不开都一样。

**改法**（`videoBeta.ts` 用一个 `EDGE = 10` 管三处）：

- 两侧留白：不再随窗口宽度变，固定 10（`--bili-vb-gutter`）；
- 左右栏间距：24 / 12 → 10（半顶栏不再单独收窄；左栏因此宽 14px，播放器高 ~8px）；
- 顶部：`#mirror-vdcon` 加 `padding-top: 10px`（只在窗口态，沉浸式不碰），两种模式都留。

半顶栏的上移量跟着从 54 → **64**：那 10px 空隙现在由 padding 出，左栏只负责把顶栏那
64px 让出来，落点仍是 10px。UP 卡的 `margin-top` 用同一个变量换算（`calc(up-y − 64)`），
实测 `up.top − title.bottom = 7.63 ≈ 8` 不变，卡片没有跟着掉。

**顺带修的一处**：非半顶栏时左栏的 sticky top 原本交给 B 站行内值（= 64），往下滚一钉住，
播放器顶部那 10px 白边就被顶栏吃掉了。现在两种模式都用 `--bili-vb-left-top` 接管
（CSS 加 `!important`），值 = B 站公式 + EDGE（**只对正值加**；左栏比视口高时行内值是负数、
由底边决定，一个像素都不动）。变量缺失时兜底 `auto`（这一帧不钉），不猜像素值。

**实测**（真实 Chrome，1678×547，BV1Qgn96oEUz，注入新 CSS + 新变量后量）：

| 模式 | 左白 | 右白 | 中间 | 播放器顶（视口坐标） |
| --- | --- | --- | --- | --- |
| 半顶栏开 | 10 | 10 | 10 | 10 |
| 半顶栏关 | 10 | 10 | 10 | 74 = 顶栏 64 + 10 |

`DEV_VERSION` → `1.2.0 v002`。

## 性能 · 播放页「打开 / 切视频变慢」：读写交错的强制排版（v003）

**现象**：1.2.0 之后播放页打开、点右栏切视频，都明显比 1.1.6 慢一拍。

**先量，别猜**（真实 Chrome / 同一稿件 / 同一网络，每档连跑两轮，
用「关掉设置面板里的『播放页优化』」做 A/B）：

| 指标 | 播放页优化 关 | 播放页优化 开 |
| --- | --- | --- |
| DCL | 655 / 672ms | 687 / 721ms |
| LCP | 1088 / 1228ms | **1420 / 1612ms** |
| 最长任务 | 332 / 345ms | **380 / 454ms** |
| 长任务合计 | 742 / 751ms | **826 / 968ms** |

也就是说这一块自己吃掉了 ~350ms 的 LCP、~120ms 的最长任务。

**根因：`layoutUp()` 里「写 CSS 变量 → 紧接着读几何」交错执行。**

`<html>` 上的自定义属性是**继承**的，改一个就等于整棵树的样式全部失效。实测
（3293 个元素 / 144Hz 屏）：

```
读 rect（布局干净）        0.00ms
写一个变量后读 rect        10.65ms
连写三个变量后读 rect      10.28ms   ← 一次重算，跟写几个无关
```

10ms 就是「整棵文档重新匹配样式 + 重新排版」。而老的 `layoutUp()` 是这样排的：

```
syncLeftTop  → 写 --left-top   ┐
syncUpPin    → 读 rect          ← 强制重算 ①
读 meta      → 写 --desc-top   ┘
读 title/up  → 写 --up-y/-h/-w
syncUpPin    → 读 rect          ← 强制重算 ②
```

最多四次。首屏 B 站水合那一秒里标题在重排、UP 卡在长高，`--up-y` / `--up-h` 几乎每帧
都要真的写进去 —— 于是每帧白烧 30~40ms，全落在 LCP 之前。

**改法：把「读」全部提到「写」前面。**

- 新增 `readGeom()` / `Geom`：左栏的 sticky 状态、rect、高度、包含块余量（原来 `leftRoom()`
  要另读两个 rect）一次读完；
- `layoutUp()` 重排成四段：**读（全部）→ 算 → 写（全部）→ 卡片钉在哪**；
- `leftPinTop(left, knownHeight?)` 复用已读高度，不再自己量一遍；
- `syncUpPin(left, upY?, geom?)` 复用调用方的几何，不再重复 `getComputedStyle` + 3 个 rect；
- 老的「先调一次无参 `syncUpPin`」和最后那次合并成一次（`upY` 为 null 时它自己会退回上次的值，
  语义不变，但少读一整轮）；
- `--left-top` 真的变了的那一帧，卡片要按**新**位置算 —— 这是唯一保留的「写完再读」，
  而且只在那几帧发生（`applyLeftTop()` 返回「改没改」）。

**验证**：新算法在页内复算一遍，和旧产物写进去的六个变量**逐值相同**：

| 状态 | `--left-top` | `--up-y` | `--up-h` | `--up-w` | `--up-top` | `--desc-top` |
| --- | --- | --- | --- | --- | --- | --- |
| 未滚动 | -433px | 671px | 48px | 585px | 238px | 44px |
| 滚到 710 | -2455px | 671px | 48px | 585px | -1784px | 44px |
| 滚到 2600（已钉住） | -2455px | 671px | 48px | 585px | -1883px | 44px |

`up.top − title.bottom = 8` 这条不变量在钉住态仍然是 8。

## 优化 · 掐掉 B 站的埋点上报（v003）

在真实 Chrome 里数了一遍「打开一次页面发多少请求」：

| 页面 | 总请求 | 其中 `data.bilibili.com/log/*` |
| --- | --- | --- |
| 播放页 | 204 | **59**（29%） |
| 首页 | 177 | **29**（16%） |

三个通道都在用：beacon 35 / XHR 18 / fetch 6（播放页）。全是纯上报，页面不读回包。
第一版（`telemetryBlock.ts`）是往页面里塞 inline `<script>` —— **这条路是错的，已废弃**：
扩展自己的 CSP（`script-src 'self'`）会直接挡掉，控制台报
`Executing inline script violates the following Content Security Policy directive`，
补丁一次都没装上（实测：装了之后 `fetch('https://data.bilibili.com/log/web')` 照样走网络）。
v004 改成 manifest 里 `"world": "MAIN"` 的独立脚本，见下面那一节。

- 为什么必须跑在页面世界：内容脚本在隔离世界，改 `navigator.sendBeacon` 不影响页面自己那份；
- 为什么不加 `declarativeNetRequest` 权限：商店对「不必要的权限」是直接拒的（见 `manifest.ts`
  里 permissions 的注释），而页面世界的脚本不需要任何权限就能改这三个 API；
- 判据写死「域名 + 路径」，别按 `log` 关键字全网匹配 —— `x/click-interface/web/heartbeat`
  是播放心跳（观看进度 / 历史靠它），`x/click-interface/click/web/h5` 是播放计数，都不能动。

## 优化 · 自绘顶栏的未读红点不占首屏（v003）

`loadUser()` 原来把 `nav`（头像 / 登录态）和 `msgfeed/unread`（消息红点）放在一个

## 修复 · 埋点拦截换成 MAIN world 脚本（v004）

v003 的 inline `<script>` 注入被**扩展自己的 CSP** 挡掉了（`script-src 'self'`，控制台
`Executing inline script violates the following Content Security Policy directive`）。
当时只验证了「补丁逻辑」，没验证「注入通道」—— 实测装上之后再发
`fetch('https://data.bilibili.com/log/web')`，请求照样走网络，resource 计数 +1。

改成 manifest 里一个独立的 content script 条目：

```json
{ "js": ["guard.js"], "run_at": "document_start", "world": "MAIN" }
```

`guard.js` 是**手写在 `extension/` 里、不走构建**的（MAIN world 里拿不到 `chrome.*`，
而构建产物那个 bundle 一进来就访问 chrome.storage，进不去）。`pnpm clear` 只删
`extension/dist` 和 `extension/manifest.json`，不会碰它；`pack-edge.mjs` 整个 `extension/`
一起打包，会带走。**以后改它要记得：源码就在 `extension/guard.js`，没有第二份。**

## 优化 · 广告投放请求也一起掐掉（v004）

在同一个 `guard.js` 里，除了埋点再加两条：

| 目标 | 理由 | 假响应 |
| --- | --- | --- |
| `data.bilibili.com/log/*` | 纯埋点，播放页 59 个 / 首页 29 个请求 | `{"code":0}` |
| `cm.bilibili.com/*` | 广告投放与计费（`cm/api/receive/content/pc` 取内容、`cm/api/fees/pc` 计费） | `{"code":-400,"message":"no ad"}` |
| `api.bilibili.com/x/vip/ads/*` | 大会员广告素材 | 同上 |

**关键取舍：不是让请求失败，而是回一个「这个位置没有广告」的假响应。**
直接报错会让 B 站那边停在 loading 状态 —— 广告位骨架 / 空槽就是这么来的；而「没有广告」
是它天天在走的分支（广告有频次控制，经常空），不会留任何占位。所有广告位本来也已经被
`adBlock.css` 藏掉了，所以内容根本没被用过。

三个通道都堵（实测同一批请求里 beacon / fetch / XHR 都在用）：

- `sendBeacon` → 直接返回 `true`（= 已排队，调用方不重试不报错）；
- `fetch` → `Response(body, {status:200})`；
- `XMLHttpRequest` → 把 URL 换成本地 `blob:`，原生走完一遍（同源，status 200、responseText、
  onload 全是真的，比自己伪造 `readyState` 稳）。**坑：blob 只认 GET**，`open('POST', blobUrl)`
  直接 onerror（而广告接口正好都是 POST）→ 重定向时把 method 一并改成 GET。

**验收（真实 Chrome，页面世界装同一份 guard.js 后逐条打）**：

| 探针 | 结果 | 是否走网络 |
| --- | --- | --- |
| `fetch` → `data.bilibili.com/log/web` | `{"code":0}` | 否（计数 27→27） |
| `XHR` → `data.bilibili.com/v2/log/web` | 200 / `{"code":0}` | 否 |
| `XHR` → `cm.bilibili.com/cm/api/fees/pc` | 200 / `{"code":-400,...}` | 否（计数 3→3） |
| `sendBeacon` → `data.bilibili.com/log/web` | `true` | 否 |
| `XHR` → `api.bilibili.com/x/web-interface/nav`（对照） | 200 / `{"code":-101}`（未登录） | **是**，原样透传 |

判据函数对四个不该拦的地址都返回 `null`：`x/click-interface/web/heartbeat`（播放心跳）、
`x/click-interface/click/web/h5`（播放计数）、`x/web-interface/nav`、以及任意 `blob:` URL。

## 优化 · 夜间模式关着时不再注入 night.css / 不再挂两个观察器（v005）

夜间模式默认**关**，但 `night.css`（14.5KB）以前是无条件注入的，`watchTheme()` 也照样挂了
两个 MutationObserver：一个盯 `<head>` 整棵子树（childList + href 属性），一个盯 `<html>`

但一条都匹配不上（所有规则都以 `html.bili-elite-night` 开头），不需要反复删了加。

## 优化 · 首页 header banner 的 28 张图层图不再下载（v006）

首页顶部那个大 banner 是一个 `animated-banner` 动画组件，由 **28 张** `/bfs/vc/*` 图层图
叠出来的（每张 7.3KB，合计约 **200KB**），而这块 banner 早就被「首页优化」用 CSS 藏了
（topbar.css §1）—— 图白下。

**为什么以前动不了**：轮播（`.recommended-swipe`）和大 banner 底图是 **SSR 在 HTML 里**的
`<img src>`，浏览器解析到就发请求，`display:none` / `content-visibility` 都不阻止图片下载，
任何 JS 都够不着。但这 28 张图层图不一样 —— 它们是 laputa-home 那个 Vue 应用**用 JS 建的**：

```
initiator: s1.hdslb.com/bfs/static/shanks/laputa-home/assets/index-84fb5632.js:48
（该 bundle 里 setAttribute("src" 出现 0 次、.src= 出现 24 次 → 走的是 IDL 属性）
```

所以 `extension/guard.js` 里换掉 `HTMLImageElement.prototype.src` 的 setter，在请求发出
**之前**把地址换成 1×1 透明 GIF。

**三道判据一起卡**，尽量别误伤：`www.bilibili.com` 首页（`/` 或 `/index.html`）+
「首页优化」开着（`html.bili-elite-home-only`）+ 地址带 `/bfs/vc/`。

**碎图怎么办**：关掉「首页优化」之后 banner 重新可见，而那些图已经不会再来了。
`topbarOptimize.ts` 的 `applyHomeOnly()` 里加了「**首页**上关掉首页优化就整页重载」——
用户只是点了个开关，页面本来也要重排，代价可接受；而且 reload 推迟到下一拍，
保证 `persist()` 的 `chrome.storage.sync.set` 先发出去（否则刷新回来开关还是「开」）。

**验收**（把 `extension/guard.js` 原样注入页面世界后打）：

## 未做 · 「内容脚本 305KB 拖慢 document_start」这条不成立（v006 实测）

原计划做代码分割。先量了三件事，结论是**没必要**：

| 项 | 实测 | 说明 |
| --- | --- | --- |
| 305KB bundle 的 V8 编译 | **3.57ms** | `node` 的 `new vm.Script()`（同一个 V8），25 次平均；V8 是惰性编译，只有顶层代码立即编译 |
| 注入 75KB CSS + 强制重算 | **~2ms** | 页面里造 2000 条规则后 `appendChild` + `getBoundingClientRect()` |
| 剩下的是执行 | 估 5~10ms | 5 份 `<style>`、自绘顶栏 DOM（`innerHTML` 约 10KB）、12 个 `bootstrapXxx()` 登记、一次 `storage.sync.get` |

加起来 10~15ms，占首页 FCP（~670ms）的 **2%**。为了这 2% 去做代码分割（`import()` +
`web_accessible_resources`、或者拆成两个 IIFE 包各自再跑一遍 `bootstrapConfig`），
换来的 FOUC 与「两个 config 实例」风险明显不划算，所以**没做**。

顺带排除的另外两条：
- 把页面级 CSS 挪到 `manifest.content_scripts[].css`（BewlyCat 就是这么干的）：CSS 注入
  实测只值 2ms，不值得为它冒「CSS 顺序 / 漏到个人空间页」的风险；
- `homePanelData` 那 26KB base64 的 `PARTS.join('')`：50 段拼 26KB 大约 0.1ms，而且那个文件
  是脚本生成的，不值得改。

## 参考 · BewlyCat 有没有可抄的（v006 结论：没有）

翻了 `bili_cat/BewlyCat` 的实现：

- 它的路线是**把整个页面换成自己的 Vue 应用**，`pageLoading.js` 只是主包起来之前用
  `opacity:0` 盖住首页、避免白屏的遮罩 —— 和我们「在 B 站原生 DOM 上做增强」是两条路，
  性能模型完全不同，没法照搬；
- `inject.global.js` 用 `world: 'MAIN'` 独立包注入 —— **和我们 guard.js 是同一套**，
  说明这条路是对的；
- 它**没有任何** prefetch / preconnect / 图片拦截；只有自己组件的 `loading="lazy"` 与
  `decoding="async"`。我们的 `hoverPrefetch`（悬停预取文档，实测 TTFB 380ms → 1ms）
  它没有对应物；
- 内容脚本同样是**单个 IIFE + CSS 内联成字符串**，也没做代码分割 —— 和上面的实测结论一致。

## 修复 · 关掉「首页优化」后首页无限刷新（v007）

**现象**：v006 里点一下「首页优化」把它关掉，首页就开始不停自己刷新。

**根因**：页面刚打开时 config 里全是**默认值**，`setupTopbarOptimize` 里那句
`applyHomeOnly(get('homeOptimize'))` 拿到的是默认的 `true`，于是
`html.bili-elite-home-only` 先被挂上；几十毫秒后 `chrome.storage.sync.get` 回来，
真实值是 `false` → `onConfigChange` → `applyHomeOnly(false)` —— 这时
`was = true && enabled = false`，**和「用户刚把开关关掉」长得一模一样**，于是又
`location.reload()`。刷新后重复同一套流程 = 死循环。

**修法**：让「副作用型的开关响应」只认**用户意图**。

1. `config.ts` 新增 `isUserEdit()`：`persist()` 里用 `userEditing` 包住
   `applyValues()`（try/finally），所以只有**设置面板点出来的**那次同步通知里它是 `true`；
   storage 快照、跨标签页同步两条路径永远是 `false`。
2. `applyHomeOnly()` 的重载条件加上 `isUserEdit()`，再补两道：
   - `isHomePage()`：搜索页 / 播放页没有这块 banner，不该被刷；
   - `!document.querySelector('.bili-header__banner animated-banner')`：**组件真的没挂上才刷**，
     万一以后 B 站换了实现、banner 还在，就不必打扰用户。

**「不刷新会不会坏」的实测结论**（先量再决定，没有拍脑袋）：

| 检查项 | 结果 |
| --- | --- |
| banner 底图 | 正常显示（1688×160，illustration 完整） |
| 全页碎图（`naturalWidth === 0` 且可见） | **0 张** |
| 空洞 / 空白块 | **没有** |
| `<animated-banner>` 组件 | **不在 DOM 里**（图层图被换成 1×1 后组件不挂载） |

也就是说「不刷新」**不会碎图、不会有空洞**，但 banner 会从「带动画层」变成「静态底图」。
所以按「需要刷新就只刷新一次」处理：保留重载，但只可能发生在**首页上用户亲手关掉这一下**，
一次，且 reload 推迟一拍（`setTimeout(…, 0)`）保证 `persist()` 的
`chrome.storage.sync.set` 先发出去 —— 否则刷新回来开关还是「开」。

**产物校验**（minify 后条件链仍然完整）：

```
function ul(e){const t=...,i=t.contains(fn);t.toggle(fn,e),
  i&&!e&&bc()&&dp()&&!document.querySelector(".bili-header__banner animated-banner")
  &&window.setTimeout(()=>location.reload(),0)}
```
（`bc` = `isUserEdit`，`dp` = `isHomePage`）

**性能影响**：`isUserEdit()` 只是一次布尔读，`document.querySelector` 只在**用户点开关那一帧**
跑一次 —— 加载路径上零开销。

`DEV_VERSION` → `1.2.0 v007`。

## 优化 · 首页首屏不再「震」一下（v008）

**现象**：首页刚打开 / 刷新时，整个屏幕会「震」一下 —— 卡片流突然重排一次。

**先量，再改。** 用 playwright + CDP screencast 逐帧录首屏、再用
`PerformanceObserver('layout-shift')` 记位移源节点，测出两处，都跟「滚动条 / 卡片被摘」
有关：

| 时刻 | layout-shift | 源节点 | 结论 |
| --- | --- | --- | --- |
| ~0.6s | （不计入 CLS，但改变 `clientWidth`） | `<html>` | 首帧只有顶栏（文档高 753 < 视口），**没有竖向滚动条**；信息流一渲染出来就溢出 → 滚动条出现 → `clientWidth` 1584 → 1567，居中 / 贴右的东西全部横移 8.5px |
| ~1.4s | **0.126** | `.bili-video-card__skeleton--cover` 从 x=794 跳到 402 | 楼层卡（番剧 / 直播）先以骨架身份排进栅格、画出来，**数据到了才被我们摘掉** → 整行卡片左滑一格、下面所有行整体上移一行高 |
| ~2.0s | 0.064 | `.bili-video-card` 批量消失 | B 站自己把骨架批次换成真卡（节点换了、格子没变），视觉上由下面的淡入盖住，不动它 |

**改法一：楼层卡改成「进栅格之前就已经不在」。**
`.floor-single-card` / `.bili-live-card` 原来写的是
`:not(:has(.floor-skeleton))`（只摘有数据的真卡、骨架留着占位），这条规则在加载过程中
会**由假变真**，于是「摘除」这个动作发生在已经画出来之后 —— 位移就是这么来的。
现在无条件 `display:none`：元素一插进来就不可见，栅格从第一次布局起就没有它，
后面再没有任何摘除动作。骨架不留也不会留空洞 —— `display:none` 的栅格子项**根本不占格**。

**改法二：滚动条常驻。**
`html.bili-elite-home-only { overflow-y: scroll }`，宽度从头到尾都是 1567。
**`scrollbar-gutter: stable` 单独写是无效的**（这条踩了坑）：隔离页面里能预留，
但 B 站这份文档上 `<html>` 的 overflow 会传播给视口、html 自己退化成 `visible`，
Chrome 不认 —— 实测 `clientWidth` 照样 1584 → 1567 来回跳，短内容时手动
`overflow-y: scroll` 才稳到 1567。代价是极短内容时右下露一条空轨道，首页信息流永远比
一屏高，看不到。

**改法三：卡片入场过渡重做（学 BewlyCat）。**
BewlyCat 的做法是「骨架和真卡同一套几何 + 只动 opacity」—— 几何不变就没有位移，
过渡只是观感。我们的骨架和真卡是**两个节点**（B 站自己换的），所以照它的思路做在真卡身上：

- 时长 160 → **220ms**（`--bili-dur-base`，卡片是有体积的东西），加 8px 上浮；
- 曲线换成 `cubic-bezier(.22,.61,.36,1)`（和搜索框聚焦同一条）—— 它前段跑得快，
  前 1/4 就到 0.5 以上，所以「从 opacity 0 开始」不会被看成空了一帧；标准曲线前段太慢，
  20 张卡同时淡入会整屏灰一下，那才真像闪；
- 位移用 `translate` 不用 `transform`：卡片自己和 B 站在封面放大上用了 transform，
  动画结束后残留 transform 会把它们顶掉；
- 打标的范围从「里面的 `.bili-video-card`」扩到**外层那一格**
  （`.feed-card` / `.bili-feed-card`），整格（含悬停衬底）一起淡入；
  并加了「祖先已打标就跳过」，否则外层和里层各淡一次，透明度乘成 0.25 起步，像漏了半张卡。

**验收（真实 chromium + 本扩展，1600×900）**：

| 检查项 | 改前 | 改后 |
| --- | --- | --- |
| `clientWidth` 首帧 → 加载完 | 1584 → 1567（来回跳两次） | **1567 → 1567** |
| layout-shift 最大单项 | 0.126（整行左滑） | **0.064**（只剩 B 站换节点，视觉被淡入盖住） |
| 栅格空洞 / 零宽子项 | — | 0 |
| 横向溢出（`scrollWidth > clientWidth`） | 无 | 无 |
| 滚动加载 | 43 → 223 张卡 | 43 → 223 张卡，顶栏保持 fixed / 64px |
| 入场类命中 | 只在里层卡上 | 31 格（`bili-elite-card-in`，`0.22s`，起始 `opacity 0`） |

`DEV_VERSION` → `1.2.0 v008`。

## 优化 · 夜间骨架去掉「扫光」+ 性能复核（v010）

### 一、扫光不是我们画的，是 B 站骨架自带的 `::after`

`§16.3` 早就把灰块换成了静止的斜向渐变（1.0.3 那版用户点名要的观感），但 B 站还给
每个骨架块挂了一层扫光叠层，我们一直没摘：

```
.floor-skeleton.show-animation .skeleton-item:after
.bili-video-card .loading_animation .bili-video-card__skeleton--{cover,text,light}:after
  content: ""; width: 400%;
  background: linear-gradient(-45deg, var(--graph_bg_regular) 25%, var(--bg1) 45%, …);
  animation: skeleton-loading 1.2s ease-in-out infinite;   /* translate(-75%) → 125% */
```

**白天看不出来**（浅灰扫浅灰），**夜里它取的是 `#232527 → #17181A`** —— 一条明显的黑带
横着扫过我们 14% 白的灰块。实测（夜间模式，从 document_start 逐帧读 `::after`）：

```
t=1258  .floor-skeleton .skeleton-item   skeleton-loading 1.2s
        host: floor-card single-card floor-skeleton show-animation
t=1483  .bili-video-card__skeleton--cover skeleton-loading 1.2s
        host: bili-video-card
        afterBg: linear-gradient(-45deg, rgb(35,37,39) 25%, rgb(23,24,26) …)
```

改法：直接把伪元素摘掉（`content: none`），而不是只 `animation: none` —— 留着的话静止的
渐变带还压在灰块上，多一层合成、两套渐变叠在一起。7 条选择器覆盖视频 / 直播 / 楼层三套
骨架。**白天也一起摘**：它本来就和我们「静止的有光泽的灰」冲突，白天只是看不出来；
顺带省掉 N 个 1.2s 无限循环动画的合成开销。

验收：同一支探针再跑一遍 → `[]`（骨架上一个 `::after` 动画都没有）。

### 二、顺手撤掉 v009 加的两条 `:has()` 摘卡规则

v009 为了「被 `.feed-card` 包一层的特殊卡」补了
`:has(.floor-single-card)` / `:has(.bili-live-card)`。复核线上 DOM：楼层卡 / 直播卡
**都是栅格直接子项**，这两条一次都没命中（实测被摘的只有轮播、2 张广告卡、18 张楼层卡，
全是直接子项）。而 `:has()` 是这类选择器里最贵的一种（每次 DOM 变化都要重新求值），
留两条空转的规则不划算 → 删掉。夜间白卡那个问题已经由 `night.css` §5.1 的
「选择器对齐」根治，不依赖这两条。

### 三、性能复核（真实 chromium，1600×900，夜间模式，各跑 2 次取范围）

| 阶段 | 首页优化 **开** | 首页优化 **关**（对照） |
| --- | --- | --- |
| FCP | 650 ~ 707ms | 680ms |
| DCL | 970 ~ 1051ms | 994ms |
| 长任务 | 6~7 个 / 合计 698~770ms / 最长 213~231ms | 9 个 / 831ms / 214ms |
| 加载前 3s 主线程 | task 1.60s（style 0.24 / layout 0.22） | — |
| 滚动 6s（信息流持续插卡） | task 1.66~1.95s，style 0.31~0.38s / 132~150 次，layout 0.10~0.11s | task 1.67s，style 0.31s / 135 次，layout 0.09s |
| 静置 6s | task 0.03~0.04s（≈0.5~0.7% CPU） | 0.6% |

结论：**「首页优化」这一整套（§16 的全部规则 + 三个 sync 函数）在滚动 / 静置阶段的开销
和关掉它时没有区别**（task 1.67 vs 1.66~1.95，落在噪声内）；加载阶段的长任务数还比关掉时
少 2 个。也就是说 v008 / v009 这几轮的改动没有引入性能回退。

顺带记两个数（以后不用再量）：滚动 6 秒插入 ~60 张卡，样式重算 132~150 次、合计
0.31~0.38s（≈2.5ms/次，1.4 万节点），布局 26~35 次 / 0.10s —— 都在 B 站自己的
Vue 渲染开销之下，不是瓶颈。

## 优化 · 播放页首帧前不再是一片黑（v011）

**起因**：用户反馈「同一台机器上，B 站原版直播页打开明显比视频页快 —— 框架成型快、开始播放也快」，
问能不能照着改。

### 一、先量清楚：视频页并不比直播页「重」

真实 Chrome 156、冷缓存、无扩展、每页一个独立 context，各跑 2 次：

| 指标 | 直播页 `/1` | 视频页 `/video/BV…` |
| --- | --- | --- |
| TTFB | **209 ~ 333ms** | **460 ~ 529ms** |
| FCP | **456ms** | 924 ~ 1112ms |
| LCP 元素 / 时刻 | `.room-bg` 满屏背景图 / **468ms** | `<video>` 首帧 / **1331 ~ 1600ms** |
| 首帧出画 | 2742 ~ 2971ms | **1331 ~ 1662ms** |
| 请求 / 字节 | 332 / 9.4MB | **245 / 7.9MB** |
| 脚本 | 121 个 / 5.7MB | **46 个 / 5.3MB** |
| 长任务 | 6 ~ 8 个 / 1.25s | 10 个 / 1.34s |

也就是说：视频页请求更少、字节更少、首帧还比直播页快一倍。**差距只在「首屏有没有画面」**：

- 直播页靠 SSR 的一张满屏背景图，0.45s 就把「页面已经打开了」这条信息给足，LCP 之后再不变化；
- 视频页的 LCP 就是视频首帧本身，而 **B 站已经不做 poster** —— `.bpx-player-video-poster`
  是空元素、0×0（实测），所以首帧之前播放器区域是**纯黑**，一黑就是 1.3~1.6s。

视频页 FCP 晚的机制（瀑布实测）：TTFB 460ms+，`#mirror-vdcon` 在 168KB HTML 的第 86KB 处；
head 里 6 个 render-blocking CSS + `core.js`(567KB) 全在 `s1.hdslb.com`，533ms 才开始下、
774ms 才结束。

### 二、能改的只有「黑屏那段」

服务端 TTFB、1.2MB 的 `video.js` 单体（443ms 长任务）、playurl 链路都动不了。能做的是
**在首帧之前把封面铺上去**：

- 封面地址来自 `__INITIAL_STATE__.videoData.pic`，不用额外接口；
- 取 `@672w_378h_1c.webp`（实测 20.6KB，`@320w` 只有 8.3KB 但铺到 1092px 宽的播放器上发虚）；
- 用 `.bpx-player-container::before` 画（`videoBeta.css` §10），**不往 `#mirror-vdcon` 插节点**；
- 摘除时机是 `loadeddata`（有画面了），另加 8s 兜底与 `error`。

### 三、踩到的坑：内容脚本读不到页面的 `window.__INITIAL_STATE__`

第一版直接在 `videoBeta.ts` 里读 `window.__INITIAL_STATE__.videoData.pic`，**一次都没生效**：
内容脚本跑在隔离世界，DOM 共享、JS 全局不共享。想退一步去解析内联脚本的文本，实测更绝 ——
浏览器 DOM 里**根本没有那个内联状态脚本**（`document.scripts` 里 0 个含 `"videoData"`，
而 curl 拿到的 250KB 响应里明明有），状态是外部脚本赋到 `window` 上的。

所以改成 `guard.js`（MAIN world，本来就在跑请求闸门）每 50ms 看一眼状态，读到就写到
`<html data-blie-pic>` —— 属性跨世界可见，而且不参与任何选择器，写它不会触发样式重算。
内容脚本只读这个属性。

### 四、验收

- 探针（`--load-extension` 起新实例，profile 冷）：封面 class **842ms** 挂上，
  `--bili-vb-poster` 指向 672w 那张；8s 无 `loadeddata` 时 **8884ms** 自动摘掉（兜底生效）；
  合成一次 `loadeddata` 立刻摘掉（主路径生效）。
- 真实 Chrome A/B（同一稿件、冷缓存）：**LCP 1596ms → 1192ms**（封面成了最大的一块绘制）；
  首帧 1357/1562/1721 vs 对照 1462/1589/1590，差值 −232/+100/+131ms，落在噪声里。
- 伪元素层级单独验过：把 `--bili-vb-poster` 换成纯红，播放器整块变红、底部发送栏与
  「登录免费看高清」提示仍在红色之上（`.bpx-player-control-wrap` 是 z-index 75）。

### 五、局限

首帧本身没有提前 —— 它由 playurl + 播放器 JS 决定，拦不掉。提前的是「屏幕上不再有
那 1.3s 黑块」，也就是用户说的「开始播放」的**感觉**。

`DEV_VERSION` → `1.2.0 v011`。

## 顶栏导航改成新标签页打开 + 修掉「切换视频闪上一条封面」（v012）

### 一、顶栏导航一律新标签页

用户要求：顶栏的「首页 / 动态 / 消息 / 收藏 / 历史」点下去别把当前页顶掉，改在右侧开新标签页。
站内没有对这些链接做点击拦截（查过 `selfTopbar.ts` 里没有 click 处理），所以只需要加属性：
`markup()` 里定义一个 `NEW_TAB = 'target="_blank" rel="noreferrer"'`，用在
`.tb-logo` / 首页 / 动态 / 四个右侧图标 / `.tb-avatar` 上。频道面板（「首页 ∨」里的那些）没动 ——
那是浏览辅助，不属于「导航」。

### 二、切换视频时不能重新铺封面（v011 的回归）

量切换的时候发现：**右栏推荐卡是 SPA 切换，不换文档**（`performance.timeOrigin` 不变，
`<video>` 元素被复用、`src` 换掉）。而 v011 在 `loadstart` 上重新铺封面，于是切换时会：

1. 把**上一条视频的封面**铺上去 —— `<html data-blie-pic>` 要等 `__INITIAL_STATE__` 更新
   （view 接口回来）才变，那时还是旧地址；
2. 盖住播放器**一直保留着的上一帧**（实测切换过程中画面是连续的，不是黑的）。

所以把 `loadstart` 那条监听整个删掉：封面只在首屏铺一次，`loadeddata` / `error` / 8s 兜底三个出口摘。

### 三、切换耗时实测（真实 Chrome，点右栏卡片，4 次）

| 阶段 | 耗时 |
| --- | --- |
| click → `loadstart`（router + view + playurl） | **215 ~ 297ms** |
| → `loadedmetadata` | 506 ~ 839ms |
| → `loadeddata`（新画面） | **782 ~ 1009ms** |
| → `playing` | **840 ~ 1251ms** |

同一批测量里把「播放页优化」关掉做对照：关 840 / 1067ms，开 993 / 1251ms —— 两组互相交叉，
**说明切换慢不是我们造成的**，剩下的是 B 站自己的接口链 + 媒体拉流解码。
（真要再快只能预取 playurl 和第一段 m4s，那需要 wbi 签名、每次悬停多两次请求 + 几百 KB，
没做。）

### 四、悬停时顺手预取「播放页要铺的那张封面」

`hoverPrefetch` 原来只预取文档。现在同一个 80ms 防抖里，再把卡片的封面换成播放页要用的
那个尺寸（`@672w_378h_1c.webp`，20.6KB）`as=image` 预取一份 —— 落到播放页时
`--bili-vb-poster` 一写上去图就在内存缓存里，黑屏段的封面能早 200~300ms 出现。
`as=image` 是浏览器最低优先级，不跟当前页抢带宽；上限 8 张。

验收：首页悬停一张卡后，`link[rel=prefetch][as=image]` 指向 `…@672w_378h_1c.webp`，
resource 里能看到这张图已经拉下来。

`DEV_VERSION` → `1.2.0 v012`。
